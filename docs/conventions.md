## Dart

Форматирование — `dart format` без исключений, ширина по умолчанию (80).
Проверка: `dart format --output=none --set-exit-if-changed .`

Анализ — `analysis_options.yaml` в корне (и отдельный, такой же, в
`example/`). Он строже, чем `package:lints/recommended`: включены
`strict-casts`, `strict-inference`, `strict-raw-types`, часть info поднята до
warning и error. `dart analyze` должен проходить без новых замечаний.

Правила, которых стоит держаться:

- Классы верхнего уровня — `final class`. Иерархий наследования в пакете нет.
- `@immutable` там, где класс действительно неизменяем. `Decimal` — исключение
  с явным обоснованием в коде (кеш `_packed`), и именно поэтому в нём стоят
  точечные `// ignore: avoid_equals_and_hash_code_on_mutable_classes`.
- Внутреннее представление (`base`, `scale`) помечается
  `@visibleForTesting`, а не делается приватным: тесты проверяют не только
  значение, но и форму его хранения.
- Приватные конструкторы `_asIs` (без нормализации) и `_pack` (с
  нормализацией) — принятые в пакете имена, держаться их.
- Импорты — относительные внутри `lib/src/` (`prefer_relative_imports` поднят
  до warning), `package:` — только для внешних зависимостей.
- Вспомогательные функции, нужные только пакету, живут в `lib/src/helpers.dart`
  как extension'ы с суффиксом `Internals`.
- `ignore`-комментарии — точечные, с причиной, если она не очевидна.
  Файловых `ignore_for_file` в `lib/` нет.

### Публичный API

Всё, что выходит наружу, экспортируется из `lib/yet_another_decimal.dart`.
Новые публичные символы добавлять только осознанно: пакет опубликован, и
любое расширение API придётся поддерживать.

Каждый публичный член снабжается dartdoc-комментарием по-английски. Стиль —
как в `Decimal`: первая строка — краткое описание, дальше при необходимости
пример в блоке ```dart. Ссылки на другие члены — в квадратных скобках
(`[base]`, `[Decimal]`).

Незаконченное помечается `// TODO(vi.k): ...` — этот формат уже используется
в коде, `flutter_style_todos` поднят до warning.

### Симметрия двух семейств

`Decimal` и `ShortDecimal` — параллельные реализации, и общий контракт держит
`lib/src/fixed_point.dart`. **Новый публичный член обязан попасть либо в
`FixedPoint`, либо в список расхождений `test/symmetry_test.dart`** — третьего
не дано: интерфейс уронит сборку, тест уронит сюиту.

Расхождений два вида, и оба перечислены явно:

- **по составу** — член есть у одного семейства и нет у другого
  (`fromBigInt`, `optimize`, `shiftLeft` в конструкторе);
- **по типу** — имена совпадают, типы разные (`inverse`, `divideToFraction`,
  `divideWithRemainder`, `operator ~/`). Такие в `FixedPoint` не выразить:
  общего супертипа у `Fraction` и `ShortFraction` нет.

Правка в одном семействе почти всегда требует зеркальной правки в другом:

| Правишь | Проверь также |
|:--|:--|
| `lib/src/decimal/decimal.dart` | `lib/src/short_decimal/short_decimal.dart` |
| `lib/src/decimal/fraction.dart` | `lib/src/short_decimal/short_fraction.dart` |
| `lib/src/decimal/division.dart` | `lib/src/short_decimal/short_division.dart` |

Если симметрию сознательно нарушают — написать в коде почему. Так уже сделано
трижды: три ступени снятия нулей и строковый кеш есть только у `Decimal`
(у `ShortDecimal` замеряно и медленнее или негде хранить), снятие десяток из
делителя — тоже (у `ShortDecimal` база упакована всегда).

## Тесты

Раскладка — по семействам и темам, файл на тему:

```
test/support/expect.dart          хелперы expectDecimal и прочие
test/support/reference.dart       эталонная модель и генератор
test/decimal/                     parse, arithmetic, divide, compare,
test/short_decimal/               convert, format, fraction, division
test/property_test.dart           законы против эталонной модели
test/competitors_test.dart        сверка с пакетом `decimal`
test/defects_test.dart            воспроизводители известных дефектов
test/symmetry_test.dart           наборы публичных членов двух семейств
test/bridge_test.dart             переходы между семействами
```

Правила:

- Проверять через хелперы из `test/support/expect.dart` (`expectDecimal`,
  `expectShortDecimal`, `expectFraction`, `expectDivision`, `expectDivide`,
  `expectDouble`), а не голым `expect`.
- **Внутреннее представление сверять только там, где оно и есть предмет
  проверки:** `parse`, `toString`, `toStringAsFixed`, `optimize`. В арифметике
  `base` и `scale` не передавать: форма результата там артефакт алгоритма, и
  оптимизация законно даёт другую форму при том же значении. `fractionDigits` —
  свойство значения, а не формы, его передавать можно везде.
- **Табличные случаи разворачивать наружу `test`,** чтобы каждый стал
  отдельным тестом с именем:

  ```dart
  for (final p in [...]) {
    test('$p', () { ... });
  }
  ```

  Цикл внутри одного `test` скрывает все случаи после упавшего. Исключение —
  циклы, где случаи не независимы (накопление суммы, перебор масштабов одного
  значения): там добавлять `reason`.
- Новую операцию покрывать в обоих семействах.
- Для `ShortDecimal` отдельно покрывать граничные значения `int`.
- Где `double` теряет точность, а пакет — нет, фиксировать это через
  `expectDouble(..., isValid: false)`.
- Тест на известный дефект пишется с **правильным** ожиданием и помечается
  `skip: 'ДN: …'`. Красных тестов в `main` нет; снятие `skip` — критерий
  готовности правки.

Язык в тестах: имена групп и тестов — как у соседей по файлу (в перенесённых
из старого монолита — по-английски, в написанных с нуля — по-русски).
Пояснения к файлу целиком (`///` в шапке) и к неочевидным ожиданиям —
по-русски: их читает владелец.

Каждая правка производительности проверяется **чередующимся** замером: машина
дрейфует на 15 % между прогонами, и последовательные «до» и «после» врут.
Порядок — `git checkout <база> -- lib/`, прогон, `git checkout HEAD -- lib/`,
прогон, и так дважды. Мерить только на закоммиченном: `git checkout` затирает
незакоммиченные правки в `lib/`.

Цифры, которые идут в `README.md`, снимаются иначе: весь набор гоняется
**дважды с разносом по времени**, и по каждой ячейке берётся лучшая из двух
медиан. Медиана пяти прогонов защищает от одного плохого замера, но не от
всплеска посторонней нагрузки, который длится дольше всей серии — а такой
всплеск может замер только замедлить. При последнем перемере два прохода
разошлись на 15 ячейках из 190, и все 15 — в сторону замедления.

Запуск: `dart test`. Покрытие:

```bash
dart test --coverage=.coverage
dart pub global run coverage:format_coverage --lcov --in=.coverage \
  --out=.coverage/lcov.info --report-on=lib \
  --packages=.dart_tool/package_config.json
```

## Совместимость с Flutter

Пакет опубликован, и его ставят в том числе во Flutter-приложения. Flutter
тянет часть пакетов из своего SDK и до недавнего времени пинил их **точной**
версией, а не диапазоном. Отсюда правило:

> Нижние границы констрейнтов держать достаточно низкими, чтобы то, что пинит
> Flutter, в них попадало. Поднимать нижнюю границу «чтобы было свежее» нельзя:
> это отрезает пользователей на живых версиях Flutter.

Что пинят установленные здесь версии:

| Flutter | Dart | `meta` |
|:--|:--|:--|
| 3.27.0 | 3.6.0 | 1.15.0, точно |
| 3.29.0 | 3.7.0 | 1.16.0, точно |
| 3.44.4 | 3.12.2 | 1.18.0, точно |
| 3.47.0 | 3.13.0 | `^1.18.3` |

Проверять резолвом, а не на глаз: минимальный пакет с `flutter` и
`flutter_localizations` из SDK плюс наш по пути, и `flutter pub get` нужной
версией из `~/fvm/versions/`. Проверено 2026-08-26 на всех четырёх — резолв
проходит везде:

| Flutter | Dart | `meta` в SDK | Что взял резолв |
|:--|:--|:--|:--|
| 3.27.0 | 3.6.0 | 1.15.0, точно | 1.15.0 |
| 3.29.0 | 3.7.0 | 1.16.0, точно | 1.16.0 |
| 3.44.4 | 3.12.2 | 1.18.0, точно | 1.18.0 |
| 3.47.0 | 3.13.0 | `^1.18.3` | 1.19.0 |

Отсюда нынешние границы: `sdk: ^3.6.0` и `meta: ^1.15.0`. Порог 3.6.0 — не
украшение: весь `dart test` прогоняется на Dart 3.6.0 из
`~/fvm/versions/3.27.0/bin/cache/dart-sdk/`, и правка, которая на нём падает,
не годится.

Там, где новая версия пакета требует SDK выше порога, констрейнт пишется
диапазоном, а не кареткой: `lints: '>=5.1.1 <7.0.0'` даёт 5.1.1 на Dart 3.6 и
6.1.0 на текущем. То же у `fixed` в `example/`.

**Языковая версия следует за порогом, а стиль `dart format` — за языковой
версией.** Порог ниже 3.7 означает старый стиль переноса строк; после
изменения порога проект переформатируется целиком, отдельным коммитом
`Format`. Смешивать его с содержательными правками нельзя.

`example/` живёт по тем же правилам, хотя Flutter-пакетом не является: тот же
порог SDK, те же диапазоны, `intl` резолвится в ту же версию, что просит
`flutter_localizations`.

## Бенчмарки

`example/` — не примеры использования, а стенд сравнения скорости. Новый
сравниваемый пакет добавляется файлом-адаптером в `example/lib/src/tests/` и
записью в `example/lib/src/packages.dart`. Цифры из прогона идут в таблицы
`README.md` — при обновлении таблиц указывать, на чём мерили.

## Коммиты

По-английски, повелительное наклонение, одна строка, без точки в конце — как
в существующей истории:

```
Add big_double to benchmarks for speed comparision
Fix links in README
Update dependencies
```

Не смешивать в одном коммите правки логики, форматирование и правки README —
в истории это уже разделено (`Format` отдельным коммитом).

**Не коммитить чужие правки вместе со своими.** Добавлять файлы поимённо
(`git add <файл>`), не `git add -A`, не `git commit -a`.

Мержить прямо в `main`, без PR.

## Версии и CHANGELOG

Версия — в `pubspec.yaml`, семантическая. Тег релиза — `vX.Y.Z`.

`CHANGELOG.md` по-английски, новые записи сверху. В нём принято объединять
близкие патч-версии в один заголовок диапазоном:

```markdown
## 1.1.0-1.1.2

- Update dependencies.
- Fix links in README.
```

Порядок публикации и правила разрешения на неё — в `AGENTS.md`, раздел
«Публикация на pub.dev».

# Архитектура

Устройство пакета `yet_another_decimal` и решения, которые за ним стоят.
Здесь только то, что меняется редко. Текущее состояние работ — в
`docs/handoff.md`.

## Задача пакета

Десятичные числа с фиксированной точкой без потери точности. Ключевое отличие
от соседей по pub.dev (`fixed`, `decimal_type`, `big_decimal`): деление нигде
не проходит через `double`, поэтому результат не портится на больших числах.
Подробное сравнение с обоснованием — в `README.md`.

## Два типа вместо одного

Пакет даёт два независимых типа с почти одинаковым API:

| | `Decimal` | `ShortDecimal` |
|:--|:--|:--|
| Хранилище | `BigInt` | `int` |
| Границы | нет | int64 (в JS — int53) |
| Переполнение | невозможно | **не контролируется**, тихо ломает результат |
| Нормализация | ленивая, с кешем | немедленная, в конструкторе |
| `@immutable` | нет (кеш `_packed`) | да, есть `const`-значения |
| Скорость | ниже | выше |

Это не наследники — два параллельных семейства классов с **общим контрактом**,
но раздельной реализацией. Дублирование реализации сознательное и подтверждено
замером: общая реализация над абстракцией стоит вдвое дороже из-за боксинга
`int` в поле типа `T`. Дорог именно общий **код**, а не общий **интерфейс**:
вызов у класса, реализующего интерфейс, при конкретном статическом типе
получателя стоит столько же, сколько без него — измерено, 0 %.

Контракт держит `FixedPoint` (см. ниже). Расхождения семейств, которые
расхождениями быть не должны, стали ошибкой компиляции.

Соответствие семейств:

| `Decimal` | `ShortDecimal` |
|:--|:--|
| `Decimal` | `ShortDecimal` |
| `Fraction` | `ShortFraction` |
| `Division` | `ShortDivision` |
| `DecimalDivideException` | `ShortDecimalDivideException` |

API двух семейств совпадает не полностью. Осознанные расхождения:

| | `Decimal` | `ShortDecimal` |
|:--|:--|:--|
| Конструктор | `shiftRight` | `shiftRight` **и** `shiftLeft` |
| Из целого | `Decimal(int)`, `Decimal.fromBigInt(BigInt)` | `ShortDecimal(int)` |
| Из строки | `parse`, `tryParse`, `fromJson` | то же |
| Расширения | `int.toDecimal()`, `BigInt.toDecimal()` | `int.toShortDecimal()` |
| `optimize()` | есть | не нужен — упаковка немедленная |

`shiftLeft` у `ShortDecimal` — не украшение: отрицательный `scale` для него
рабочий режим, и задавать его явно приходится чаще.

`toBigInt()` и `toInt()` есть теперь у обоих: раньше у каждого семейства было
своё. Различаются они точностью, а не наличием — у `ShortDecimal` `toInt()`
переполняется там, где `toBigInt()` точен.

Есть ещё четыре члена, у которых совпадают имена, но не типы: `inverse` и
`divideToFraction` возвращают дробь своего семейства, `divideWithRemainder` —
своё деление с остатком, `operator ~/` — `BigInt` против `int`. Их
`FixedPoint` описать не может (общего супертипа нет), и их держит явный список
в `test/symmetry_test.dart`.

## Общий контракт: `FixedPoint`

`lib/src/fixed_point.dart` — самоограниченный дженерик
`FixedPoint<T extends FixedPoint<T>> implements Comparable<T>`, который
реализуют оба семейства. Описывает 38 членов: арифметику, сравнения,
округления, преобразования и печать.

**Наружу не экспортируется.** Публичный интерфейс замораживается: расширять
потом можно, сужать — нет. Внутри же он инструмент дисциплины компилятора:
забыли член во втором семействе — ошибка сборки, а не находка ревьюера через
год. Проверено прямо: добавление в интерфейс члена, которого нет ни у кого,
роняет сборку обоих семейств сразу.

Самоограниченность параметра значит, что `Decimal` и `ShortDecimal` —
**несвязанные типы**: `decimalValue + shortValue` не соберётся. Это решение, а
не упущение: у смешивания пришлось бы выбирать тип результата, и любой выбор
неверен в половине случаев. Переход между семействами — явный, через мост.

## Мост между семействами

`lib/src/bridge.dart` — два расширения:

```dart
Decimal toDecimal();                    // на ShortDecimal, всегда точно
ShortDecimal? toShortDecimalOrNull();   // на Decimal, null при непредставимости
```

Вверх всегда безопасно: любое значение int64 — значение `BigInt`. Вниз может
не поместиться, поэтому `null`, а не исключение: значение вне диапазона здесь
нормальный ответ, а не ошибка.

Тонкость, на которой мост однажды уже ошибся: **смотреть надо на упакованную
форму, а не на сырую**. `Decimal.parse('1e20')` хранит базу `10^20`, которая в
int64 не лезет, — но упакованная форма (база 1, масштаб −20) лезет прекрасно.
Мост сначала пробует сырую пару, а при неудаче — печатную форму, единственную
упакованную, до которой снаружи класса можно дотянуться.

## Представление числа

Число хранится парой полей:

```
значение = base × 10^(−scale)
```

- `base` — значащая часть (`BigInt` или `int`);
- `scale` — положение десятичной точки.

`scale` может быть **отрицательным** — это значит, что у числа есть хвостовые
нули, которые не хранятся: `(base: 9223372036854775807, scale: −23)` — это
число из 42 цифр, укладывающееся в int64. Для `ShortDecimal` это не
оптимизация, а способ существования: считать такое число можно только в том же
масштабе, иначе `base` вылетит за границы `int`.

Оба поля помечены `@visibleForTesting` — это внутреннее представление, а не
часть публичного API. Для отладки есть `debugToString()`.

## Ключевые механизмы

### Выравнивание — `_align`

```dart
(BigInt, BigInt, int) _align(Decimal other)
```

Приводит два числа к общему `scale`, домножая меньшее на степень десяти, и
возвращает `(a, b, scale)`. На нём построено `+`, `-`, `%`, `~/`, `remainder`,
`divideToFraction`, `Division`.

Из этого следует главный инвариант равенства: **числа сравниваются по
значению, а не по представлению**. `(base: 60, scale: 1) == (base: 6, scale: 0)`.

**Сравнения у `ShortDecimal` через `_align` не идут.** Домножение при
выравнивании — это ровно то, что переполняет int64 молча и со сменой знака на
`10^19`: из-за него `0.000000000000000001 < 10` возвращало `false`, а
сортировка переставала быть сортировкой (дефект Д2). Вместо него `_compare`,
который домножает только когда результат заведомо помещается, а иначе отвечает
делением. `_align` остался у арифметики, где переполнение настоящее, а не
промежуточное.

Степени десяти не пересчитываются: у `Decimal` они кешируются по мере
надобности, у `ShortDecimal` лежат готовой таблицей от `10^0` до `10^18`.

### Нормализация — «упаковка»

Упаковка — снятие хвостовых нулей у `base` с уменьшением `scale`:
`(600, 2) → (6, 0)`.

- **`ShortDecimal`** упаковывает **сразу**, в фабрике `_pack`, после каждой
  операции. Иначе `int` переполняется абсурдно быстро: восемнадцати умножений
  `1.0 * 1.0` хватает, чтобы выйти за int64, хотя значение всё это время равно
  единице.
- **`Decimal`** упаковывает **лениво**, фабрикой `_pack`, и кеширует результат
  в изменяемом поле `_packed`. `BigInt` не переполняется, поэтому платить за нормализацию после
  каждой операции незачем. Упакованная форма нужна только там, где она
  действительно требуется: `hashCode`, `fractionDigits`, `isInteger`,
  `toString`. Публичный `optimize()` позволяет заплатить эту цену заранее —
  например, перед многократным выводом одного и того же числа.

Рядом с `_packed` живёт второй кеш — `_text`, печатная форма. Одно и то же
число печатают снова и снова (виджет во Flutter перестраивается десятки раз в
секунду), а каждый вызов заново делал арифметику `BigInt`, снятие нулей и
несколько `substring`. Десять печатей денежной величины стоили 613 нс, стали
11. Первая печать при этом не изменилась — а именно её выигрывало снятие нулей
строковыми средствами. У `ShortDecimal` такого кеша нет и быть не может:
конструкторы `const`, писать некуда.

Снятие хвостовых нулей у `Decimal` идёт тремя ступенями: нечётная база —
сразу ответ, до четырёх нулей — цикл, дальше — двоичный поиск с одним делением.
Средняя ступень не украшение: без неё поиск проигрывает циклу на чётных числах
без хвостовых нулей. У `ShortDecimal` те же три ступени **замедлили** всё —
там цикл идёт по машинным словам, и экономить нечего.

Оба кеша — причина, по которой `Decimal` не `@immutable` и почему в нём стоят
`// ignore: avoid_equals_and_hash_code_on_mutable_classes`. Наблюдаемое
значение при этом неизменно: `base` и `scale` — `final`.

Чего кеш **не** объясняет: отсутствие `const`-конструктора. У `BigInt` нет
`const`-конструктора вообще (`const x = BigInt.from(1)` — ошибка компиляции),
поэтому `const Decimal` недостижим независимо от `_packed`. Убрать кеш можно —
это даст `@immutable`, право на `@pragma('vm:deeply-immutable')` и позволит
избавиться от `optimize()`, — но `const` из этого не появится. Проверено
2026-08-25.

Обратная сторона у `ShortDecimal`: `const` там уже есть внутри
(`zero`/`one`/`two`/`ten`), но **наружу его отдавать нельзя**. Публичный
`const`-конструктор возможен только «сырой», без упаковки, а это отдаёт
пользователю право создавать неканоничные значения — ровно то, из-за чего
`ShortDecimal.ten` ломает `Set` и `Map` (дефект Д7).

`hashCode` считается по упакованной форме именно затем, чтобы согласоваться с
`==`, который сравнивает по значению.

### Деление — только точное

Деление возвращает результат, **только если он представим** конечной
десятичной дробью. Алгоритм:

1. делитель ноль — `UnsupportedError`;
2. вынести знак делителя (остаток в Dart неотрицателен, и отрицательный
   делитель иначе не доходит до единицы), а отрицать **результат**, не делимое:
   у `ShortDecimal` отрицание `int.min` теряет знак;
3. делитель единица или деление нацело — ответ сразу, без НОД и разложения;
4. иначе сократить на НОД;
5. вытащить из делителя десятки (это чистый сдвиг `scale`), затем степень
   двойки или пятёрки — целиком, а не по разряду;
6. если делитель после этого не стал единицей — результат непредставим.

Три формы одного и того же:

| Форма | Что делает при непредставимом результате |
|:--|:--|
| `divideOrNull` | возвращает `null` |
| `divide(other, {scaleOnInfinitePrecision})` | округляет до заданного числа знаков |
| `operator /` | бросает `DecimalDivideException` |

**Первичная — `divideOrNull`.** Ловля исключения стоит около 750 нс, чтение
`null` — 180: заглавный путь пакета не должен быть его самым медленным.
`operator /` — надстройка над тотальной формой, и цена надстройки нулевая.
Убрать `throw` из оператора — задача 2.0.

`isDivisibleBy` отвечает на вопрос «вернёт оператор или бросит», а не «делится
ли нацело»: три пополам делится в этом смысле, потому что 1.5 записывается.

Исключение — не тупик, а способ вернуть управление вызывающему. Оно несёт в
себе всё, что можно сделать дальше:

```dart
try {
  final r = a / b;
} on DecimalDivideException catch (e) {
  e.fraction;               // Fraction — точная дробь
  e.quotientWithRemainder;  // Division — частное и остаток
  e.round(2);               // Decimal — округлить до 2 знаков
  e.floor(2); e.ceil(2); e.truncate(2);
}
```

Те же результаты доступны и без исключения: `divideToFraction`,
`divideWithRemainder`, `divideToDouble`.

Поэтому `DecimalDivideException` — `Exception`, а не `Error`: это штатная
развилка, а не ошибка программиста.

### `Fraction` — точная дробь

Рациональное число: `numerator` / `denominator`, всегда сокращённое,
знаменатель всегда положителен (знак живёт в числителе). Арифметика `+ - * /`,
сравнение, модуль, обращение, `toDouble`, округления
`floor`/`round`/`ceil`/`truncate` до заданного числа знаков — именно они
превращают непредставимое деление в `Decimal`. Отрицательное число знаков
поддерживается: это округление до десятков и выше, как у самих чисел.
`Fraction` `@immutable`, в отличие от `Decimal`.

У `ShortFraction` три места, где int64 заставляет делать иначе:

- **сокращать перекрёстно до умножения**, а не после: иначе произведение двух
  int64 переполняется там, где точный результат представим;
- **знак нормализовать после сокращения НОД**: `2 / int.min` становится
  нормализуемым только после того, как двойка сокращена. Если и после
  сокращения знаменатель равен `int.min` — `ArgumentError`, значение
  непредставимо;
- **округление к числу знаков, которое в int64 не влезает**, считается в
  `BigInt` и сужается обратно; если не влезает и результат, возвращается
  ближайшее представимое. Это единственное место, где переполнение не
  молчаливое: молчаливое здесь меняло знак.

### `Division` — частное с остатком

`quotient` (целое) и `remainder` (`Decimal`). Инвариант, проверяемый в тестах:

```
quotient * divisor + remainder == dividend
```

### `fastGcd`

Свой цикл Евклида в `lib/src/helpers.dart` вместо `BigInt.gcd`, см.
[dart-lang/sdk#46180](https://github.com/dart-lang/sdk/issues/46180).

Пара, помещающаяся в машинные слова, уходит на `int`-путь: он быстрее
штатного `int.gcd` втрое, и деление денежных значений от него вдвое быстрее.
Остальные идут циклом Евклида.

**Порог по величине из ревью проверен и отвергнут.** Ревью рекомендовало на
длинных сопоставимых операндах звать штатный `BigInt.gcd`, обещая 2.5×; замер
на этой машине дал обратное — вдвое медленнее на дробях из 60-значных чисел.
Урок, записанный в самом ревью («мерить только внутри пакета»), сработал второй
раз, теперь против его же рекомендации. Вердикт — в
`docs/records/2026-08-25[3]-package-review.md`, раздел П1, подробности — в
`2026-08-26[4]-wave-3-performance-report.md`.

Условие «помещается в машинное слово» проверяется через `isValidInt`, а не
через `bitLength`: замер показал, что `bitLength` дороже деления.

Используется в `operator /` и при сокращении дробей.

## Границы `ShortDecimal`

Переполнение **не проверяется намеренно**. Проверка на каждой операции
кратно замедлила бы сложение, ради скорости которого этот тип и существует:

```dart
ShortDecimal(9223372036854775807) + ShortDecimal.one; // -9223372036854775808
```

В границы int64 должна укладываться значащая часть — `base` без хвостовых
нулей. Само число может быть сколь угодно длинным, пока с ним работают в его
собственном масштабе. Развёрнутое объяснение с примерами — в `README.md`,
раздел «`ShortDecimal` limitations».

Молчаливое переполнение — контракт типа, но **не оправдание для случаев, где
и аргументы, и канонический результат в int64 укладываются**, а переполняется
только промежуточное значение. Такие места починены: умножение сокращает
двойку против пятёрки до перемножения (`2^62 * 5` теперь считается), дроби
сокращаются перекрёстно, округление уходит в `BigInt` и возвращается.

`_pow10` — таблица от `10^0` до `10^18`, а не `math.pow`: тот молча
оборачивался, причём `10^19` — в **отрицательное** число.

## Исключения

| Исключение | Когда |
|:--|:--|
| `DecimalDivideException`, `ShortDecimalDivideException` | результат деления непредставим |
| `FormatException` | `parse` не разобрал строку (`tryParse` вернёт `null`) |
| `UnsupportedError` | деление на ноль — везде, включая `operator /`, `divideOrNull` и `inverse` |
| `ArgumentError` | отрицательный `fractionDigits`, `precision <= 0`, `lowerLimit > upperLimit` в `clamp`, непредставимая нормализация `ShortFraction` |

Тексты всех сообщений — по-английски.

Три свойства методики, за которые стоит держаться:

- **эталонная модель не использует код пакета** — иначе она повторяла бы его
  ошибки вместо того, чтобы их ловить;
- **представление сверяется только там, где оно и есть предмет проверки**
  (`parse`, `toString`, `toStringAsFixed`, `optimize`), а в арифметике нет:
  оптимизация законно даёт другую форму при том же значении;
- **дефект получает тест с корректным ожиданием и пометкой `skip`**, снятие
  которой и есть критерий готовности правки. Красных тестов в `main` не
  бывает.

`expectDouble` умеет проверять и «сломанный» случай (`isValid: false`) — так
в тестах зафиксировано, где `double` действительно теряет точность, а
`Decimal` нет.

## `example/`

Отдельный пакет (`publish_to: none`). В нём две вещи: `bin/example.dart` —
короткий тур по пакету для читателя pub.dev, и стенд сравнения скорости с
`decimal`, `fixed`, `decimal_type`, `big_decimal`, `big_double`, цифры из
которого попадают в таблицы `README.md`.

```
example/bin/example.dart      тур: точность, деление, деньги, мост
example/bin/benchmark.dart    точка входа стенда, теги и `--runs=N`
example/bin/format.dart       вспомогательная утилита
example/lib/src/packages.dart перечень сравниваемых пакетов
example/lib/src/tests.dart    перечень бенчмарков и их данные
example/lib/src/operations.dart операции
example/lib/src/run.dart      прогон, серия, сводная таблица
example/lib/src/tests/*.dart  по файлу-адаптеру на каждый сравниваемый пакет
```

Аргументы фильтруют прогон по имени или тегу, префикс `-` исключает:
`dart bin/benchmark.dart divide -fixed`.

Операций одиннадцать: `add`, `multiply`, `divide`, `divide-and-view`,
`raw-view`, `repeat-view`, `parse`, `compare`, `round`, `to-double`,
`to-string-as-fixed`, `unrepresentable-divide`.

Методика — то, ради чего стенд переделан в волне 5. Без неё он врал:

- **Ответ каждого бенчмарка сверяется до замера.** Ожидаемое значение лежит
  рядом с набором и посчитано вне Dart, точной рациональной арифметикой.
  Неверный ответ не может оказаться «быстрым»; так у `fixed` вылез
  `compareTo`, который сравнивает базы, не приведя масштабы.
- **Отсутствие операции — не ошибка.** Адаптер не переопределяет то, чего у
  пакета нет; база бросает `UnsupportedOperation`, в таблице появляется «—».
- **Серия прогонов и медиана** (`--runs`, по умолчанию 5). Один прогон не
  значит ничего: машина дрейфует на 15 %. Рядом с медианой печатается разброс.
- **Результат каждого цикла уходит в сток** (`MyBenchmarkBase.blackhole`) —
  статическое поле, которое оптимизатор не вправе выбросить.
- **Шапка окружения** печатается перед прогоном: версия Dart, ОС, число ядер,
  JIT или AOT, версии сравниваемых пакетов из `pubspec.lock`.
- **Наборы двух сортов:** «круглые» (степени десяти, один повторённый
  множитель) и `dirty` — без нулей на концах, без общих множителей и без
  повторов цифр.

`repeat-view` до 1.2.0 назывался `prepared-view` и не мерил ничего: он печатал
одно и то же значение сто раз подряд, и строковый кеш отвечал на девяносто
девять из них. Теперь пара честная: `raw-view` — первая печать,
`repeat-view` — все последующие.

# План волны 5. Документация и стенд

Волна закрывает четыре пункта бэклога владельца: dartdoc («write comments
(doc)»), `example/README.md` («write example/README»), замер
`toStringAsFixed` («test and performance for toStringAsFixed») и граничные
случаи `ShortDecimal` — последний, похоже, уже закрыт волной 0, это надо
проверить по коду, а не по памяти.

## Почему стенд идёт первым

README волны 5 обязан показать свежие цифры. Взять их неоткуда, кроме стенда,
а стенд сейчас врёт как минимум в одной строке и молчит в семи сценариях,
которых у него нет вовсе. Значит, порядок жёсткий: сначала методика, потом
данные, потом сценарии, потом прогон, и только потом таблицы в README.

Остальные три пункта (dartdoc, `example/README.md`, `pubspec.yaml`) от стенда
не зависят и могут идти в любом порядке после.

## Что со стендом не так

Разбор по коду `example/lib/src/`.

### С1. `prepared-view` перестал что-либо мерить

`MyBenchmarkBase.exercise` для `Op.preparedView` зовёт `prepareValues()` один
раз, а потом гоняет `preparedView()` сто раз подряд **по одному и тому же
списку значений**. Пока у `Decimal` не было строкового кеша, каждый из ста
проходов честно печатал число заново. С кешем печатается только первый, а
остальные девяносто девять читают указатель: 15.9 мкс превратились в 0.023.

Хуже того, `measure()` из `benchmark_harness` зовёт `exercise()` в цикле две
секунды — кеш переживает и это, потому что объекты те же.

Честно измерить «печать подготовленного числа на холодную» на одном и том же
объекте под кешем нельзя в принципе. Значит, сценарий надо не чинить, а
назвать своим именем: он меряет **повторную** печать, и это ровно тот сценарий,
ради которого кеш и заводился. Холодная печать остаётся за `raw-view`, где
`-(-value)` каждый раз создаёт новый объект.

### С2. Результат цикла может быть выброшен оптимизатором

Внутри `exercise` результат каждого прохода складывается в локальную
переменную, и наружу уходит только последний. Формально возврат из метода
материализует последнее значение, но не девяносто девять предыдущих. Для
операций, у которых нет побочных эффектов, это приглашение оптимизатору.
Нужен сток, который нельзя выбросить: запись в статическое поле.

### С3. Все базы «чистые»

В наборах либо `10000000000000000000`, либо `123456789`, либо степени десяти,
либо `123`. Такие значения — лучший случай для снятия нулей, для `gcd` и для
быстрого пути деления. Реальные суммы выглядят иначе. Нужен набор с
«грязными» базами: детерминированный генератор с фиксированным зерном, ни
одного круглого числа.

### С4. Семи сценариев нет вовсе

Стенд знает шесть операций: `add`, `multiply`, `divide`, `divide-and-view`,
`raw-view`, `prepared-view`. Не меряется ничего из того, что пользователь
делает не реже: `parse`, сравнения и сортировка, округления, `toDouble`,
`toStringAsFixed`, дроби, непредставимое деление.

`toStringAsFixed` — прямое пожелание владельца из бэклога.
Непредставимое деление — единственный сценарий, где видна цена тотальных
форм (`divideOrNull`) против ловли исключения.

### С5. Один прогон вместо серии

`_measureTest` меряет один раз и печатает результат. Машина дрейфует на 15 %
между прогонами — это записано в `docs/conventions.md` и проверено на волне 3.
Цифры в README должны быть медианой серии, а не выстрелом наугад.

### С6. Не записано, на чём мерили

В README сказано «на MacBook Pro M1», и всё. Версия Dart, версии сравниваемых
пакетов, число ядер — ничего. Через год цифры будет не с чем сопоставить.

## Шаги

### Ш1. Методика

Правится `example/lib/src/tests/my_benchmark_base.dart` и
`example/lib/src/run.dart`.

1. **Сток.** `static Object? blackhole;` в `MyBenchmarkBase`, запись в него на
   каждом проходе цикла в `exercise`. Статическое поле оптимизатор выбросить не
   может.
2. **Серия и медиана.** `run()` получает число прогонов (по умолчанию 5),
   каждый бенчмарк меряется столько раз, в сводку идёт медиана. Рядом с
   медианой печатается разброс (min…max), чтобы дрейф машины был виден
   глазами. Флаг командной строки — `--runs=N`.
3. **Окружение.** Перед прогоном печатается шапка: версия Dart
   (`Platform.version`), ОС (`Platform.operatingSystemVersion`), число ядер,
   режим (JIT/AOT) и версии сравниваемых пакетов из `pubspec.lock`. Эта шапка
   целиком уходит в README под таблицу.
4. **`prepared-view` называется своим именем.** Описание сценария переписать:
   он меряет повторную печать одного и того же значения. `raw-view` остаётся
   холодным путём. В README обе строки подаются как разные вопросы: «сколько
   стоит напечатать число впервые» и «сколько стоит напечатать его снова».

### Ш2. Грязные базы

Правится `example/lib/src/tests.dart`.

Детерминированный генератор (`Random(20260826)`), базы из непериодических
цифр, масштабы вразнобой. Варианты для четырёх сценариев: `add-dirty`,
`multiply-dirty`, `divide-dirty`, `raw-view-dirty` — по версии на `BigInt` и на
`int`. Ожидаемый результат считается один раз и вписывается в код константой,
как это уже сделано для остальных наборов: стенд обязан сверять ответ, иначе
он меряет скорость неправильных вычислений.

### Ш3. Недостающие операции

Правятся `example/lib/src/operations.dart`, `tests.dart`, все адаптеры в
`example/lib/src/tests/`.

Новые `Op`: `parse`, `compare` (сортировка списка), `round`, `toDouble`,
`toStringAsFixed`, `unrepresentableDivide`.

Дроби (`divideToFraction`) в стенд не идут: аналога нет ни у одного
конкурента, сравнивать не с чем, а собственную цену дробей меряет тест
производительности внутри пакета. Решение записать в отчёт.

Не всякий пакет умеет всякую операцию. Базовый класс получает
`Set<Op> get unsupportedOperations => const {}`; `run()` такие пары
пропускает, и в сводке появляется «—» со сноской «Not supported» — механика
для этого в `_printSummary` уже есть. Так стенд не будет выдавать отсутствие
метода за ошибку.

### Ш4. Прогон и фиксация

`dart compile exe example/bin/benchmark.dart`, прогон `all` в AOT, серия из
пяти, медиана. Результат — в отчёт волны 5 целиком, в README — выжимкой.

# Ревью проекта перед публикацией 1.2.0

## Как проводилось

Четыре независимых агента по областям: семейство на `BigInt`, семейство на
`int64`, публичный API с документацией, тесты со стендом. **Каждая находка,
попавшая в этот отчёт, перепроверена мной лично прогоном** — то, что
воспроизвести не удалось, сюда не попало. Репозиторий не менялся: все пробы
выполнялись во временных файлах вне дерева.

Инструменты на момент ревью: `dart analyze` чист на Dart 3.13.0 и 3.6.0,
`dart format` чист, 598 тестов зелёные на обоих SDK, покрытие `lib/` — 100 %
строк, `pana` 160/160, `dart pub publish --dry-run` без предупреждений.

**Ни один из этих инструментов не поймал ни одной находки ниже.** Это главный
вывод о состоянии проверок, а не о состоянии кода.

## Executive summary

Пакет хорошо устроен, аккуратно документирован и плотно покрыт тестами.
Проблема в другом: **проверки измеряют не то, что нужно**. Сто процентов
покрытия строк достигнуто при том, что целая ветка печати не исполняется ни
одним тестом, а отрицательное число знаков у `ShortDecimal` не проверяется
вовсе — четыре мутации кода выживают.

Семь находок уровня High. Четыре из них — молчаливо неверные числа:

- прибавление нуля меняет значение (`ShortDecimal`, от 1e19);
- `~/` и `/` дают разные ответы на одних и тех же данных, при том что верный
  ответ представим;
- деление на `int.min` даёт неверный знак;
- `divideToDouble` возвращает ноль вместо представимого субнормального числа.

Три оставшиеся High — про обещания: устаревание, объявленное в `CHANGELOG`, до
пользователя не доходит; раздел README про оптимизацию опровергается
собственным кодом пакета; публичная претензия README к пакету `fixed` не
воспроизводится, а её примеры не компилируются.

Важно для оценки риска: **почти все дефекты — старые**, не из последних волн.
Единственная High-находка, внесённая в этой сессии, — Р5 (неработающее
устаревание). Прямое округление деления, новые члены, единый тип исключения и
раздельные точки входа проверены отдельно и претензий не вызвали.

## Project overview

Пакет даёт два независимых типа десятичных чисел с фиксированной точкой:
`Decimal` на `BigInt` (без ограничений) и `ShortDecimal` на `int` (быстрый, с
молчаливым переполнением). Оба хранят значение как `base × 10^-scale`.

Устройство: `lib/src/decimal/` и `lib/src/short_decimal/` — два параллельных
семейства по три типа в каждом (число, дробь, деление с остатком);
`lib/src/fixed_point.dart` — внутренний интерфейс, держащий состав членов
одинаковым; `lib/src/bridge.dart` — явные переходы между семействами;
`lib/src/helpers.dart` — общие примитивы (`fastGcd`, разбор десятичной
строки). Три точки входа: зонтичная и по одной на семейство.

Ключевое архитектурное решение — **дублирование вместо обобщения**: замерено,
что общая реализация через дженерики стоит вдвое дороже из-за боксинга.
Контракт держит интерфейс, расхождения перечислены явно в тесте симметрии.

## Critical and high-severity findings

### Р1. Прибавление нуля меняет значение

**High.** `lib/src/short_decimal/short_decimal.dart:220-232` (`+`, `-`), корень
— `_align` (`:1139-1152`) и `_pow10` (`:1026-1033`).

`_align` домножает базу операнда с меньшим масштабом на `_pow10(разрыв)`. При
разрыве больше 18 `_pow10` уходит в `math.pow` и заворачивается. Когда второй
операнд — `zero`, домножается база **самого числа**, а не нуля.

```
1e18 + zero => 1000000000000000000    ок
1e19 + zero => -8446744073709551616   неверно
5e64 + 3    => 3                      число исчезло целиком
```

Канонический результат здесь — само `x`, он представим тривиально;
переполняется только промежуточное. По правилу владельца
(`docs/handoff.md`, «Переполнение чинится только там, где канонический
результат помещается в int64») это дефект, а не задокументированное молчаливое
переполнение.

**Сценарий:** `values.fold(ShortDecimal.zero, (a, b) => a + b)` — обычный
способ сложить список — портит сумму, если хоть одно значение от 1e19. README
эти значения прямо рекламирует как поддерживаемые (`README.md:658-670`).

**Асимметрия:** на малых числах (масштаб > 0) всё цело — там домножается база
нуля. Проверено от 1e-16 до 1e-20.

**Направление:** короткое замыкание на нулевом операнде в `+`/`-` (цена
нулевая, закон восстанавливается) плюс системно — `_alignOrNull` через уже
существующий `_scaledOrNull`, как это сделано в `_compareScaled`.

> **Вердикт (2026-08-26):** исправлено коротким замыканием. `+` и `-` отвечают
> до выравнивания, если один из операндов ноль, — одна проверка ценой в
> сравнение. Проверено на сдвигах 0, 5, 18, 19, 25 и 60 во всех четырёх
> сочетаниях, плюс `fold(zero, +)`. Системное `_alignOrNull` **не делалось**:
> для `+`/`-` разрыв масштабов больше восемнадцати при ненулевых операндах
> означает, что точный ответ и правда непредставим, — там молчаливое
> переполнение остаётся контрактом. Разбор в Р2 показывает, где оно контрактом
> не является.

### Р2. `~/` и `/` расходятся, хотя верный ответ представим

**High.** `short_decimal.dart:468-476` (`~/`), `:497` (`remainder`),
`:483-494` (`divideToFraction`, `divideToDouble`), `short_division.dart:28-33`.

```
2e19 /  4 => 5000000000000000000   верно
2e19 ~/ 4 => 388313981572612096    неверно
2e19 divideWithRemainder 4 => 388313981572612096
1e-19 divideToDouble 1 => -1.1838881245526248e-19   (ожидается 1e-19, и знак!)
```

Тот же корень, что у Р1. `5000000000000000000` укладывается в int64 с запасом,
то есть это снова промежуточное переполнение при представимом результате.

**Это опровергает записанное решение.** `docs/handoff.md` утверждает: «`_align`
остался у `~/`, `%`, `remainder`, `divideToFraction` и `ShortDivision`: там
переполнение настоящее, а не промежуточное, и остаётся молчаливым». Посылка
неверна — переполнение промежуточное. Решение надо пересматривать, а не только
чинить код.

**Что я проверил лично:** `~/`, `divideWithRemainder`, `divideToFraction`,
`divideToDouble`. Для `%` и `remainder` на тех же данных ответ оказался верным
(`2e19 % 4 => 0`) — они делят тот же `_align`, но конкретного входа, на котором
они врут, я не воспроизводил.

**Направление:** `_alignOrNull` + запасной путь на `BigInt`, по образцу
`ShortFraction._addExactly` и `_dropFractionExactly`, где эта схема уже
реализована.

> **Вердикт (2026-08-26):** исправлено. Появились `_alignOrNull` (через уже
> существующий `_scaledOrNull`) и `_alignExactly` на `BigInt`; на точный путь
> переведены `~/`, `%`, `remainder`, `divideToFraction`, `divideToDouble` и
> `ShortDivision`. Где ответ представим — он теперь верный: `2e19 ~/ 4` даёт
> `5000000000000000000` и согласуется с `/`, инвариант деления с остатком
> держится, `1e-19.divideToDouble(1)` даёт `1e-19` вместо отрицательного
> мусора.
>
> `divideToFraction` сокращает пару на НОД **до** возврата в int64: сама
> выровненная пара может из него выйти, а та же дробь в низших членах —
> помещаться.
>
> `divideToDouble` больше не ходит через `ShortFraction`: double представим и
> там, где дробь нет. Заодно он перестал делить `int` на `int` — это округляло
> дважды на операндах длиннее 2^53, то есть Р8 в миниатюре. Оба семейства
> теперь зовут одно и то же корректное преобразование, переехавшее в
> `helpers.dart`.
>
> **Решение в `docs/handoff.md` пересмотрено:** посылка «там переполнение
> настоящее, а не промежуточное» опровергнута этой находкой и заменена.
>
> Молчаливое переполнение остаётся там, где точный ответ и правда
> непредставим: пример из README (`922337203685477580700000000000000000000000
> - 1`) теперь закреплён тестом как контракт, а не как случайность.

### Р3. Деление на `int.min` даёт неверный знак

**High.** `short_decimal.dart:343-425`, конкретно `:361-364`.

```dart
final negate = divisor.isNegative;
if (negate) divisor = -divisor;   // -int.min == int.min
```

Комментарий рядом объясняет, почему отрицается результат, а не делимое, — но
`-divisor` болеет ровно тем же.

```
min / min                     => -1     (у Decimal: 1)
min divideWithRemainder min   =>  1     ← два члена пакета противоречат друг другу
2^62 divideOrNull min         => null   (представимый ответ -0.5 отброшен)
```

Затрагивает `operator /`, `divideOrNull`, `isDivisibleBy`, `pow` с
отрицательным показателем. `-1` вместо `1` — молчаливо неверное значение.

**Направление:** снимать знак после сокращения на НОД, как это уже сделано в
`ShortFraction`, либо особый путь для `divisor == int.min`. Осторожно:
`fastGcd(int.min, int.min)` возвращает `int.min`, так что «сначала НОД» само по
себе не спасает.

> **Вердикт (2026-08-26):** исправлено особым путём. Если после снятия знака
> делитель всё ещё отрицателен — это `int.min`, — оба конца делятся пополам:
> отношение сохраняется, а делитель приходит в диапазон. Для нечётного
> делимого это невозможно, и там честный `null`: точный ответ потребовал бы
> `5^63`, чего int64 не держит. Теперь `min / min` даёт 1 (как у `Decimal`),
> `divideWithRemainder` с ним согласован, а `2^62 / int.min` возвращает −0.5
> вместо `null`.

### Р4. `divideToDouble` отдаёт ноль вместо представимого числа

**High.** `lib/src/decimal/decimal.dart:471-493`, строка 492.

`math.pow(2.0, -shift)` теряет значимость при `shift > 1074`, и весь диапазон
субнормальных схлопывается в ноль:

```
1 / 1e307 => 1.0000000000000001e-307   ок
1 / 1e308 => 0.0                        должно быть 1e-308
toDouble(1e-310) => 1e-310              тот же пакет, другой путь — верно
```

Комментарий на `:482-483` («An exponent out of range turns into zero or
infinity here, which is the right answer for a ratio out of range») верен
только для тех отношений, которые действительно вне диапазона. Эти — внутри.

Это тот же класс, что Д8 (`NaN` из деления `BigInt`), который `CHANGELOG.md`
числит исправленным: правку сделали для переполнения, для потери значимости —
нет. Результат подменяется нулём молча, ловить нечего.

**Направление:** не допускать промежуточного, теряющего значимость, либо
использовать заведомо верный путь `Decimal.toDouble()` (точная десятичная
строка → `double.parse`).

> **Вердикт (2026-08-26):** исправлено вместе с Р8 — у них общая причина, и
> чинить порознь было бы бессмысленно. `_ratioToDouble` переписан: частное
> берётся сразу в той точности, которую сохранит ответ (53 бита, пока
> результат нормальный, и меньше, когда субнормальный), округляется **один**
> раз с остатком в роли sticky-бита, и только потом умножается на степень
> двойки — по частям, чтобы ни одно промежуточное не вышло из диапазона.
> Проверено на 20 000 случайных пар с масштабами от −320 до +320, включая
> субнормальные и переполнение: **ноль неверно округлённых**. Заодно
> выяснилось, что и `1 / 1e307` старая реализация округляла неверно — этот
> случай в находке числился исправным.

### Р5. Объявленное устаревание до пользователя не доходит

**High.** `decimal.dart:1200-1212` и `:1214-1223`; `CHANGELOG.md:52-54`.
**Внесено в этой сессии.**

`@Deprecated` поставлен на **расширениях** `DecimalBigIntExtension` /
`DecimalIntExtension`, а не на их методах. Дart помечает неявный вызов
`42.toDecimal()` только если аннотация на самом члене.

Подтверждение из этого же репозитория: анализатор на Dart 3.6 выдаёт три
предупреждения об устаревшем `optimize()` (аннотация на члене — работает) и
**ни одного** на `5.toDecimal()` в `test/decimal/convert_test.dart:242`.

**Последствия:** `CHANGELOG` объявляет устаревание, которого никто не увидит; в
2.0 члены исчезнут у людей, ни разу не получивших предупреждения.

**Направление:** перенести `@Deprecated` на сами методы `toDecimal()`.

> **Вердикт (2026-08-26):** исправлено. Аннотация перенесена с расширений на
> оба метода `toDecimal()`. Проверено из **другого** пакета: `dart analyze` в
> `example/` теперь даёт `deprecated_member_use` и на `42.toDecimal()`, и на
> `BigInt.from(42).toDecimal()`, а на `42.toShortDecimal()` — молчит, как и
> должно. Внутрипакетные использования в тестах закрыты точечными `ignore`:
> член устарел, но до удаления обязан работать и обязан быть проверен.

### Р6. Раздел README про оптимизацию опровергается собственным кодом

**High.** `README.md:793-878`.

Числа в разделе измерены до того, как волна 3 добавила строковый кеш
(`decimal.dart:865`, `toString() => _text ??= _print()`). Проверено прогоном
(1 млн итераций, JIT):

| | обещано README | фактически |
|:--|--:|--:|
| второй пример, без нормализации | 2.568 с | 0.272 с |
| второй пример, с нормализацией | 15.578 с | **0.020 с** |

README строит на этих числах довод: «we will lose performance… we will pay too
much for it» — и это **единственное обоснование** того, почему нормализация не
встроена в `toString`. Фактически нормализация теперь на порядок **быстрее**.

**Направление:** перемерить оба примера и переписать вывод — либо признать, что
довод устарел вместе с числами.

> **Вердикт (2026-08-26):** раздел переписан по свежим замерам, и довод
> оказался вернее, чем числа под ним.
>
> Перемерено на десяти миллионах итераций, AOT, на той же машине, что и
> таблицы README, со стоком, который оптимизатору не выбросить:
>
> | | как есть | после `normalized()` |
> |:--|--:|--:|
> | одно число печатается много раз | 0.02 с | 0.02 с |
> | каждое число печатается однажды | 1.36 с | 5.38 с |
> | то же на уже каноническом | 1.58 с | 1.61 с |
>
> Первый пример умер: строковый кеш сравнял обе стороны, и «оптимизация
> ускоряет печать в пятьдесят раз» больше не про что. Второй пример мерил не
> то, что обещал: он сохранял нормализованное значение в переменную, и со
> второго круга число было уже каноническим — отсюда и выигрыш в шестнадцать
> раз, который ревью справедливо назвало опровержением написанного. На честной
> постановке — каждое число новое и печатается один раз — нормализация
> **проигрывает вчетверо**, и вывод README («нормализацию не встроили в
> `toString`, потому что за неё платили бы все») остаётся верным. Ровно это
> теперь в разделе и написано, вместе с тем, для чего `normalized()` нужен на
> самом деле: каноническая форма, а не скорость печати.
>
> Попутно закрыт **Р26** — обещание «повторный вызов ничего не стоит» стало
> правдой.

### Р7. Претензия README к `fixed` не воспроизводится, а её примеры не компилируются

**High.** `README.md:41-83`.

- Примеры используют `Fixed.fromInt(1, scale: 0)` и `.copyWith(scale: 3)`. И в
  6.1.1, и в 6.2.0 параметр называется `decimalDigits`: `Error: No named
  parameter with the name 'scale'`. Ни один из шести снипетов не собирается
  против версий, которыми пакет сам себя мерит.
- Главный тезис — «the main drawback… `double` is used for the division
  operation under the hood», с `print(b / a); // 111111111111111120 (!)`. На
  6.2.0 и 6.1.1 ответ `111111111111111111`, точный; `fixed` делит через
  `BigInt`.

Публичный README критикует названный пакет утверждением, которое перестало быть
правдой, кодом, который не собирается. Остальные три претензии к чужим пакетам
воспроизводятся и верны.

> **Вердикт (2026-08-26):** проверено прогоном на 6.1.1 (её резолвит стенд) и
> на 6.2.0 (отдельным пакетом в стороне от дерева) — находка верна в обеих
> частях.
>
> Параметр переименован в `decimalDigits` ещё в 6.0.0; все шесть примеров
> исправлены и теперь собираются. Претензия про `double` снята: `fixed` делит
> в `BigInt` с округлением половины от нуля, и `Fixed.parse('111111111111111111')`
> в квадрате и обратно даёт точное `111111111111111111`. Вместо неё в README
> сказано прямо, что утверждение устарело и снято, — умолчать было бы дешевле,
> но публичная страница пакета уже год говорила о чужом пакете неправду.
>
> Первая претензия воспроизводится и осталась: деление берёт большее из двух
> чисел знаков и молча округляет к нему, так что `1/8` даёт 0, 0.1 или 0.13 в
> зависимости от того, как записаны стороны. Это и есть довод, ради которого
> раздел писался.

## Medium and low-severity findings

### Medium

**Р8. `divideToDouble` округляет дважды.** `decimal.dart:475-478`. Сверено с

завышения, одинаково у всех пакетов. `example/README.md` обещает «A wrong
answer is never reported as a fast one», но у `big_double` стоит
`ignoreMatchingErrors: true`, и его неверные ответы показываются временем.
Строка `parse` меряет разный объём работы: наш `parse` ленив по замыслу,
конкуренты нормализуют сразу.

**Р33. Мелкие расхождения dartdoc:** `operator %` обещает «always positive» (для
нуля не так, в обоих семействах); `toStringAsFixed` называет `fractionDigits`,
а код сравнивает со `scale`; `tryParse` не упоминает предел показателя 10^6;
`_splitTrailingZeros` объявляет предусловие слабее фактического;
`fixed_point.dart:19-21` перечисляет исключённые из интерфейса члены и не
называет `unscaledValue`.

## Architecture review

**Сильные стороны.** Дублирование двух семейств вместо обобщения — решение,
подтверждённое замером, и оно окупается: код каждого семейства читается без
оглядки на второе. Интерфейс `FixedPoint` ловит забытый член на компиляции —
при добавлении членов в этой сессии он сработал ровно так, как задуман. Мост
между семействами явный, и это правильно: неявное расширение прятало бы вопрос
о типе результата.

**Слабое место — `_align`.** Он остался единственным местом, где переполнение
не осознано (Р1, Р2), и именно через него проходят почти все операции
`ShortDecimal`, кроме сравнений и сложения-умножения. Рядом уже существуют
`_scaledOrNull`, `_compareScaled`, `_addExactly`, `_dropFractionExactly` —
инфраструктура «посчитать точно, если не влезает» построена, но к `_align` не
подключена. Это не архитектурный тупик, а незаконченная работа.

**Спорное решение — валидация конструкторов ассертами** (Р16). Для пакета,
который ставят во Flutter-приложения, расхождение debug и release означает, что
ошибка находится в разработке и молча портит числа в продакшене.

## Testing review

Сюита сильная по замыслу: property-тесты против независимой рациональной
модели, сверка с конкурентом, тест симметрии, воспроизводители всех пятнадцати
прежних дефектов. Модель действительно не использует код пакета — инвариант
проверен.

Но **100 % покрытия строк даёт ложное чувство защищённости**: ни одна из семи
High-находок не поймана, две ветки не исполняются вовсе (Р12, Р13), три
проверки тавтологичны (Р15), а эталонная модель врёт на отрицательных знаках
(Р14).

Наивысший приоритет по тестам, в порядке ценности:

1. Расширить сверку двух семейств: сейчас `ShortDecimal` сверяется с `Decimal`
   только по `+ - * compareTo ==`, округлениям и печати. Не сверяются
   `divideOrNull`, `divide`, `~/`, `%`, `remainder`, `toStringAsFixed`,
   `toDouble`, `toInt`, `precision`, `pow`, `clamp`. Это самый дешёвый оракул,
   какой есть у проекта, — две независимые реализации одной спеки, — и он
   используется на треть. Р1, Р2 и Р3 он бы поймал.
2. Починить `Ref._shift` и расширить генератор на отрицательные знаки — это
   закрывает Р13 и Р14 разом.
3. Печать после заполнения канонической формы (Р12).
4. Заменить тавтологии на сверку с моделью (Р15).

## Performance and reliability

Производительность разобрана в записях волн 3 и `2026-08-26[12]`; ревью
добавляет к ней две вещи.

`_dropFractionExactly` (`short_fraction.dart:296-327`) ужимает по одному
разряду за итерацию: `ShortFraction(1,3).round(50000)` считается около
полутора секунд. Корректность не страдает.

`round`/`_dropFraction` с большим отрицательным числом знаков строит
`10^|n|` без проверки аргумента: `Decimal.one.round(-1000000000)` либо съест
память, либо будет считать неограниченно долго. То же у `_align` при разборе
`1e-1000000`. Проверок нет ни в одном из мест.

Конкурентности в пакете нет — асинхронности, потоков и разделяемого состояния
не существует, кроме двух кешей степеней десяти, которые заполняются
идемпотентно. `ShortDecimal` получил `vm:deeply-immutable` и может разделяться
между изолятами; `Decimal` этого права не получит, пока хранит `BigInt`.

## Maintainability

Код читается, комментарии объясняют «почему», а не «что», решения записаны в
`docs/records/` вместе с ценами и замерами — по поддерживаемости это заметно
выше среднего для пакетов такого размера.

Технический долг сосредоточен в трёх местах: незаконченное осознание
переполнения в `_align`; документация, отставшая от кода (Р6, Р7, Р19, Р20,
Р21, Р22, Р33); отсутствие CI, из-за которого любое из этого может уехать в
релиз незамеченным.

Дублирование двух семейств — осознанное и оправданное, но оно требует
дисциплины: каждый из Р1, Р2, Р3, Р10, Р11, Р13 — это место, где одно семейство
ушло от другого. Тест симметрии сверяет только **имена** членов, не поведение;
сверку поведения делает property-тест, и он покрывает треть.

## Positive findings

Это стоит сохранить:

- **Прямое округление деления** (`decimal.dart:399-428`, эта сессия) — сверено
  с прежней реализацией на 473 284 случайных делениях, расхождений ноль.
- **Новые члены 1.2.0** — `unscaledValue × 10^exponent == value`,
  `normalized() == this`, согласованность `hashCode` проверены на 100 000
  значений; `movePointLeft`/`movePointRight` совпадают с операторами.
- **Единый тип исключения** при делении на ноль — работает во всех девятнадцати
  точках входа обоих семейств.
- **`toDouble()`** корректно округлён на всех 100 000 проверенных значениях, а
  2 389 расхождений с `decimal` — случаи, где прав наш пакет.
- **Печать и округления** совпадают с `decimal` побайтово на 120 000 значений,
  включая экспоненциальную запись и отрицательное число знаков.
- **`_pack` — настоящая каноническая форма**, `hashCode` согласован с `==` при
  любом способе построения.
- **Три точки входа согласованы и полны**, мост живёт только в зонтичной.
- **Стенд** меряет честно в главном: сток от оптимизатора настоящий, значения
  строятся вне измеряемой области, всем пакетам даются побайтово одинаковые
  входные строки, ожидаемые ответы посчитаны вне Dart.

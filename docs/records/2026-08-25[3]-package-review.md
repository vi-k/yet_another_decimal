# Полное ревью пакета

Ревью заказано владельцем перед переработкой. Рамка, определяющая приоритеты:
**пакет существует ради производительности выше, чем у конкурентов, при
сохранении качества; главный конкурент — `decimal`.**

Проводилось шестью независимыми потоками (два поиска ошибок по семействам,
производительность, архитектура и API, тесты, Codex вторым мнением). Все
находки ниже **воспроизведены запуском кода**, а не выведены из чтения.

Окружение: Dart 3.13.0, macOS arm64, пакет в состоянии коммита `c47768d`.

## Подтверждённые дефекты

### Д1. Деление на отрицательное число бросает исключение вместо результата

**Severity: Critical. Оба семейства.**

`lib/src/decimal/decimal.dart:142-175`, `lib/src/short_decimal/short_decimal.dart:201-232`

```dart
Decimal(1) / Decimal(-2);    // DecimalDivideException, ожидалось -0.5
Decimal(6) / Decimal(-3);    // DecimalDivideException, ожидалось -2
Decimal(-6) / Decimal(-4);   // DecimalDivideException, ожидалось 1.5
Decimal(5) / Decimal(-1);    // DecimalDivideException, ожидалось -5
ShortDecimal(6) / ShortDecimal(-3); // то же самое
```

Причина. После сокращения на НОД делитель сохраняет знак: `fastGcd` возвращает
модуль, поэтому `divisor` остаётся отрицательным. Дальше идут циклы снятия
множителей:

```dart
while (divisor % _bigInt5 == BigInt.zero) { ... }
while (divisor % BigInt.two == BigInt.zero) { ... }
if (divisor != BigInt.one) throw DecimalDivideException._(this, other);
```

Оператор `%` в Dart евклидов — при положительном правом операнде результат
всегда неотрицателен. `-2 % 5` равно `3`, а не `-2`. Циклы доводят делитель до
`-1`, и финальная проверка `divisor != BigInt.one` срабатывает на совершенно
представимом результате.

Масштаб. Дифференциальный прогон против точной рациональной арифметики на
`BigInt`: из 16 294 брошенных `DecimalDivideException` **2 981 (18 %) ложные** —
результат точно представим.

Направление исправления: нормализовать знак до циклов — если делитель
отрицателен, инвертировать и делитель, и делимое. Правка на три строки в
каждом семействе.

**Вердикт (волна 1, 2026-08-25): починено** (`98ebf57`). Знак делителя
выносится до разложения, а отрицается результат, не делимое: у `ShortDecimal`
отрицание `int.min` теряет знак. Тест — группа Д1 в `test/defects_test.dart`,
плюс property-тест и сверка с конкурентом.

### Д2. `_pow10` переполняется — ломаются сравнение, округление и `toInt`

**Severity: Critical. Только `ShortDecimal`.**

`lib/src/short_decimal/short_decimal.dart:529-532`

```dart
static int _pow10(int exponent) {
  assert(exponent >= 0, "exponent can't be negative");
  return math.pow(10, exponent) as int;
}
```

`math.pow(10, 19) as int` даёт `-8446744073709551616`, `math.pow(10, 64) as int`
даёт `0`. Ни исключения, ни признака. Один корень — три группы симптомов.

**Сравнение и сортировка** (через `_align`, `:534-547`, а он под `+`, `-`, `%`,
`remainder`, `~/`, `<`, `<=`, `>`, `>=`, `==`, `compareTo`):

```dart
final dust  = ShortDecimal.parse('0.000000000000000001'); // scale 18
final limit = ShortDecimal.parse('10');                   // scale -1
dust < limit;          // false (!)  разрыв масштабов 19
dust.compareTo(limit); // 1     (!)
```

Соседние масштабы ведут себя по-разному, значит нарушается транзитивность
`compareTo` и портится `List.sort()`:

```dart
[ShortDecimal(2), ShortDecimal(1, shiftRight: 20), ShortDecimal(1)]..sort();
// [2, 0.00000000000000000001, 1]  — не отсортировано
```

Сложение при том же разрыве даёт не абсурд, а правдоподобное число:
`0.000000000000000001 + 1000` печатается как `3.875820019684212737`.

**Округление** (через `_dropFraction`, `:549-561`):

```dart
ShortDecimal.parse('0.0000000000000000001').round();  // 1 (!), ожидалось 0
ShortDecimal.parse('0.0000000000000000001').toStringAsFixed(0); // '1'
ShortDecimal.parse('0.<63 нуля>1').round();  // IntegerDivisionByZeroException
```

Округление почти-нуля до единицы — тихая порча данных. При масштабе 64
делитель становится нулём, и приходит исключение о делении на ноль на
совершенно корректном числе.

**`toInt`** (`:405-409`). Причём на примере, который README прямо помечает как
рабочий:

```dart
final a = ShortDecimal(9223372036854775807) >> 40; // README: "// ok"
a.toInt();               // -1   (!) ожидалось 0
a > ShortDecimal.one;    // true (!) число меньше единицы
```

Важно, что это **не то ограничение, которое пакет декларирует**. README обещает:
переполнение возможно, если значащая часть не укладывается в int64. Здесь и
значащие части, и корректный результат укладываются прекрасно — переполняется
только промежуточная константа, без которой во многих случаях можно обойтись
(при разрыве масштабов ≥ 19 знак сравнения и результат усечения определяются
без всякого домножения).

**На web поведение ещё раз иное.** В dart2js `int` — это double, и `Infinity`
проходит каст `as int`: `_pow10(400)` даёт `Infinity`, а `round()` того же
числа возвращает `0`, тогда как на VM — `1`. Один вход, три разных ответа в
зависимости от платформы.

**Вердикт (волна 1, 2026-08-25): починено** (`0579741`). Таблица степеней
вместо `math.pow`; сравнения переведены на `_compare`, который домножает только
когда результат помещается; округление знает про непомещающийся делитель.
Уточнение к находке: порог не в разрыве масштабов, а в переполнении
произведения — разрыв в пять тоже переполняет при большой базе.

### Д3. Деление на ноль зависает намертво с ростом памяти

**Severity: Critical. Оба семейства.**

`lib/src/decimal/decimal.dart:141-175`, `lib/src/short_decimal/short_decimal.dart:201-232`

```dart
Decimal(1) / Decimal(0);  // не возвращается никогда
```

Подтверждено запуском: процесс печатает `start` и не завершается; убит по
таймауту через 12 секунд (код выхода 137). Память при этом растёт — на 25-й
секунде наблюдался RSS 181 МБ и продолжал расти.

Причина. При `other.base == 0` НОД равен `|base|`, после сокращения делитель
становится нулём. Дальше:

```dart
while (divisor % _bigInt5 == BigInt.zero) {
  k *= BigInt.two;
  scale++;
  divisor = divisor ~/ _bigInt5;
}
```

Ноль делится на пять нацело сколько угодно раз: условие `0 % 5 == 0` истинно
всегда, а `0 ~/ 5` снова ноль. Цикл вечен, и на каждой итерации `k` удваивается
как `BigInt` — отсюда рост памяти до OOM. `scale++` попутно уходит в
переполнение.

Особенно скверно, что **все остальные пути деления на ноль ведут себя
корректно** и бросают сразу:

```dart
Decimal(1) ~/ Decimal(0);                    // IntegerDivisionByZeroException
Decimal(1) % Decimal(0);                     // IntegerDivisionByZeroException
Decimal(1).remainder(Decimal(0));            // IntegerDivisionByZeroException
Decimal(1).divideToFraction(Decimal(0));     // UnsupportedError: division by zero
Decimal(1).divideWithRemainder(Decimal(0));  // UnsupportedError: division by zero
Decimal(0) / Decimal(0);                     // IntegerDivisionByZeroException
```

То есть `operator /` — единственная дыра, и ведёт она не к исключению, а к
зависанию: во Flutter это замерший интерфейс, который не ловится `try/catch` и
не виден в стеке.

**Вердикт (волна 1, 2026-08-25): починено** (`98ebf57`). Проверка в начале
деления, `UnsupportedError` — как у `Fraction` и `Division`.

### Д4. `Decimal.toBigInt()` теряет порядок величины при отрицательном масштабе

**Severity: Critical. Только `Decimal`.**

`lib/src/decimal/decimal.dart:337-338`, причина в `_dropFraction` (`:520-532`)

```dart
final a = Decimal(1) << 3;                              // 1000
a.toBigInt();                                           // 1  (!)

final b = Decimal.parse('1') / Decimal.parse('0.001');  // 1000
b.toBigInt();                                           // 1  (!)
```

`toBigInt()` определён как `truncate().base`. При `scale <= fractionDigits`
метод `_dropFraction` возвращает `this` **как есть**, не трогая масштаб. Дальше
берётся сырое поле `base` — а при отрицательном масштабе это мантисса без
хвостовых нулей, а не значение числа. Сам `truncate()` при этом корректен:
`a.truncate()` печатает `1000`. Ломается ровно извлечение `.base`.

Число молча уменьшается в 10^n раз. Для денежной библиотеки это худший
возможный класс дефекта: ни исключения, ни признака ошибки.

Отрицательный масштаб возникает не только от `<<`, но и штатно от `operator /`
на делитель с большим масштабом — то есть от обычной арифметики.

**Зеркальный метод исправен.** `ShortDecimal.toInt()` (`short_decimal.dart:405-409`)
ту же ситуацию обрабатывает верно: `ShortDecimal.parse('1000')` имеет
`base: 1, scale: -3` и даёт `toInt() == 1000`. Это прямое доказательство того,
что зеркальность семейств уже нарушена и держится ни на чём.

**Вердикт (волна 1, 2026-08-25): починено** (`98ebf57`). Домножение на
`10^-scale`, как у `ShortDecimal.toInt`.

### Д5. `toStringAsFixed` не добивает нулями числа по модулю меньше единицы

**Severity: High. Оба семейства.**

`lib/src/decimal/decimal.dart:465-467`, `lib/src/short_decimal/short_decimal.dart:514-516`

```dart
Decimal.parse('0.5').toStringAsFixed(3);   // '0.5',   ожидалось '0.500'
Decimal.parse('-0.5').toStringAsFixed(3);  // '-0.5',  ожидалось '-0.500'
Decimal.parse('0.05').toStringAsFixed(5);  // '0.05',  ожидалось '0.05000'
```

Причина. Ветка для случая, когда целая часть пуста:

```dart
if (scale >= number.length) {
  return '${sign}0.${number.padLeft(scale, '0')}';
}
```

добивает нулями **влево до `scale`**, а вправо до `fractionDigits` не добивает
вовсе. Вторая ветка (`padRight(fractionDigits, '0')`) отрабатывает правильно —
поэтому дефект виден только на числах меньше единицы.

Семейства при этом расходятся между собой на нуле:
`Decimal.parse('0.0').toStringAsFixed(2)` даёт `'0.0'`, а
`ShortDecimal.parse('0.0').toStringAsFixed(2)` — `'0.00'`.

Это функция форматирования денег: ценник печатается как `0.5`, а не `0.50`.

**Вердикт (волна 2, 2026-08-26): починено** (`f6fde16`). Добавлен
`padRight(fractionDigits)` в ветку «целая часть пуста», оба семейства.

### Д6. `divideWithRemainder` падает под ассертами при отрицательном масштабе

**Severity: High. Оба семейства.**

`lib/src/decimal/division.dart:20` → `decimal.dart:63`,
`lib/src/short_decimal/short_division.dart:20` → `short_decimal.dart:64`

`Division` конструирует остаток через `Decimal.fromBigInt(..., shiftRight: scale)`,
не проверяя знак `scale`, а конструктор содержит `assert(shiftRight >= 0)`.

```dart
// dart run --enable-asserts
Division(Decimal(1) << 2, Decimal(3) << 1);
// _AssertionError: 'shiftRight >= 0': shiftRight must be positive

ShortDecimal.parse('400').divideWithRemainder(ShortDecimal.parse('30'));
// _AssertionError: Use `shiftLeft` instead of the negative `shiftRight`
```

Худший класс отказа: **в debug падает, в release молча работает.** Под Flutter
это значит краш у разработчика и тишину в продакшне.

Для `ShortDecimal` вероятность максимальна: `_pack` делает масштаб
отрицательным у любого круглого числа, поэтому `ShortDecimal.parse('400')`
уже несёт `scale = -2`. Достаточно обычного `parse` — никакой экзотики со
сдвигами не требуется.

Косвенное подтверждение, что автор на это наступал: в
`ShortDecimalDivideException.toString()` (`short_decimal.dart:593`) строка с
`quotientWithRemainder` закомментирована, тогда как в `DecimalDivideException`
она есть. То есть печать исключения могла уронить программу — исключение при
печати исключения.

**Вердикт (волна 2, 2026-08-26): починено** (`f6fde16`). Остаток собирается
внутренним конструктором; закомментированная строка в печати исключения
возвращена.

### Д7. `ShortDecimal.ten` не нормализована — рушится `Set` и `Map`

**Severity: High. Только `ShortDecimal`.**

`lib/src/short_decimal/short_decimal.dart:27`

```dart
static const ShortDecimal ten = ShortDecimal._asIs(10, 0);
```

Весь класс держится на инварианте «представление всегда упаковано»: `hashCode`
считается прямо по `(base, scale)` без нормализации именно потому, что
упакованная форма канонична. Константа `ten` собрана через `_asIs` в обход
`_pack`, а каноническая десятка — это `(base: 1, scale: -1)`.

```dart
ShortDecimal.ten == ShortDecimal(10);                    // true
ShortDecimal.ten.hashCode == ShortDecimal(10).hashCode;  // false (!)
{ShortDecimal.ten, ShortDecimal(10)}.length;             // 2 (!)
<ShortDecimal, int>{ShortDecimal(10): 1}[ShortDecimal.ten];  // null (!)
```

Контракт `hashCode`, записанный в собственном dartdoc класса («returns the same
hashCode for decimal with the same value»), нарушен публичной константой.

Заражение расходится дальше по операциям, которые не проходят через `_pack`:
`ShortDecimal.ten << 1` даёт `(10, -1)` против канонического `(1, -2)`,
`-ShortDecimal.ten` даёт `(-10, 0)` против `(-1, -1)`. Чинят представление
только `*`, `>>` и `+`/`-`.

У `Decimal` того же нет: `Decimal.ten` и `Decimal(10)` дают равные хеши и
множество из одного элемента, потому что `hashCode` там считается по
`_requirePacked`, а не по сырым полям.

**Вердикт (волна 2, 2026-08-26): починено** (`f6fde16`). `ten` — каноническая
пара `(1, -1)`.

### Д8. `divideToDouble` возвращает `NaN` или `0.0` на числах высокой точности

**Severity: Medium. Оба семейства.**

`lib/src/decimal/decimal.dart:187-192`

```dart
// два случайных числа вида 0.<n цифр>
n = 300  ->  0.8959943397331056     // верно
n = 310  ->  0.0                    // (!)
n = 320  ->  NaN                    // (!)
```

`Fraction.numerator / Fraction.denominator` — это `BigInt.operator /`, который
в SDK реализован как `toDouble() / other.toDouble()`. Когда после сокращения оба
`BigInt` превышают `double.maxFinite` (~1.8·10^308), получается `Infinity /
Infinity`, то есть `NaN`, либо `конечное / Infinity`, то есть `0.0` — хотя само
отношение прекрасно представимо в `double`.

`_align` приводит операнды к общему масштабу, поэтому у чисел с высокой
точностью числитель и знаменатель разрастаются одновременно. Именно ради таких
чисел и берут версию на `BigInt`.

`divideToDouble` предлагается в README как безопасная альтернатива `/`,
не бросающая исключений. Сейчас она безопасна в том смысле, что не бросает, —
и возвращает `NaN`, который тихо расползается по вычислениям.

**Вердикт (волна 2, 2026-08-26): починено** (`13bd65b`). 64 значащих бита
отношения сдвигом, показатель возвращается умножением. Замечание находки «у
конкурента та же болезнь» остаётся верным: это стало нашим отличием, а не
выравниванием.

### Д9. `Fraction` не принимает отрицательный `fractionDigits`, а `Decimal` принимает

**Severity: Medium. Оба семейства.**

`lib/src/decimal/fraction.dart:66-107`, проявляется через
`DecimalDivideException.floor/round/ceil/truncate` (`decimal.dart:548-555`)

```dart
Decimal.parse('123.4').floor(-1);                       // 120 — работает
Fraction(BigInt.from(1234), BigInt.from(10)).floor(-1);  // ArgumentError
```

У `Decimal` отрицательный `fractionDigits` — поддерживаемый сценарий:
округление до десятков, сотен и так далее (`_dropFraction` с ним работает
корректно). У `Fraction` тот же аргумент уходит в `BigInt.pow(-1)` и даёт
`ArgumentError: Exponent must not be negative`.

Больно это потому, что README предлагает `DecimalDivideException.round(n)` как
штатную замену не сработавшему делению. Пользователь, привыкший к
`Decimal.round(-1)`, получает исключение именно в аварийной ветке — там, где
код и так уже обрабатывает нештатную ситуацию.

**Вердикт (волна 2, 2026-08-26): починено** (`b7057ce`). При отрицательном
`fractionDigits` домножается знаменатель. **Ожидание Д15 при этом пришлось
переписать**: оно требовало от `ShortFraction` `ArgumentError` на том же
аргументе, то есть описывало сегодняшнее случайное поведение, а не желаемое.

### Д10. `tryParse` двух семейств расходится и оба принимают шестнадцатеричное

**Severity: Medium. Оба семейства.**

`lib/src/decimal/decimal.dart:78-100`, `lib/src/short_decimal/short_decimal.dart:96-156`

```dart
Decimal.tryParse('-');       // null
ShortDecimal.tryParse('-');  // 0        (!)

Decimal.tryParse('0x10');       // 16    (!)
ShortDecimal.tryParse('0x10');  // 10    (!!)
```

Шестнадцатеричное просачивается из `BigInt.parse`/`int.parse`, которые его
принимают. У `ShortDecimal` поверх этого срабатывает снятие хвостовых нулей, и
`0x10` превращается в `base: 1, scale: -1`, то есть печатается как `10`. Строка
`"0x10"` из внешнего JSON даст в двух семействах два разных неверных числа.

Пустая строка, пробел, `.` и `1e5` отвергают оба одинаково.

**Вердикт (волна 2, 2026-08-26): починено** (`645687c`). Делегирование в
`BigInt.parse`/`int.parse` заменено явным сканером по грамматике. Заодно закрыт
пункт бэклога `parse('1e21')`: экспоненциальная запись поддержана.

### Д11. `ShortFraction` переполняется при округлении к 19+ знакам

**Severity: Medium. Только `ShortDecimal`.**

`lib/src/short_decimal/short_fraction.dart:67-106`

Числитель домножается на `_pow10(fractionDigits)` до деления, поэтому при
`fractionDigits >= 19` работает уже переполненная константа — хотя точный
результат в `int` укладывается:

```dart
ShortFraction(4, 7).round(18);  // 0.571428571428571429    верно
ShortFraction(4, 7).round(19);  // 0.0443787407511556681   (!)
ShortFraction(4, 7).round(20);  // -0.00832624231658590793 (!) отрицательное
```

Через публичный API это выглядит так: пользователь поймал
`ShortDecimalDivideException` от `1 / 3` и попросил 19 знаков — получил
отрицательное число.

**Вердикт (волна 2, 2026-08-26): починено** (`b7057ce`). Три ступени: `int`,
`BigInt`, ближайшее представимое. Последняя — осознанное отличие от молчаливого
переполнения остального семейства: молчаливое здесь меняло знак.

### Д12. `ShortDecimal.tryParse` принимает `+0` не так, как `+1`, и глотает табуляцию

**Severity: Medium. Только `ShortDecimal`.**

`lib/src/short_decimal/short_decimal.dart:96-156`

```dart
ShortDecimal.tryParse('+1');   // 1     — плюс поддерживается
ShortDecimal.tryParse('+0');   // null  (!) Decimal даёт 0
ShortDecimal.tryParse('+0.0'); // null  (!) Decimal даёт 0
```

После снятия хвостовых нулей от `'+0'` остаётся `'+'`, а проверка «остался
только знак» написана только для минуса. Формат с обязательным знаком
(`+0.00` в биржевых дельтах) ломается ровно на нуле.

Отдельно — ручная защита от пробельных символов проверяет только ASCII-пробел:

```dart
ShortDecimal.tryParse('1\t0');    // 10    (Decimal: null)
ShortDecimal.tryParse('1.5\t0');  // 0.15  (Decimal: null)
```

Второй случай хуже первого: разбор не просто пропускает мусор, а конструирует
совершенно другое число — проглатывает и табуляцию, и цифру за ней.

**Вердикт (волна 2, 2026-08-26): починено** (`645687c`), тем же сканером, что и
Д10.

### Д13. `ShortDecimal *` переполняется до нормализации, хотя канонический результат помещается

**Severity: Medium. Только `ShortDecimal`.**

`lib/src/short_decimal/short_decimal.dart:196-198`

```dart
ShortDecimal(4611686018427387904) * ShortDecimal(5);
// 4611686018427387904  (!) — вернулся первый множитель
// точный результат 23058430092136939520 канонически представим:
// base = 2305843009213693952, scale = -1
```

`operator *` сначала вычисляет `base * other.base`, и только потом зовёт
`_pack`. Произведение переполняется до нормализации, после чего восстановить
значение уже нечем.

Это ровно тот случай, который **не покрывается декларированным ограничением
типа**: README обещает переполнение, когда значащая часть не влезает в int64, а
здесь она влезает — `2305843009213693952` меньше `int.max`. Переполняется
только промежуточное произведение.

Лечится перекрёстным сокращением множителей 2 и 5 до умножения с переносом
образовавшихся десяток в `scale`. Безопасный путь при этом можно оставить
коротким: проверка нужна только когда произведение близко к границе.

**Вердикт (волна 2, 2026-08-26): починено** (`b7057ce`). Двойка против пятёрки
сокращается до умножения. Проверка переполнения стоила сначала 70 %, после
переноса фильтра в оператор — 8 %.

### Д14. `ShortFraction` перемножает до сокращения — результат бывает абсурдным

**Severity: Medium. Только `ShortDecimal`.**

`lib/src/short_decimal/short_fraction.dart:47-105`

```dart
const max = 9223372036854775807;
ShortFraction(max, 2) * ShortFraction(2, max - 2);
// 1/3  (!)  точный результат: 9223372036854775807/9223372036854775805

ShortFraction(max, max - 2).round(1);  // 0, ожидалось 1
```

`operator *` перемножает числители и знаменатели, и только потом сокращает.
Перекрёстные двойки можно было сократить до умножения — тогда переполнения бы
не было вовсе. `1/3` вместо числа, практически равного единице, — не «немного
неточно», а полностью выдуманный ответ.

Та же болезнь у `+`/`-` (там нужен НОД знаменателей) и у округления, которое
считает `numerator * 10^digits` без проверки диапазона — это Д11.

**Вердикт (волна 2, 2026-08-26): починено** (`b7057ce`). Перекрёстное
сокращение в `*` и `/`, общий знаменатель через НОД в `+` и `-`. Находка «та же
болезнь у `+`/`-`» подтвердилась сверкой: там переполнялась ещё и сумма
числителей, для неё сделан точный путь через `BigInt`.

### Д15. `ShortFraction`: отрицательный знаменатель и `_TypeError` вместо `ArgumentError`

**Severity: Low. Только `ShortDecimal`.**

`lib/src/short_decimal/short_fraction.dart:11-24`, `:67, 79, 91, 102`

Нормализация знака сделана как `divisor = -divisor`, что для `int.min` знак не
меняет. В release создаётся объект с отрицательным знаменателем, печатающийся
как `-1/-9223372036854775808`, в debug падает собственный
`assert(denominator > 0)`. `Fraction` на `BigInt` в той же ситуации корректен.

Отдельно: `ShortFraction.floor/round/ceil/truncate` не проверяют отрицательный
`fractionDigits`, и `math.pow(10, -1) as int` даёт `_TypeError` вместо внятного
`ArgumentError`, который в этой же ситуации выдаёт `Fraction`.

**Вердикт (волна 2, 2026-08-26): починено с правкой ожидания** (`b7057ce`).
Знак нормализуется после сокращения НОД. Требование «знаменатель всегда
положителен» для `1/int.min` невыполнимо — точное значение требует знаменателя
`2^63`, — поэтому неприводимая дробь бросает `ArgumentError`, а тест проверяет
соседний случай `ShortFraction(2, int.min)`. Требование `ArgumentError` на
отрицательный `fractionDigits` отменено: оно противоречит Д9.

## Сверка каждого дефекта с конкурентами

Прогнано на `decimal` 3.2.6, `big_decimal` 0.5.0, `fixed` 6.2.0 теми же
входными данными. Столбец «эталон» — точный ответ.

### Где мы единственные, кто ошибается

| Случай | эталон | **мы** | decimal | big_decimal | fixed |
|:--|:--|:--|:--|:--|:--|
| `1 / -2` | `-0.5` | **исключение** | `-0.5` | исключение¹ | `-0.5000` |
| `6 / -3` | `-2` | **исключение** | `-2` | `-2` | `-2.0000` |
| `-6 / -4` | `1.5` | **исключение** | `1.5` | исключение¹ | `1.5000` |
| `1 / 0` | ошибка | **ЗАВИСАЕТ** | `ArgumentError` | `IntegerDivisionByZeroException` | `FixedException` |
| `1000` в целое² | `1000` | **`1`** | `1000` | `1000` | `1000` |
| `'0.5'` в 3 знака | `0.500` | **`0.5`** | `0.500` | `0.500` | `0.500` |
| `'-0.5'` в 3 знака | `-0.500` | **`-0.5`** | `-0.500` | `-0.500` | `-0.500` |
| `'0.05'` в 5 знаков | `0.05000` | **`0.05`** | `0.05000` | `0.05000` | `0.05000` |
| `parse('0x10')` | `null` | **`16`/`10`**³ | `null` | `null` | `null` |
| `parse('-')` | `null` | **`0`**⁴ | `null` | `null` | `null` |

¹ `big_decimal` требует явного режима округления; с `UNNECESSARY` он бросает
там, где результат точен — это его собственная шероховатость, но она отличается
от нашей: он честно сообщает «нужно округление», а не «результат непредставим».
² у нас `(Decimal(1) << 3).toBigInt()`, у остальных эквивалент.
³ `Decimal` даёт `16`, `ShortDecimal` — `10`. Два разных неверных ответа.
⁴ у `Decimal` верно (`null`), у `ShortDecimal` — `0`.

**Вывод по этой таблице.** Восемь случаев из десяти — это места, где все три
конкурента отвечают правильно, а мы нет. Ни один из них не зависает при делении
на ноль. Ни один не принимает шестнадцатеричное. Это не «мы строже» и не «у нас
другая модель» — это дефекты.

### Где мы не хуже других

| Случай | мы | decimal | Комментарий |
|:--|:--|:--|:--|
| `a / b` в `double`, 310+ знаков | `NaN` | `NaN` | у конкурента ровно та же болезнь: оба делегируют в `BigInt.operator /` |
| `parse('1.2.3')` | `null` | `null` | а вот `fixed` возвращает `1.20` — это его дефект |

`divideToDouble` чинить всё равно стоит: это станет отличием, а не
выравниванием. Но записывать это в «мы хуже конкурента» было бы неверно.

### Где конкурент умеет, а мы нет

| Случай | мы | decimal | big_decimal | fixed |
|:--|:--|:--|:--|:--|
| `parse('1e21')` | `null` | `1000000000000000000000` | `1e+21` | `null` |

Это пункт из бэклога владельца. Сверка показывает, что он не косметический:
главный конкурент экспоненциальную запись разбирает, и данные из чужого JSON
или из `double.toString()` приходят именно в таком виде.

### Где сверять не с кем

Переполнение `ShortDecimal` (Д2, Д14, Д15 и часть Д11) сравнивать не с чем:
ни у одного конкурента нет типа на `int` — все считают на `BigInt`. Эталоном
служит наш же `Decimal`, и он всюду отвечает так же, как `decimal`:

| Случай | **`ShortDecimal`** | `Decimal` (эталон) | `decimal` |
|:--|:--|:--|:--|
| `2^62 * 5` | **`4611686018427387904`** | `23058430092136939520` | `23058430092136939520` |
| `0.0000000000000000001.round()` | **`1`** | `0` | `0` |
| `0.000000000000000001 < 10` | **`false`** | `true` | `true` |
| `{ten, 10}.length` | **`2`** | `1` | `1` |

Отсутствие конкурента здесь не смягчающее обстоятельство, а наоборот: `int`-тип
и есть главное отличие пакета, и именно он сломан в четырёх местах.

### Что из этого следует для тестов

Сверка с конкурентами становится обязательной частью сюиты, а не разовым
упражнением. В `test/support/` заводится второй эталон рядом с рациональной
моделью: `decimal` как `dev_dependency` (он уже стоит в `example/`). Для всякой
операции, у которой есть аналог, тест сверяет три ответа — наш `Decimal`, наш
`ShortDecimal` и `decimal`, — и расхождение считается падением.

Это дало бы красный тест на восьми дефектах из пятнадцати ещё до того, как их
кто-нибудь начал искать.

Оговорка: конкурент не эталон истины. Там, где расходимся осознанно
(`operator /` бросает вместо возврата дроби; `'1e21'` до его поддержки;
округление `big_decimal` с явным режимом), расхождение фиксируется в тесте
явным списком с объяснением — так же, как список осознанных расхождений между
нашими двумя семействами.

## Что подтверждено как корректное

Проверено прогоном 20 000 случайных случаев против точной рациональной
модели на `BigInt`:

- `floor`/`round`/`ceil`/`truncate` у `Decimal` — расхождений нет, включая
  отрицательные значения и половинные случаи (округление half-away-from-zero);
- `Decimal` против `ShortDecimal` на значениях, влезающих в int64 и не
  выходящих за границу масштаба из Д2, — расхождений нет;
- `==` и `hashCode` согласованы на разных представлениях одного значения, в
  том числе при отрицательном масштабе.

`pana` даёт 160/160 — формальных претензий pub.dev нет.

## Производительность: где пакет теряет и что это стоит

Все цифры ниже — AOT (`dart compile exe`), Dart 3.13.0, macOS arm64, прогрев,
минимум из пяти сэмплов.

### П1. `gcd`: обход sdk#46180 нужен, но должен выбирать алгоритм по форме аргументов

`lib/src/helpers.dart:1-13`

**Правка этой записи от 2026-08-25.** Первая редакция ревью утверждала, что
обход устарел и `fastGcd` для `BigInt` надо заменить на штатный `BigInt.gcd`.
Это было неверно. Утверждение опиралось на микробенчмарк со случайными парами
**сопоставимой величины** — а в этом пакете `gcd` вызывается совсем на другой
форме данных: делимое большое, делитель маленький. Замер внутри реального кода
пакета показал обратное.

Суть: у двух алгоритмов разные сильные стороны.

- **Евклид через `%`** (нынешний `fastGcd`) мгновенно схлопывает пару разной
  величины: одно взятие остатка превращает 81-значное число в 9-значное.
- **Двоичный `BigInt.gcd`** (в SDK это `_binaryGcd`, алгоритм Стейна) идёт
  сдвигами и на такой паре проигрывает, зато выигрывает, когда операнды
  сопоставимы.

Issue [dart-lang/sdk#46180](https://github.com/dart-lang/sdk/issues/46180)
по-прежнему открыт, и обоснование в коде остаётся верным — но только для
половины случаев.

Замер внутри пакета (множитель — во сколько раз быстрее нынешнего кода;
меньше единицы значит медленнее):

| Сценарий | сейчас, нс | A: `int` + SDK | B: `int` + Евклид | C: `int` + выбор по величине |
|:--|--:|--:|--:|--:|
| деление 50 денежных значений | 51645 | 1.52× | 1.52× | **1.53×** |
| деление 20 больших (81 на 9 знаков) | 56900 | **0.37×** | 0.95× | 0.96× |
| `divide-small` из README (1/256 ×9) | 18857 | 0.78× | 1.17× | **1.18×** |
| `Fraction` из 30-значных, ×50 | 264968 | 2.48× | 1.02× | **2.49×** |
| `Fraction` из 60-значных, ×50 | 693426 | 2.51× | 1.00× | **2.55×** |

Корректность всех вариантов сверена на 5000 случайных делений внутри пакета —
результаты совпадают.

Вариант A — та самая ошибочная рекомендация: он рушит деление больших чисел
почти втрое. Вариант C нигде не хуже нынешнего и до 2.5 раза лучше:

```dart
BigInt fastGcd(BigInt other) {
  final a = bitLength, b = other.bitLength;
  if (a < 63 && b < 63) {
    return BigInt.from(toInt().fastGcd(other.toInt()));
  }
  // Двоичный gcd выигрывает только на сопоставимых величинах;
  // на разнокалиберной паре одно взятие остатка по Евклиду дешевле.
  if (a > 80 && b > 80 && (a - b).abs() * 4 < (a < b ? a : b)) {
    return gcd(other);
  }
  var g = this;
  var o = other;
  while (o != BigInt.zero) {
    final tmp = o;
    o = g % o;
    g = tmp;
  }
  return g.abs();
}
```

Пороги `80` и коэффициент `4` подобраны замером и обязаны быть перепроверены на
целевой платформе — это единственная часть правки, которая держится на цифрах,
а не на рассуждении.

`int fastGcd` (`helpers.dart:15-26`) остаётся без изменений — он быстрее
штатного `int.gcd` в 3.6 раза и служит быстрым путём.

**Урок для метода работы:** микробенчмарк на синтетических данных дал прямо
противоположный ответ по сравнению с замером на форме данных, которая реально
встречается в пакете. Любую оптимизацию `gcd`, `pow` и деления проверять только
внутри пакета.

**Вердикт (волна 3, 2026-08-26): принято наполовину.** Быстрый путь для пар,
помещающихся в машинные слова, взят — деление денежных значений вдвое быстрее,
`divide-small` быстрее на треть. Порог для штатного `BigInt.gcd` (операнды
длиннее 80 бит и в пределах четверти друг от друга) **проверен и отвергнут**:
на этой машине он даёт вдвое медленнее на дробях из 60-значных чисел
(293 мкс против 147). Урок из самой этой записи сработал второй раз — теперь
против её же рекомендации. Условие на длину заменено на `isValidInt`: он
дешевле `bitLength`, а `bitLength` в замерах волны 2 оказался дороже деления.
Подробности — в `2026-08-26[4]-wave-3-performance-report.md`.

### П2. Степени десяти пересчитываются на каждой операции

`lib/src/decimal/decimal.dart:504-518` (`_align`), `:528`,
`lib/src/decimal/fraction.dart:67,79,91,103`,
`lib/src/short_decimal/short_decimal.dart:529-532`

`_bigInt10.pow(n)` вызывается в `_align`, а `_align` стоит под `+`, `-`, `%`,
`remainder`, `~/`, всеми четырьмя сравнениями, `==`, `compareTo`, `Division` и
`divideToFraction`. Это самый горячий код пакета, и он каждый раз заново строит
степень десяти.

Видно по зависимости стоимости сложения от разницы масштабов: при равных
масштабах — 11.7 нс, при разнице 2 — 39 нс. Три четверти операции уходит в
`pow`.

Таблица степеней даёт `+` в 1.87 раза быстрее и `compareTo` в 2.2 раза.
Для `ShortDecimal` таблица из 19 констант заодно закрывает Д2 — там сейчас
`math.pow(10, n) as int`, который и медленнее в 8.3 раза, и молча переполняется.

**Вердикт (волна 3, 2026-08-26): принято** (`758bcb3`). У `ShortDecimal`
таблица появилась ещё в волне 1 вместе с Д2. Сложение ускорилось в 1.29 раза —
меньше обещанных 1.87, потому что в стенде на операцию приходится не только
выравнивание.

### П3. `toString()` ничего не кеширует, и здесь конкурент нас обгоняет

`lib/src/decimal/decimal.dart:389-430`

`toString()` читает `_packed`, но никогда его не пишет и не кеширует строку.
Каждый вызов заново делает `base.abs()`, `BigInt.toString()`, цикл снятия нулей
и несколько `substring`.

Десять вызовов `toString()` на одном объекте:

| Значение | сейчас | `decimal` | со строковым кешем |
|:--|--:|--:|--:|
| 30 знаков, 21 хвостовой ноль | 6909 | 638 | **9.1** |
| 6 знаков (деньги) | 744 | 594 | **9.5** |
| 100 знаков, 55 нулей | 22257 | 8743 | **8.9** |

У `decimal` 3.2.6 нормализованная форма лежит в `late final _rescaled`, поэтому
повторный вывод дешёвый. **Мы на этом пути медленнее конкурента в 1.25–2.5
раза**, и в README этого не видно: стенд меряет либо всегда новое значение
(`raw-view`), либо заранее прогретое (`prepared-view`), но не «одно значение,
много раз» — а во Flutter именно так и бывает, один и тот же `Decimal`
рендерится в `build()` десятки раз в секунду.

**Первый** вызов на свежем значении мы, наоборот, выигрываем в 2.2–5.5 раза, и
терять это нельзя: снятие хвостовых нулей строковыми средствами вообще не
трогает `BigInt`. Нужен именно строковый кеш рядом с `_packed`, а не замена
алгоритма.

**Вердикт (волна 3, 2026-08-26): принято** (`1c082dd`). Десять печатей одного
значения — 613 нс вместо 613×… то есть 11 нс; на 100 знаках с 55 нулями 35 мкс
превратились в 7 нс. Первая печать не изменилась. Цена — 5 % на умножении:
лишнее поле это лишний указатель в каждом объекте.

### П4. `toDouble()` идёт через форматирование и разбор строки

`lib/src/decimal/decimal.dart:340-341`, `lib/src/short_decimal/short_decimal.dart:411-412`

`double.parse(toString())` — самый дорогой путь из возможных. Для
`ShortDecimal`, где значение уже лежит в двух машинных словах, это особенно
странно.

| | сейчас | прямой путь | `decimal` |
|:--|--:|--:|--:|
| `Decimal`, деньги | 98.6 | **56.6** | 77.5 |
| `Decimal`, 40 знаков | 1100 | **60.7** | — |
| `ShortDecimal`, деньги | 90.8 | **3.5** | — |

То есть на типичных денежных величинах мы сейчас **медленнее `decimal`**, хотя
могли бы быть быстрее в 20 раз.

Быстрый путь: если `|base| ≤ 2^53` и `0 ≤ scale ≤ 22`, то `base / 10^scale` в
`double` корректно округлён (оба операнда точно представимы, округление одно).
Вне этих границ — падать в нынешний путь через строку. Это сохраняет наше
преимущество перед `decimal`, который делит всегда и потому теряет точность на
двойном округлении.

**Вердикт (волна 3, 2026-08-26): принято** (`d88b8b9`). Деньги: 73 → 40 нс у
`Decimal`, 57 → 5 нс у `ShortDecimal`. Обещанные 26× у второго не вышли, вышло
11×. Побитовое совпадение с путём через строку закреплено тестом на границах
`2^53` и `10^22`.

### П5. `operator /` не имеет быстрого пути точного деления

`lib/src/decimal/decimal.dart:142-175`, `lib/src/short_decimal/short_decimal.dart:201-232`

Три вещи сразу: нет проверки «делится нацело» (самый частый случай), нет
раннего выхода при `divisor == 1`, и множители 2 и 5 снимаются по одному
разряду за итерацию — для делителя `10^6` это 24 операции `BigInt`.

| Сценарий | сейчас | с быстрым путём |
|:--|--:|--:|
| `divide-small` из README | 17596 | **1484** (11.9×) |
| 50 делений на 2/4/5/8/10/16/20/25/40/50 | 41290 | **16199** (2.55×) |
| `divide-large` из README | 2433 | **1584** (1.54×) |

Последняя строка важнее всех: `divide-large` — **единственное место в стенде,
где мы сейчас проигрываем** (`big_decimal` 1.639 мкс, `fixed` 1.829, мы 2.205).
Быстрый путь точного деления этот проигрыш снимает.

Оговорка к правке: быстрый путь даёт **другое представление** результата —
численно эквивалентное, но с другим `scale`. `==` это переживёт, а тесты,
сверяющие `base`/`scale` напрямую, — нет. См. раздел про тесты.

**Вердикт (волна 3, 2026-08-26): принято** (`49802ed`, `6c6bb3a`).
`divide-small` втрое, `divide-large` в 1.52 раза — и это снимает единственный
проигрыш в стенде: 1.48 мкс против 1.64 у `big_decimal`.

### П6. Снятие хвостовых нулей идёт по одному разряду

`lib/src/decimal/decimal.dart:489-502`, `lib/src/short_decimal/short_decimal.dart:78-89`

`while (base % _bigInt10 == BigInt.zero) { base ~/= _bigInt10; }` — две
операции `BigInt` на каждый снятый ноль. Для 100-значного числа с 55 нулями это
111 операций.

Трёхступенчатая замена (проверка `isOdd` за O(1), затем один `%`, затем
бинарный поиск с одним финальным делением) даёт от 5.3× до 17× в зависимости от
значения и 1.58× на связке «сложение, затем `hashCode`». Последнее заметно
всюду, где `Decimal` служит ключом `Map` или элементом `Set`.

Важно: без промежуточной ступени с одним `%` бинарный поиск **проигрывает**
нынешнему коду на чётных числах без хвостовых нулей.

**Вердикт (волна 3, 2026-08-26): принято наполовину** (`9ff1135`). У `Decimal`
— пятикратно на длинных числах и вчетверо на нечётной базе. У `ShortDecimal` та
же правка замерена и **отвергнута**: она замедляет все случаи, включая те, ради
которых делалась. Предупреждение находки про среднюю ступень подтвердилось: без
неё поиск проигрывает циклу.

## Методология бенчмарков: чему из README можно верить

**Что в стенде сделано правильно.** Общая форма упражнения для всех пакетов;
сверка результата в `setup()` (она реально ловит неверные ответы — у трёх
конкурентов из пяти в текущем прогоне стоит ERROR); AOT; `benchmark_harness`
с автоподбором итераций; разделение `raw-view` и `prepared-view` — осознанная
попытка не дать ленивому представлению выиграть даром.

Отдельно проверено и **снято** подозрение, что компилятор выбрасывает мёртвый
код: автономный прогон с обязательным использованием результата даёт те же
цифры, что и стенд.

**Чему верить нельзя:**

1. **Отложенная работа не оплачивается.** В `add`/`multiply`/`divide` результат
   ни разу не приводится к строке внутри измеряемого цикла. Та же цепочка
   `multiply-small` с одним `toString()` в конце стоит 1900 нс против 116.8 нс,
   которые показывает стенд. **Стенд меряет 6 % работы.** Строка `multiply` в
   README не значит почти ничего, строка `add` занижена в два-три раза.

2. **Но форы против главного конкурента это уже не даёт.** `decimal` 3.2.6
   перешёл ровно на нашу схему: то же представление, нормализация через
   `late final _rescaled`, `Rational` тоже ленивый. Претензия «сравнивается
   ленивое с энергичным» справедлива против `fixed`, `big_decimal` и
   `decimal_type`, но **не против `decimal`**. При честном учёте с
   `toString()` — 2954 нс у нас против 6334 у него; с полной нормализацией —
   5057 против 5307, то есть паритет.

3. **Данные подобраны под ленивую нормализацию.** В `add-big-int` каждое
   значение — `10^19` с девятнадцатью хвостовыми нулями. Пакет, который не
   нормализует, здесь не платит ничего. В реальных деньгах база оканчивается на
   что угодно. Нужен второй набор с «грязными» базами.

4. **Разброс не измеряется.** `benchmark_harness` даёт одно среднее по одному
   прогону. Различия в таблице сплошь 3–8 % (`add-big-int`: 1.635 / 1.693 /
   1.729 / 1.801) — это **внутри шума**, и стенд честно помечает их все
   звёздочкой, но текст README читается как «мы выигрываем».

5. **`ShortDecimal` исключён из сравнения.** Понятно почему, но в результате
   самая сильная карта пакета в итоговой таблице не играет.

6. **Стенд меряет только арифметику.** Не измеряются `parse`, сравнения,
   округления, `toDouble`, `toStringAsFixed`, `Fraction`/`Division`, аллокации.
   При этом `toStringAsFixed` — место нашего семикратного преимущества, а
   `toDouble` — место, где мы проигрываем. Обоих в таблице нет.

7. **Числа не привязаны к окружению.** Не фиксируются версии зависимостей
   (в `example/pubspec.yaml` стоят диапазоны `^`), коммит, флаги VM и машина.
   Прогоны идут в фиксированном порядке в одном процессе, без медианы по серии
   независимых запусков.

8. **README расходится со стендом в мелочи:** сказано про 100 циклов, а для
   деления в `example/lib/src/operations.dart` установлено 1000.

9. **Адаптер `decimal` материализует `Rational` обратно в `Decimal` после
   каждой операции** (`example/lib/src/tests/decimal_test.dart:49-68`). Это
   честно для контракта «после каждого шага нужен `Decimal`», но занижает
   `decimal` в сценарии цепочки рациональных вычислений с одной финальной
   конверсией. При переработке стенда стоит мерить оба режима.

**Таблица в README устарела.** Свежий прогон того же стенда с `decimal` 3.2.6:

| | README | сейчас |
|:--|:--|:--|
| `add` | 1.694 мы / 1.863 decimal — мы впереди | 1.635 / 1.729 / 1.693 — **все в шуме** |
| `divide-large` | 2.025 мы / 1.650 big_decimal | 2.205 мы / 1.639 big_decimal / 1.829 fixed — **проигрываем двоим** |
| `prepared-view` | 16.689 мы / 16.845 decimal | 16.957 мы / **16.515 decimal** |
| `divide-small` | 12.969 / 496 (38×) | 16.474 / 539 (32×) — держится |
| `raw-view-zeros` | 15.681 / 83.212 (5×) | 16.182 / 105.455 — держится |

## Где мы действительно сильнее `decimal`

Это важно не потерять при переработке.

- **`divide-small` — 32×.** Причина фундаментальна: `decimal.operator /`
  возвращает `Rational`, а его `toDecimal()` в цикле умножает дробь на десять
  до целочисленности, с полным сокращением на каждом шаге. Мы снимаем множители
  2 и 5 прямо из делителя. Догнать это без переписывания `decimal` нельзя.
- **`toStringAsFixed(2)` — 7.5×** (3876 нс против 28944 на 50 значениях).
  У `decimal` это четыре операции над `Decimal` ради выравнивания нулей. Для
  форматирования денег — самый частый вызов вообще, **и о нём в README не
  сказано ни слова**.
- **Первый `toString()` на свежем значении — 2.2–5.5×.**
- **`ShortDecimal`** там, где значения влезают в int64: сложение вчетверо
  быстрее нашего же `Decimal`, деление — в 88 раз.

## Что уже сделано хорошо и чего нельзя трогать

1. **Плоское представление `base × 10^-scale` вместо рационального.** Главное
   решение пакета, и оно верное: `decimal` пришёл к тому же, а всё, что у него
   осталось на `Rational`, проигрывает в десятки и сотни раз.
2. **`int fastGcd`** — в 3.6 раза быстрее штатного `int.gcd`. В отличие от
   BigInt-версии, эта себя оправдывает.
3. **Снятие хвостовых нулей в `toString()` строковыми средствами** — ни одного
   деления `BigInt`. Именно это даёт пятикратное преимущество в
   `raw-view-zeros`. Любая «оптимизация», заменяющая это на `_requirePacked`,
   ухудшит пакет.
4. **Ленивая нормализация с кешем и публичным `optimize()`.** Механизм верный,
   не хватает только участия `toString()` в кешировании.
5. **Немедленная упаковка в `ShortDecimal._pack`** — не непоследовательность, а
   необходимость: без неё `multiply-large-int` переполнил бы int64.
6. **`_dropFraction` мимо дробей** — округления одним делением на степень
   десяти, без сокращений и без рационального. `decimal` пришёл к этому позже.

## Архитектура и публичный API

### А1. Исключение как штатный результат деления — главная архитектурная ошибка

`1 / 3` — не ошибка программиста и не исключительная ситуация. Это половина
делений в обычном коде. Сейчас на неё бросается исключение, и оно сделано
первичным API, а тотальные `divideToFraction`/`divideWithRemainder` —
второстепенными.

Измерено на AOT (`dart compile exe`, Dart 3.13.0, macOS arm64, 200 000
итераций с прогревом; воспроизведено дважды независимо):

| Сценарий | yad `Decimal` | yad `ShortDecimal` | `decimal` 3.2.6 |
|:--|--:|--:|--:|
| `1 / 8` — представимо | 932 нс | **9.8 нс** | 2509 нс |
| `1 / 3` через `operator /` + `try/catch` | **1971 нс** | 966 нс | — |
| `1 / 3` через `divideToFraction().round(6)` | 565 нс | **16.5 нс** | — |
| `1 / 3` → 6 знаков, эквивалент у конкурента | — | — | 1437 нс |

Три вывода, каждый существенный для переработки.

**Заглавный API пакета — его самый медленный путь.** На непредставимом делении
`Decimal` через `try/catch` даёт 1971 нс против 1437 нс у `decimal`, то есть
пакет **проигрывает конкуренту ровно в том сценарии, ради которого написан**.
При этом быстрый путь уже существует: `divideToFraction` даёт 565 нс — в 2.5
раза быстрее `decimal` и в 3.5 раза быстрее собственного заглавного пути. Для
`ShortDecimal` разрыв ещё грубее: 16.5 нс против 966 нс, в 59 раз.

**Стоимость самого механизма.** Отдельный микробенчмарк: `throw` + `catch` —
803 нс, возврат `null` — 0.4 нс. Разница в 2000 раз. `try`/`catch` вокруг
успешного пути при этом бесплатен, платит только ветка отказа — но платит
столько, что одно исключение стоит дороже шестидесяти точных делений
`ShortDecimal`.

**Бенчмарки в README этого не показывают.** `example/lib/src/tests/*.dart`
гоняет только представимые деления. Таблицы README измеряют исключительно
happy path, поэтому главная маркетинговая таблица пакета не отражает поведение
на реальных данных.

Отдельно — цена для пользователя, не измеряемая в наносекундах. `Decimal c = a / b;`
это выражение, чей статический тип `Decimal`, но которое значения не
возвращает. Его нельзя поставить в `map()`, в `fold()`, в инициализатор поля,
в цепочку `a / b * c`. Каждое деление в бизнес-коде обязано быть обёрнуто в
`try`, иначе приложение падает на первом же `1/3`.

Как ту же задачу решает конкурент: `decimal.operator /` возвращает `Rational` —
тотальная функция, тип честно сообщает «результат может быть непредставим», а
`toDecimal(scaleOnInfinitePrecision: n)` делает решение пользователя явным.
Их вариант дороже на одну аллокацию, но он тотален и композируем.

**Вердикт (волна 4, 2026-08-26): принято в части 1.2.0** (`a25a397`). Добавлены
`divideOrNull`, `divide(..., scaleOnInfinitePrecision)` и `isDivisibleBy`;
`operator /` стал надстройкой над тотальной формой. Замер: 749 нс через
`try/catch` против 182 через `divideOrNull`. Убрать `throw` из оператора —
по-прежнему задача 2.0.

### А2. Дублирование семейств: контракт продублирован без нужды, реализация — обоснованно

Аргумент, записанный в `docs/architecture.md` («общий интерфейс заставил бы
`ShortDecimal` платить за полиморфизм»), проверен измерением и **оказался
неверным для контракта и верным для реализации**:

| Что именно разделяется | Цена в AOT |
|:--|:--|
| `implements Iface<T>`, вызов при конкретном статическом типе | 18.5 мс против 18.1 мс — **0 %** |
| вызов через интерфейсный тип, один реализатор | **0 %** (девиртуализация по CHA) |
| вызов через интерфейс, два реализатора чередуются | **+0.74 нс** на вызов |
| общая реализация: дженерик + witness-объект | 121 мс против 60 мс — **2×** |

Пользовательский код всегда пишет `ShortDecimal a = …; a + b` — статический тип
конкретный, класс `final`, вызов прямой и инлайнится независимо от того, какие
интерфейсы класс реализует. Доказательство от противного есть в самом пакете:
оба класса уже реализуют `Comparable<T>` и остаются быстрыми.

Дорого обходится только попытка написать алгоритм **один раз над абстракцией**:
поле типа `T` боксит `int`. Здесь автор прав, и дженерики в Dart действительно
не специализируются. Но это аргумент против общей реализации, а не против
общего контракта.

**Цена дублирования уже материализовалась: найдено 25 расхождений** на 1500
строк, написанных одним человеком за один заход. Два из них молча портят
значения (`Decimal.toBigInt()` при отрицательном масштабе — Д4;
`tryParse('0x10')` даёт 16 против 10 — Д10). То есть вероятность
рассинхронизации не гипотетическая, она реализовалась ещё до первой публикации.

Самые показательные расхождения:

| Что | `Decimal` | `ShortDecimal` |
|:--|:--|:--|
| `toBigInt()` / `toInt()` | теряет множитель при `scale < 0` | верно |
| `tryParse('0x10')` | 16 | 10 |
| `pow()` | точный `BigInt.pow` | молча переполняется |
| `DivideException.toString()` | печатает частное с остатком и дробь | строка закомментирована |
| `Fraction.toDecimal()` | есть | отсутствует |

| `toStringAsExponential/Precision` | бросают `UnimplementedError` | отсутствуют |
| тесты | 30 в группе | 22 в группе |

### А3. Моста между семействами нет вообще

Нет `ShortDecimal.toDecimal()`, нет `Decimal.toShortDecimal()`. Переход между
типами возможен только через строку. Это удивительно, потому что весь смысл
двух семейств — «быстрый тип для операций, большой для накопления».

Причина архитектурная: `decimal.dart` и `short_decimal.dart` не знают друг о
друге, а `Fraction`/`Division` живут внутри `part`-семейств. Починить внутри
существующей структуры нельзя — нужен третий файл-мост.

**Вердикт (волна 4, 2026-08-26): принято** (`5bde8ae`).
`ShortDecimal.toDecimal()` и `Decimal.toShortDecimalOrNull()`. Тонкость,
найденная тестом: смотреть надо на упакованную форму — `1e20` не помещается
сырой базой и помещается упакованной.

### А4. `base`/`scale` под `@visibleForTesting` — канонического представления у пользователя нет

Приём работает: внешний пакет получает предупреждения анализатора. Но защищает
он не от того.

- **README сам нарушает этот контракт**: восемь примеров вызывают
  `debugToString()`. Пользователь, скопировавший пример, получает предупреждение,
  а в проекте с `flutter analyze` в CI — красный билд.
- `@visibleForTesting` **разрешает** использование в `test/` любого пакета. От
  использования снаружи это не защищает — чужие тесты законно завяжутся на
  представление.
- **Нет способа сериализовать число.** Ни `toJson`/`fromJson`, ни
  `unscaledValue`/`exponent`, ни конструктора из пары. Единственный путь —
  `toString()`/`parse()`, то есть форматирование и разбор строки на каждый
  round-trip в БД. У `decimal` есть `toJson`/`fromJson`, `toRational`,
  `precision`, `scale`; у `fixed` — `minorUnits`, `decimalDigits`.
- **Невозможна локализованная печать.** У `decimal` есть отдельная библиотека
  `package:decimal/intl.dart` с `DecimalFormatter` поверх `NumberFormat`. Здесь
  такого нет, и пользователь не может написать её сам. Для пакета, который
  метит в денежные расчёты, это самый заметный практический пробел.

**Вердикт: не сделано, и это осознанно.** Канонического представления наружу
по-прежнему нет: `base`/`scale` остаются `@visibleForTesting`. Публичный доступ
к паре — это разрешение создавать неканоничные значения, то есть Д7 в правах
пользователя. Задача 2.0, если вообще.

### А5. Чего не хватает в публичном API

| Член | Зачем | Есть у `decimal` |
|:--|:--|:--:|
| тотальное деление (`divideOrNull`, `divide(…, scaleOnInfinitePrecision:)`) | не платить 803 нс за исключение | да, через `Rational` |
| `toJson` / `fromJson` | сериализация без строкового round-trip | да |
| `unscaledValue` / `exponent` | своя сериализация, БД, protobuf | да |
| локализованное форматирование | деньги — главный сценарий | да, `decimal/intl.dart` |
| `Decimal ↔ ShortDecimal` | весь смысл двух семейств | н/д |
| `Decimal.toInt()`, `ShortDecimal.toBigInt()` | сейчас у каждого своё | да |
| `Fraction`: `compareTo`, `abs`, `inverse`, `toDouble` | публичный тип без сравнения и модуля | `Rational` имеет всё |
| `precision`, `inverse`, `isPositive` | ожидаются от числового типа | да |
| `pow` с отрицательным показателем | `x^-2` | да |
| `toStringAsExponential`, `toStringAsPrecision` | ожидаются от любого числового типа | да, реализованы |

**Вердикт (волна 4, 2026-08-26): принято целиком** (`b614c6b`, `af39c7a`).
Добавлены `precision`, `isPositive`, `inverse`, `toJson`/`fromJson`,
`toInt`/`toBigInt` в обоих семействах, `pow` с отрицательным показателем,

### А6. Метаданные и документация

`pana` даёт 160/160, WASM-ready, 6/6 платформ, 58.5 % публичного API с dartdoc.
Формально всё в порядке, но:

- нет `repository:` и `issue_tracker:` в `pubspec.yaml` — только `homepage:`;
- один topic (`decimal`) при лимите пять; не заявлены `math`, `fixed-point`,
  `bigint`, `money` — прямой минус к обнаруживаемости у пакета, который
  конкурирует за трафик с `decimal`;
- `example/README.md` — заглушка от `dart create`. Вкладка Example на pub.dev
  вторая по посещаемости после Readme, и реального примера использования в
  пакете нет вообще: `example/` — это стенд бенчмарков;
- нет library-level dartdoc в `lib/yet_another_decimal.dart` — страница
  библиотеки на pub.dev пустая;
- **`DecimalDivideException` и `ShortDecimalDivideException` не документированы
  ни одной строкой** — при том, что это классы, с которыми пользователь обязан
  взаимодействовать при каждом `1/3`. Не документированы также сами классы
  `Decimal`/`ShortDecimal`, `Fraction`/`ShortFraction`, `Division`/`ShortDivision`
  и все extension-методы;
- расширения `int.toDecimal()` и `BigInt.toDecimal()` **точно совпадают по
  имени** с расширениями из `decimal` 3.2.6. При импорте обоих пакетов
  `1.toDecimal()` становится неоднозначным — ошибка компиляции ровно во время
  миграции, то есть у целевой аудитории.

Замечание к нашей же документации: `docs/handoff.md` утверждал, что «публичный
API `ShortDecimal` почти без dartdoc». Это неверно — методы `ShortDecimal`
документированы не хуже `Decimal`. Реальный пробел в другом месте: исключения,
`Fraction`, `Division`, сами классы.

**Вердикт: волна 5.** Метаданные `pubspec.yaml`, dartdoc для типов, у которых
его нет вовсе, `example/README.md` и README по свежим цифрам — всё это
последняя волна переработки.

### Структурная причина дыр

В группе `ShortDecimal` **отсутствуют целиком** подгруппы `compare` и
`toStringAsFixed`, которые есть у `Decimal` (`test:1683`, `test:1947`). Их не
скопировали при дублировании семейства — отсюда непокрытыми оказались
`compareTo`, `hashCode`, `<=`, `>=`, `floor`, `round`, `ceil`, `remainder`,
бинарный `-` и весь `toStringAsFixed` (`short_decimal.dart:486-521`, 0 %).

Требование зеркальности семейств из `docs/conventions.md` сейчас не защищено
ничем, кроме дисциплины.

### Дефекты методики

**Тест, который пройдёт при исчезновении дефекта.** Группы вида
`+n / -n` (`test:1272`) написаны так:

```dart
try {
  v1 / v2;
} on DecimalDivideException catch (e) {
  expect(...);  // все проверки здесь
}
```

В `try` нет `fail()`. Если деление перестанет бросать, тест молча пройдёт с
нулём выполненных проверок. Именно поэтому Д1 не был замечен: тесты на
отрицательный делитель есть, но берут заведомо непредставимое `1512.9 / -86100`.

**Тесты фиксируют реализацию, а не поведение.** `base:` и `scale:`
передаются в хелперы 245 раз каждый. В `parse` и `toString` это оправдано —
там форма хранения и есть предмет проверки. В арифметике — нет:

```dart
expectDecimal(Decimal(1) / Decimal(100), '0.01',
    base: BigInt.from(100), scale: 4);
```

`base: 100, scale: 4` — артефакт алгоритма деления. Математически корректный
результат `base: 1, scale: 2` завалит тест. То есть **любая оптимизация
`operator /` обязана ломать тесты** — а пакет живёт ради оптимизаций.

**Табличные циклы прячут падения.** Доминирует паттерн «один `test` с циклом
по таблице из 37 случаев». Упал третий — остальные 34 не выполнялись, а
сообщение не говорит, какой именно случай упал. `reason:` не используется во
всём файле ни разу.

**Property-based тестов нет ни одного** (`Random` — ноль вхождений). При этом
эталон доступен и дёшев: рациональная арифметика на `BigInt` в 30 строк.
Фаззер на 20 000 случаях за секунду нашёл Д1 и Д3 — оба пропущены сюитой из
938 проверок.

**Один файл на 4336 строк.** Нельзя прогнать тесты одного метода; пропажу
целой группы не видно в дереве каталогов (см. выше).

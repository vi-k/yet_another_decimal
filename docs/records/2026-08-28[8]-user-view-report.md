# Обзор глазами пользователя: Д16–Д19

## Как смотрели

требованием подтверждать находку запущенным кодом, а не рассуждением:

| Проход | Что делал |

Три прохода оборвались на недельном лимите модели, но пробы успели написать —
их прогон доделан вручную. Ни один из проходов не менял репозиторий: каждый

## Что нашлось хорошего

- **Из 68 примеров README и dartdoc не разошёлся ни один.** Единственное
  отмеченное расхождение оказалось артефактом сравнения.
- `toDouble` на двадцатизначных значениях промахивается мимо ближайшего
  `double` у `decimal` трижды из десяти, у нас — ни разу.
- `divideOrNull` в десять раз дешевле ловли исключения и в девятнадцать —
  пути через `decimal` с проверкой.
- На двухстах тысячах операций `Decimal` вдвое быстрее `decimal`,
  `ShortDecimal` — вдесятеро.
- Мост между семействами безопасен по направлению, JSON не проходит через
  `double`, смешать с `int` и `double` нельзя — компилятор ловит.

## Дефекты

Все четыре — **расхождение кода с собственным dartdoc**, а не с чьим-то
ожиданием. Воспроизводители лежат в `test/defects_test.dart`.

### Д16. `divideToFraction` усекал вместо броска

Dartdoc обещает `ArgumentError`, когда дробь не помещается в int64.
Реализация прогоняла пару через `BigInt.toInt()`, который усекает молча:
`(2^63−1)·10 / 1` отвечало `9223372036854775807` вместо
`92233720368547758070`.

**Оказалось глубже, чем выглядело.** Та же пара уходила в `divide` с числом
знаков: деление считало по усечённой паре и молча возвращало неверный ответ.
Поэтому пара теперь живёт в `BigInt`, а решение принимает вызывающий —
`divideToFraction` бросает, `divide` считает точным путём. Ветка, строившая
дробь из усечённой пары, оказалась мёртвой и убрана: покрытие держалось
именно на усечении.

### Д17. `floor` и `ceil` теряли направление

Dartdoc: «Rounds the fraction towards negative infinity». Факт: `floor(20)` от
`4/7` возвращал значение **больше** `4/7`, а `ceil(20)` — то же самое число.

Причина — в цикле, который снижает масштаб, пока значение не влезет в int64:
там было зашито округление к ближайшему, а запрошенный режим игнорировался.
Теперь каждая отбрасываемая цифра уходит туда, куда просил вызывающий.

Это уточняет решение по Д11: «вернуть ближайшее представимое» остаётся, но
ближайшее **в запрошенную сторону**. Знак и порядок величины сохраняются, как
и раньше, а направление больше не теряется.

### Д18. `ShortFraction.toDouble` округлял дважды

`numerator / denominator` на `int` теряет последние биты операндов, а потом
округляет уже испорченное. `9007199254740993/7` давало `1286742750677284.5`
против правильного `1286742750677284.75`, который отдаёт `Fraction`. За 2^53
теперь берётся тот же точный путь, что у старшего семейства; ниже границы
остаётся обычное деление — там IEEE округляет один раз и делает это верно.

### Д19. Масштаб переполнялся в делении

У сдвигов проверка была, у деления — нет: `this.scale - other.scale`
переполнялся молча, и `Decimal(100, shiftRight: 2^63−1)`, поделённый на
десять, отвечал значением с масштабом, ушедшим в минус. Оно печаталось как
целое `100` и сравнивалось как целое, а сравнение двух таких значений роняло
`RangeError` из `_pow10`.

Правка зеркальна в обоих семействах. Тест для `ShortDecimal` пришлось писать
иначе: там представление каноническое сразу, поэтому за край масштаб уводит
единица, а не сотня — у сотни два нуля уже сняты.

## Цена правки Д19 и почему она нулевая

Проверка стоит на горячем пути, поэтому замерялась чередованием, дважды.

| | вызов `_scaleMinus` | проверка вписана в оператор |
|:--|:--|:--|
| `ShortDecimal` деление | медленнее на 5–9 % | без разницы |
| `Decimal` деление | в пределах шума | без разницы |
| `add-int` (контроль) | не сдвинулся | не сдвинулся |

Это ровно тот случай, что уже записан в решениях про `operator *`: вынесенная
в метод проверка не инлайнится. Вписанная — бесплатна.

## Что осталось из того же обзора

Документационное, отдельным заходом: README дважды обещает, что из четырёх
форм деления бросает только последняя — на нулевом делителе бросают все;
dartdoc `ShortDecimal` советует `toDecimal()`, которого нет при узком импорте;
отдельные операции `Short*` о переполнении молчат, а `ShortFraction` обещает
«nothing is lost»; вкладка Example на pub.dev покажет описание стенда, потому
что тур лежит в `example/bin/`, а не по одному из путей, которые ищет pub.dev.

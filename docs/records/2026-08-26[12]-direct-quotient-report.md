# Отчёт: прямой хвост округления

## Что было

```dart
Decimal divide(Decimal other, {int? scaleOnInfinitePrecision}) {
  final result = divideOrNull(other);
  if (result != null) return result;
  if (scaleOnInfinitePrecision == null) throw DecimalDivideException._(this, other);
  return divideToFraction(other).round(scaleOnInfinitePrecision);   // ← вот это
}
```

Хвост строил точную дробь — выравнивал масштабы, сокращал на `gcd` — и тут же
делил её обратно. Сокращение при этом на ответ не влияет никак.

Разложение по времени (JIT, на одно деление): весь `divide` — 0.606 µs, из них
`divideOrNull` 0.205 (в этой строке всегда впустую), дробь с округлением 0.391.

## Почему замена ничего не теряет

Не эмпирика, а тождество. Если `a·10ⁿ = q·b + r`, то поделив обе части на
`g = gcd(a, b)`, получаем `(a/g)·10ⁿ = q·(b/g) + r/g`, где `r/g` — целое и
меньше `b/g`. Значит:

- частное то же самое `q`;
- решение «округлять вверх» — это `2r ≥ b`, и оно равносильно `2(r/g) ≥ b/g`.

То есть сокращение — работа, которой ответ не требует.

Проверено и перебором до правки: 20 000 случайных пар (оба знака, масштабы от
−10 до 10, `n` от −8 до 16, базы до 25 цифр) — расхождений ноль.

## Что сделано

`Decimal._roundedQuotient(other, fractionDigits)`: выравнивание масштабов и
сдвиг к целевому свёрнуты в **одну** степень десяти, взятую с той стороны, где
она остаётся умножением; знак выносится в числитель; дальше одно деление и один
остаток.

```dart
final exponent = fractionDigits - scale + other.scale;
if (exponent > 0) {
  numerator *= _pow10(exponent);
} else if (exponent < 0) {
  denominator *= _pow10(-exponent);
}
```

**`ShortDecimal` оставлен как был, и это осознанная асимметрия.** Там
`ShortFraction._dropFraction` работает по сокращённой дроби, и сокращение —
не оптимизация, а то, что удерживает числа внутри int64: `_scaledOrNull`
возвращает null при переполнении и роняет вычисление на точный BigInt-путь.
Без сокращения этот путь звался бы заметно чаще, а наивный прямой счёт на `int`
молча переполнялся бы — то есть вернулся бы Д11. Причина записана в dartdoc
`_roundedQuotient`.

## Тесты

Написаны и **позеленели до правки** — иначе они фиксировали бы не старое
поведение, а новое:

- закон в `test/property_test.dart`: `divide` до `n` знаков совпадает с точной
  моделью на 2000 случайных пар; представимое деление возвращается точным, а не
  урезанным до `n`;
- точечные случаи в `test/decimal/divide_test.dart`: оба знака у обоих
  операндов, `n = 0`, отрицательный `n`, значение вида `1e30`, и сверка
  `divide == divideToFraction().round()` на двенадцати парах.

Всего 560 тестов (было 557), покрытие `lib/` осталось 100 % строк по каждому
файлу.

**Замечание про эталонную модель:** `Ref._shift` при отрицательном
`fractionDigits` делит числитель нацело и теряет остаток, поэтому
`roundToScaled` с отрицательным аргументом ненадёжен. Закон это обходит,
отрицательные проверяются точечно. Модель не чинилась — на нынешние тесты не
влияет, но знать стоит.

компиляция, прогон, `git checkout HEAD -- lib/`, компиляция, прогон, и так

против 8.12/7.74), как и должно быть — его не трогали.

Прогноз перед правкой был «около 10 µs»; вышло лучше, 8.6.

Строка в README перемерена заново с `--passes=2` и заменена целиком, вместе с
колонками конкурентов: наш `Decimal` 8.718 против `big_decimal` 5.171 —
отставание **1.7× вместо 2.7×**, метка `(▼2x)` из ячейки ушла.

## Что осталось в этой строке

Треть времени — попытка разделить точно (`divideOrNull`), которая здесь всегда
кончается `null`. Выбросить нельзя: `divide` обязан вернуть точный ответ там,
где деление представимо, пусть даже длиннее запрошенных `n` знаков.
`big_decimal.divide` в той же ситуации всё равно округлит до заданного
масштаба — он отвечает на более простой вопрос. Дальше жать нечего, не сломав
контракт.

# Перемер таблиц README

## Зачем

Числа в таблицах были сняты 2026-08-27 и устарели трижды: `raw-view`
переделан в пул из 103 циклов, в стенде появился пятый конкурент
`precise_decimal`, и прошли три ускорения — `divide` с числом знаков,
`ShortDecimal.divide` и сложение. Каждое ускорение проверялось чередующимся
замером отдельно, но подтвердить картину целиком мог только полный прогон.

Пока прогона не было, прозу вокруг таблиц править было нельзя: числа в тексте
и в таблице обязаны приходить из одного замера.

## Как снималось

```bash
dart compile exe example/bin/benchmark.dart -o <scratchpad>/bench
cd example && <scratchpad>/bench all --passes=2
```

13:04:18 → 14:47:00, час сорок три, 35 тестов в двух проходах, код выхода 0.
Во время прогона на машине не запускалось ничего.

Окружение, из шапки стенда:

```
Dart:   3.13.0 (stable) on "macos_arm64"
OS:     Version 26.5.2 (Build 25F84)
CPUs:   14
Mode:   AOT (dart compile exe)
Runs:   5 (median of the series)
Passes: 2 (the best of them per cell)
Deps:   decimal 3.2.6, decimal_type 0.0.3, fixed 6.1.1, big_decimal 0.7.0,
        precise_decimal 0.0.1, yet_another_decimal 1.2.0, big_double 1.0.2
```

Против прошлого раза окружение не сдвинулось: тот же Dart 3.13.0, та же
система, те же версии конкурентов. Добавился `precise_decimal 0.0.1`.

## Что куда пошло

Четыре набора данных, как и в прошлый перемер:

1. **Полная таблица** — сводка стенда без колонки `big_double`. К прежним
   четырём конкурентам добавилась колонка `precise_decimal`; она в зачёте
   участвует, поэтому метки `★` в этой таблице посчитаны стендом уже с ней.
2. **Короткая таблица** (раздел «Performance») — колонки `decimal`, `Decimal`,
   `ShortDecimal`, только int-наборы, метки пересчитаны заново по этим трём:
   `★` — победитель и все в пределах 10 %, `(▼Nx)` — во сколько раз медленнее
   победителя с округлением вниз, при `N < 2` метки нет.
3. **Блок окружения** — из шапки прогона; в README идут только конкуренты, наш
   пакет и `big_double` из строки `Deps` опущены, как и раньше.
4. **Отдельные числа в прозе** — их три, все три поправлены.

Ячейки не переносились руками: обе таблицы собраны скриптом прямо из сводки
стенда, короткая — с пересчётом меток по формуле выше. 190 ячеек глазами не
переносятся без ошибки.

## Что изменилось

**Строка `unrepresentable-divide` выиграна.** Была единственной, которую пакет
проигрывал; теперь `Decimal` идёт впереди всех в сравнении, а `ShortDecimal`
впереди `Decimal` на порядок:

| | 2026-08-27 | 2026-08-28 |
|:--|--:|--:|
| `decimal` | 126.541 µs | 124.405 µs |
| `big_decimal` | ★ 4.956 µs | 4.814 µs |
| `precise_decimal` | — | 4.274 µs |
| `Decimal` | 8.333 µs | ★ 3.766 µs |
| `ShortDecimal` | 7.530 µs | ★★ 0.353 µs |

**Четыре `★` на умножении вернулись.** В прошлом перемере `Decimal` терял метку
на `multiply-large-big-int`, `multiply-small-big-int`, `multiply-small-int` и
`multiply-dirty-int`, и терял на доли наносекунды. Теперь метка стоит на всех
шести строках умножения. Подгонять ничего не пришлось: как и было сказано в
прошлый раз, на умножении разницы между пакетами нет, и метка ходит туда-сюда
внутри полупроцента.

**`add-dirty-int` остаётся единственной строкой, где мы вторые** — 0.225 против
0.170 у `precise_decimal`. Причина разобрана в `2026-08-28[1]`: у них несущее
значение хранит `int`, пока помещается. Правкой сложения не лечится, это смена
представления и разговор для 2.0.

**Регрессии нет.** Остальная таблица подвинулась на единицы процентов в обе
стороны — это машина, а не код.

Числа в прозе:

| Где | Было | Стало |
|:--|:--|:--|
| `divide-dirty-big-int`, отставание `decimal` | 347 раз | 342 раза |
| `to-double-wide`, время `decimal` | 2.6 µs | 2.5 µs |
| `to-double-wide`, наше время | 2.3 µs | 2.4 µs |

## Что переписано в прозе

Два места устарели не числами, а утверждением, и оба названы в `docs/handoff.md`
заранее:

- абзац «The row this package still loses is `unrepresentable-divide`» — строка
  больше не проигрывается, и объяснение теперь про то, что `gcd` из этого пути
  ушёл: когда у делителя нет с десяткой общих простых множителей, ненулевой
  остаток от округления сам доказывает, что конечной записи нет;
- абзац после короткой таблицы, где `Decimal` и `ShortDecimal` на этой строке
  названы близкими, — между ними теперь порядок, и строка встала в один ряд с
  остальными строками деления.

Заодно `repeat-view`: `Decimal` был впереди `ShortDecimal` «в семьдесят раз»,
стало пятьдесят с лишним.

Обе правки перенесены в `README.ru.md` тем же коммитом, таблицы — один в один.
Проверено скриптом: строки замеров в двух файлах совпадают побайтно.

## Что осталось верным и проверено

- `compare` у `fixed` по-прежнему `ERROR` — «The results don't match»: его
  `compareTo` сравнивает хранимые целые, не приведя масштабы. Текст README
  рядом с таблицей верен.
- `to-double-wide` — единственная строка, где `ERROR` показывает `decimal`.
- `big_decimal` на делении малых чисел отказывается с `Rounding necessary`, и
  это по-прежнему `ERROR` в таблице.

## Подраздел про `precise_decimal`

Колонка в таблице появилась, а в прозе пакет не был назван ни разу: раздел
«What packages are already in place?» разбирал четверых. Владелец выбрал
дописать пятый подраздел — по фактам из `2026-08-27[3]`: чем он хорош
(единственный конкурент стенда, который поддерживает все 35 тестов и нигде не
отвечает неверно), в чём расходится с нами (сохраняет масштаб при печати, несёт
остальной GDA — `DecimalContext`, условия и ловушки; второго семейства на `int`
у него нет) и почему он выигрывает `add-dirty-int`.

Заодно поправлен счёт, который подраздел ломает: «три пакета из четырёх» стало
«из пяти», а список тех, у кого описанных проблем с делением нет, получил третье
имя.

Отдельным коммитом: перенос чисел и разбор нового конкурента — разные работы.

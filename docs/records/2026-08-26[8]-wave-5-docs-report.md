## Стенд

### Что чинили

Шесть дефектов методики, разобранных в плане. Итог:

- **Сток.** `MyBenchmarkBase.blackhole` — статическое поле, в которое уходит
  результат каждого измеряемого цикла. До этого наружу из `exercise` уходил
  только последний из ста.
- **Серия и медиана.** `--runs=N`, по умолчанию пять. В сводке медиана, в
  консоли рядом с ней разброс. Разброс оказался полезнее, чем ожидалось: он
  прямо показал, какие замеры испорчены посторонней нагрузкой (см. ниже).
- **Шапка окружения.** Версия Dart, ОС, число ядер, JIT или AOT, версии
  сравниваемых пакетов из `pubspec.lock`. Уходит в README под таблицу.
- **`prepared-view` → `repeat-view`.** Честно измерить «первую печать
  подготовленного числа» под строковым кешем нельзя в принципе: кеш переживает
  и сто циклов внутри `exercise`, и все вызовы `exercise` внутри `measure`.
  Поэтому сценарий не чинили, а назвали тем, чем он стал, — повторной печатью.
  Холодный путь остаётся за `raw-view`, где `-(-value)` каждый раз создаёт
  новый объект. `prepareValues` теперь одна на всех: прогон того же кода, что
  меряется.
- **Грязные наборы.** `add-dirty`, `multiply-dirty`, `divide-dirty` — базы без
  нулей на концах, без общих множителей и без повторов цифр, сгенерированы один
  раз с фиксированным зерном и выписаны в код константами. `divide-dirty` делит
  произведение обратно на его же множители: деление точное, но узнать об этом
  можно только через `gcd`.
- **Шесть операций.** `parse`, `compare`, `round`, `to-double`,
  `to-string-as-fixed`, `unrepresentable-divide`. Все на одном «денежном»
  наборе: семь знаков до точки, от трёх до восьми после.

### Чего в стенде сознательно нет

- **`raw-view-dirty`.** Существующий набор `raw-view` и так без нулей на
  концах, а случай с нулями закрыт отдельным `raw-view-zeros`. Ещё одна пара
  строк ничего бы не добавила, кроме ширины таблицы.
- **Бенчмарков дробей.** Аналога `divideToFraction` нет ни у одного конкурента,
  сравнивать не с чем. Цену дробей внутри пакета меряют его собственные тесты.

### Как проверяется ответ

Ожидаемое значение каждого набора посчитано **вне Dart** — точной рациональной
арифметикой на Python — и выписано в `tests.dart` рядом с данными. Это не
формальность: именно она поймала обе находки ниже.

Отсутствие операции больше не выдаётся за ошибку. Адаптер просто не
переопределяет то, чего у пакета нет; база бросает `UnsupportedOperation`, и
`run()` показывает «—».

## Две находки в чужих пакетах

**`fixed` 6.2.0 сравнивает неправильно.** `Fixed.compareTo` смотрит на
хранимые целые, не приведя масштабы:

```dart
if (minorUnits == other.minorUnits) {
  return decimalDigits.compareTo(other.decimalDigits);
} else {
  return minorUnits.compareTo(other.minorUnits);
}
```

Для 0.5 (base 5, scale 1) и 0.49 (base 49, scale 2) это даёт 5 < 49, то есть
`0.5 < 0.49`. В таблице README это `ERROR` со сноской.

**`decimal` при ограничении точности отбрасывает хвост, а не округляет.**
`Rational.toDecimal` по умолчанию берёт `truncate`. Мы округляем. Чтобы
сравнение мерило скорость, а не разницу в семантике, адаптер просит у него
округление явно: `toBigInt: (value) => value.round()`.

Заодно выяснилось, что `compareTo` в Dart не обязан возвращать -1/0/1: у
`decimal`, `fixed` и `decimal_type` он возвращает разность. Сценарий `compare`
суммирует `.sign`, иначе ожидаемое значение зависело бы от реализации.

## Цифры

Полный прогон: AOT, пять прогонов, медиана, Dart 3.13.0, macOS 26.5.2, 14 ядер.
Обе таблицы — в README, здесь только то, что стоит помнить.

| Что | Мы | Лучший из конкурентов | Разрыв |
|:--|--:|--:|--:|
| `divide-dirty-big-int` | 1.366 µs | 472.576 µs (`decimal`) | 345× в нашу пользу |
| `divide-small-big-int` | 5.523 µs | ERROR у всех, кроме `decimal` (614.881) | 111× |
| `repeat-view-big-int` | 0.024 µs | 19.012 µs (`decimal`) | 792× |
| `to-string-as-fixed` | 5.728 µs | 16.004 µs (`decimal`) | 2.8× |
| `to-double` | 0.705 µs | 2.002 µs (`decimal`) | 2.8× |
| `parse` | 10.506 µs | 10.942 µs (`big_decimal`) | вровень |
| `unrepresentable-divide` | 13.788 µs | 5.093 µs (`big_decimal`) | **2.7× не в нашу пользу** |

Последняя строка — единственная, где мы проигрываем, и она в README названа
прямо. Причина: `big_decimal` масштабирует и делит, а мы строим точную дробь и
округляем её. Дробь — то, из-за чего вообще возможны `divideOrNull` и
`isDivisibleBy`, так что размен сознательный.

`ShortDecimal` в сравнении не участвует (int64 — не та же работа, что `BigInt`),
но в таблице стоит: на арифметике он втрое-впятеро быстрее нашего `Decimal`, на
делении — в 25–30 раз.

### Про достоверность прогона

Первый заход был убит вместе с концом хода агента на 17-м сценарии из 34;
остаток домерян кусками тем же бинарником на той же машине. Разброс по всем
замерам после этого — не больше 13 %, у подавляющего большинства меньше 5 %,
при том что конвенции проекта допускают дрейф машины до 15 %.

Один замер (`divide-small-big-int`, наш `Decimal`) в первом заходе имел разброс
64 % — в него попал параллельный `dart analyze`. Он перемерян; медиана
изменилась с 6.492 на 5.523 µs. Это ровно тот случай, ради которого в стенд
добавлены серия и печать разброса: без них испорченный замер попал бы в README
и выглядел бы как обычное число.

# Хвост ревью краёв: сделано

Все три находки оказались дефектами, и ни одна из них не потребовала нового
решения владельца: правило Д27 («выдуманное число — не переполнение значения»)
их закрывает. Разбор — в плане, здесь только сделанное и проверенное.

## Что изменилось

### Д34 — `ShortFraction.operator /`

Знак делителя выносится в числитель **до** построения произведений: отрицается
положительный сомножитель числителя, у которого отрицание есть всегда. Пара
`int.min / -1`, которой знака положить некуда, больше не возникает там, где
ответ представим:

```dart
ShortFraction(2, 1) / ShortFraction(-1, 4611686018427387904);
// было: ArgumentError
// стало: -9223372036854775808
```

Когда числитель делителя равен `int.min`, знаменатель ответа не меньше `2^63` —
там отказ честный и остался.

### Д37 — `pow` с отрицательным показателем

Степень под единицей строится с проверкой переполнения (`_powOrNull`), а не
`math.pow`. Дальше три исхода:

- **степень поместилась** — как раньше, `one / power`;
- **степень не поместилась, а обратная величина основания есть** — ответ
  считается от неё: `5^-30` — это `0.2^30`, и `2^30` в int64 с запасом. Раньше
  это отвергалось;
- **обратной величины нет** — `ShortDecimalDivideException` с честной парой
  `1 / основание` вместо выдуманного делителя;
- **обратная величина есть, а её степень из int64 выходит** —
  `UnsupportedError`, как у `inverse`.

`ShortDecimal(int.min).pow(-3)` больше не жалуется на деление на ноль.

### Д35 — экспоненциальная запись и `toStringAsPrecision`

Округление ведущих цифр переехало в строку: `roundDigits` в `StringInternals`
(`lib/src/helpers.dart`), общий для обеих семей. `toStringAsExponential` больше
не зовёт `round` и не строит степень десятки вовсе, `toStringAsPrecision`
читает по нему перенос и потому округляет значение один раз, а не два.

```dart
Decimal.parse('1e-1000000').toStringAsExponential(2);       // 1.00e-1000000
ShortDecimal(1, shiftRight: 9223372036854775807)
    .toStringAsExponential(2);              // 1.00e-9223372036854775807
```

Показатель считается через `_scaleMinus`, то есть у самого дна масштаба отказ
приходит с тем же сообщением, что у `exponent`, и называет масштаб. У потолка
показателя перенос тоже упирается в край int64 и отказывает там же.

`toStringAsPrecision` пишет число целиком, и миллион знаков остаётся его
границей — но проверка стоит **до** вычисления числа знаков (оно само
заворачивается на краях масштаба), а в отказе теперь названы `precision` и
настоящая причина.

## Решения, принятые по ходу

Оба — по правилу Д27 и по прецеденту `inverse`; оба обратимы правкой в одном
месте, если владелец решит иначе.

1. **Ответ вне int64 у `pow` с отрицательным показателем — отказ, а не
   молчаливое переполнение.** `ShortDecimal(2).pow(-63)` бросает
   `UnsupportedError`. Довод тот же, что записан в dartdoc `inverse`:
   молчаливое переполнение ответило бы здесь положительное число отрицательным.
   Тип исключения для `3^-40` и `2^-63` при этом сменился, но обе формы бросали
   и раньше — сломать это не могло ничего.
2. **`toStringAsPrecision` длиннее миллиона знаков по-прежнему отказывает.**
   Граница миллиона — решение владельца, общее для пакета; менялась только
   честность сообщения.

## Чего это не задело

- **Стенд не затронут:** ни `pow`, ни `toStringAsExponential`, ни операторы
  дробей в адаптерах `example/lib/src/tests/` не участвуют. Горячие пути
  (`parse`, печать, `+`, `-`, `*`, `/`, `divide`, округление, сравнение) не
  тронуты ни одной правкой, перемер таблиц README от этой работы не зависит.
- **Молчаливое переполнение `*` у дробей** — политика, записанная в dartdoc
  класса; брутфорс подтвердил, что представимых ответов она не съедает.
- **Старшее семейство в Д34 и Д37 не менялось:** `BigInt` не заворачивается, и
  дифференциал это подтвердил — короткая семья теперь совпадает со старшей
  всюду, где ответ в int64 есть.

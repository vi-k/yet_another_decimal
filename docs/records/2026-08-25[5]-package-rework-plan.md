# План переработки до 1.2.0

Обоснование каждого пункта — в ревью, целевое устройство — в спеке. Здесь
только порядок и критерии.

## Почему такой порядок

Одно соображение определяет всю очерёдность.

**Тесты сейчас фиксируют внутреннее представление.** `base` и `scale`
сверяются в 245 местах, в том числе в арифметике, где форма хранения — артефакт
алгоритма. Быстрый путь точного деления даёт численно тот же результат с другим
`base` и другим `scale`. Значит:

> Пока тесты не переписаны, **любая оптимизация будет выглядеть как поломка**, и
> отличить настоящую регрессию от смены представления будет невозможно.

Отсюда: тестовый фундамент идёт первым, до единой правки в `lib/`. Дальше —
дефекты (от них уже есть красные тесты), дальше — производительность (её теперь
есть чем защитить), дальше — новый API, дальше — документация.

## Волна 0. Тестовый фундамент

Правок в `lib/` нет ни одной.

1. `test/support/reference.dart` — эталонная рациональная модель на `BigInt`
   (числитель и знаменатель) и генераторы случайных значений для обоих
   семейств. Тридцать строк модели, ноль зависимостей.
2. Property-тесты против модели: `+ - * ~/ % remainder`, все сравнения,
   `compareTo` и его согласованность с операторами, транзитивность,
   `floor/round/ceil/truncate`, round-trip `parse(toString())`,
   `toStringAsFixed(n)` — ровно `n` знаков и обратный разбор в `round(n)`.
3. Кросс-семейный тест: один список входов, обе реализации, одинаковый
   ожидаемый ответ. Он же ловит расхождения, которых сейчас 25.
4. **Сверка с конкурентом.** `decimal` добавляется в `dev_dependencies` корня
   (он уже стоит в `example/`). Для всякой операции, у которой есть аналог,
   тест сверяет три ответа — наш `Decimal`, наш `ShortDecimal` и `decimal` — и
   считает расхождение падением. Осознанные расхождения перечисляются явным
   списком с объяснением, как и расхождения между нашими семействами.
   Обоснование: сверка, проведённая в ревью, даёт красный на восьми дефектах из
   пятнадцати — в том числе на всех, где мы единственные, кто отвечает неверно.
5. Воспроизводители всех пятнадцати дефектов — по тесту на каждый, красные.
6. Из хелперов `expectDecimal`/`expectShortDecimal` убрать сверку `base`/`scale`
   везде, кроме `parse`, `toString` и `optimize`.
7. Табличные циклы разложить в отдельные `test(...)` или добавить `reason`.
   Сейчас упавший третий случай из тридцати семи скрывает остальные и не
   говорит, какой именно упал.
8. Разбить единый файл на 4336 строк по темам и семействам. У `ShortDecimal`
   завести отсутствующие группы `compare` и `toStringAsFixed`.

**Готово, когда:** пятнадцать тестов красные и падают ровно на описанном в
ревью поведении; все остальные зелёные; в арифметических проверках не осталось
сверки представления.

## Волна 1. Четыре критических дефекта

| Дефект | Правка |
|:--|:--|
| Д1 деление на отрицательное | вынести знак делителя до циклов разложения, оба семейства |
| Д2 `_pow10` переполняется | таблица констант; при разрыве масштабов ≥ 19 отвечать без домножения |
| Д3 деление на ноль зависает | проверка в начале `operator /`, `UnsupportedError` как у `Fraction` |
| Д4 `toBigInt` теряет порядок | домножать на `10^-scale`, как это уже делает `ShortDecimal.toInt` |

Д2 — самая крупная: одна таблица закрывает сравнение, сортировку, округление,
`toInt` и расхождение поведения между VM и web.

**Готово, когда:** четыре теста из волны 0 позеленели; property-тесты и
кросс-семейный проходят; `dart test` зелёный целиком.

## Волна 2. Остальные одиннадцать дефектов

Порядок внутри волны свободный, они независимы.

- Д5 `toStringAsFixed` не добивает нулями — `padLeft(scale).padRight(fractionDigits)`.
- Д6 падение под ассертами — внутренние вызовы через `_asIs`/`_pack`; вернуть
  закомментированную строку в `ShortDecimalDivideException.toString()`.
- Д7 `ShortDecimal.ten` неканонична — собрать через `_pack`.
- Д8 `divideToDouble` даёт `NaN` — считать масштабированием, не через
  `BigInt.operator /`.
- Д9 `Fraction` и отрицательный `fractionDigits` — поддержать, как у `Decimal`.
- Д10 и Д12 разбор строк — явная валидация вместо делегирования в
  `BigInt.parse`/`int.parse`; закрыть hex, `'-'`, `'+0'`, табуляцию. Заодно
  решить судьбу `'1e21'` из бэклога владельца.
- Д11, Д15 `ShortFraction` — перекрёстное сокращение до умножения, проверка
  диапазона в округлении.
- Д13 `ShortFraction` и `int.min` — нормализация знака и внятный `ArgumentError`.
- Д14 `ShortDecimal *` — перекрёстное сокращение множителей 2 и 5 до умножения.

**Готово, когда:** все пятнадцать позеленели; покрытие строк не ниже 90 % по
каждому файлу `lib/`.

## Волна 3. Производительность

Только теперь — когда есть чем отличить регрессию от смены представления.

| Пункт | Ожидаемый выигрыш |
|:--|:--|
| П1 `gcd`: выбор алгоритма по величине аргументов | 1.5× на деньгах, 2.5× на длинных `Fraction`, без потерь на остальном |
| П2 таблица степеней десяти | 1.87× сложение, 2.2× `compareTo` |
| П5 быстрый путь точного деления | 11.9× `divide-small`, снимает проигрыш в `divide-large` |
| П6 снятие нулей за три ступени | 5–17×, плюс 1.58× на связке «сложение и `hashCode`» |
| П3 строковый кеш `toString` | снимает проигрыш конкуренту на повторном выводе |
| П4 прямой путь `toDouble` | 1.7× для `Decimal`, 26× для `ShortDecimal` |

П1 переписан после того, как первая рекомендация («заменить на штатный
`BigInt.gcd`») была опровергнута замером внутри пакета: на паре «большое
делимое, маленький делитель» штатный алгоритм в 2.7 раза медленнее. Пороги
выбора алгоритма подобраны замером и обязаны быть перепроверены на целевой
платформе. Обоснование в коде дополняется ссылкой на замер — issue sdk#46180
остаётся открытым и по-прежнему объясняет половину картины.

П4 обязателен к покрытию тестом на побитовое совпадение с
`double.parse(toString())` на границах `2^53` и `10^22` — это место, где легко
молча испортить точность.

**Готово, когда:** все тесты зелёные; прогон стенда показывает улучшение по
целевым строкам и отсутствие ухудшения по остальным; `divide-large` больше не
проигрывает.

## Волна 4. Публичный API

Всё аддитивно, ничего не ломается.

1. `abstract interface class FixedPoint<T extends FixedPoint<T>>` в
   `lib/src/fixed_point.dart`, оба семейства его реализуют. В 1.2.0 наружу не
   экспортируется. Имя выбрано с расчётом на то, что когда-нибудь он может
   стать публичным супертипом в роли `num` для `int` и `double`.
2. Тест симметрии: сверка наборов публичных членов плюс явный список осознанных
   расхождений.
3. `lib/src/bridge.dart` — `ShortDecimal.toDecimal()` и
   `Decimal.toShortDecimalOrNull()`.
4. Тотальное деление: `divideOrNull`, `divide(other, {scaleOnInfinitePrecision})`,
   `isDivisibleBy`.
5. Недостающие члены: `toJson`/`fromJson`, `Decimal.toInt()`,
   `ShortDecimal.toBigInt()`, `precision`, `isPositive`, `inverse`, `pow` с
   отрицательным показателем, `Fraction`: `compareTo`/`abs`/`inverse`/`toDouble`,
   `ShortFraction.toShortDecimal()`.
6. Реализовать `toStringAsExponential` и `toStringAsPrecision` в обоих
   семействах — сейчас у `Decimal` они бросают, у `ShortDecimal` их нет.

**Готово, когда:** тест симметрии зелёный; `dart pub publish --dry-run` без
предупреждений; `pana` не ниже нынешних 160/160.

## Риски

| Риск | Что делать |
|:--|:--|
| Быстрый путь деления меняет представление результата | волна 0 обязана предшествовать волне 3; иначе регрессию не отличить от смены формы |
| Микробенчмарк даёт ответ, противоположный замеру внутри пакета | так уже случилось с `gcd`: синтетические данные показали одно, реальная форма аргументов — обратное. Любую оптимизацию `gcd`, `pow` и деления мерить только внутри пакета |
| Прямой `toDouble` может молча испортить точность | тест на побитовое совпадение с нынешним путём на границах диапазона |
| Общий интерфейс становится публичным API | набор членов фиксируется до релиза; расширять потом можно, сужать — нет |
| Волна 2 велика | дефекты независимы, можно резать на несколько заходов; критерий готовности от этого не меняется |

## Чего в плане нет

- **Не трогаем то, что работает.** Плоское представление `base × 10^-scale`,
  отрицательный масштаб как рабочий режим, снятие нулей строковыми средствами в
  `toString`, ленивая нормализация `Decimal`, немедленная у `ShortDecimal`,
  `int fastGcd`, `_dropFraction` мимо дробей, сравнение по значению — всё это
  проверено и остаётся.
- **Не объединяем реализации двух семейств.** Измерено: общая реализация через
  дженерики стоит 2× из-за боксинга. Дублируется контракт, и его закрывает
  интерфейс.
- **Не вводим проверку переполнения `ShortDecimal`.** Контракт остаётся
  молчаливым по решению владельца; чинится только переполнение промежуточных
  значений при представимом результате.
- **Не делаем 2.0.** Список отложенного — в конце спеки.
- **Не гонимся за `const`.** Для `Decimal` он недостижим в принципе: у `BigInt`
  нет `const`-конструктора, и `_packed` тут ни при чём. У `ShortDecimal` он уже
  есть внутри и наружу выходить не должен — публичный «сырой»
  `const`-конструктор отдал бы пользователю право создавать неканоничные
  значения, а это ровно причина Д7.

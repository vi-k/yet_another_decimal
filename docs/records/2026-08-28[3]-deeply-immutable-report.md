# `const`, `vm:deeply-immutable` и кеш печати

## Откуда вопрос

Владелец спросил, насколько `ShortDecimal` нужен `const`: по существу он
используется в нескольких константах — можно ли это расширить или, наоборот,
убрать ради кеша печати, которого у `ShortDecimal` нет.

## Что оказалось

**Публичного `const`-конструктора у `ShortDecimal` нет вовсе.** `_asIs`
приватный, а `ShortDecimal(...)`, `parse` и `fromJson` — фабричные. Написать
`const ShortDecimal(1999, shiftRight: 2)` нельзя: такого API наружу не
выведено. Внутри пакета `const` работает в пяти местах — `zero`, `one`, `two`,
`ten` и `const ShortFraction._(0, 1)`. Наружу видны четыре константы, и вся
польза от их константности — возможность взять их в константном контексте.

**Кеш печати блокирует не `const`, а прагма.** Проверено компилятором:

```
Error: Deeply immutable classes must only have final non-late instance fields.
  String? _text;                  ← поле кеша
  late final String text = ...;   ← и ленивое тоже
```

**Прагме `const`-конструктор не нужен.** Класс с обычным конструктором и
`final`-полями её проходит — проверено там же. Значит `const` и кеш здесь
независимы: отказавшись от `const`, кеша не получишь, пока стоит прагма.
Формулировка «конструкторы `const`, писать некуда», стоявшая в README и в
документах, называла вторичную причину.

**Расширять `const` наружу по-прежнему нельзя** — по причине, записанной в
`docs/architecture.md` ещё раньше: публичный `const`-конструктор возможен
только «сырой», без упаковки, а это отдаёт пользователю право строить
неканоничные значения, то есть дефект Д7 (`ShortDecimal.ten`, ломающая `Set` и
`Map`). Даже «целочисленный» конструктор не спасает: у целых тоже снимаются
хвостовые нули — `ten` хранится как `base 1, scale -1`.

## Чем подтверждается, что прагма работает

Компилятор проверяет только соответствие класса требованиям. Что обещанное
свойство есть на деле, не проверял никто, и это стоило проверить.

Признак прямой: **разделяемый объект возвращается из другого изолята тем же
экземпляром**, а копируемый — новым. Прогон:

```
ShortDecimal (deeply-immutable)    тот же объект: true
Decimal (поле BigInt)              тот же объект: false
контрольный класс из двух int      тот же объект: false
```

Контрольный класс здесь не для красоты: он повторяет поля `ShortDecimal`, но
без аннотации, — и копируется. Значит дело в аннотации, а не в том, что поля
простые.

Закреплено в `test/isolate_test.dart`, четыре теста: `ShortDecimal` переживает
изолят собой, `Decimal` возвращается копией, класс без аннотации — тоже копией,
и константы семейства разделяются наравне с обычными значениями. Проходит и на
Dart 3.6.0 — пороге SDK.

## Закрытый вопрос из плана 2.0

В `2026-08-26[13]` стояло: «Проверить до решения: совместим ли `Expando` с
`@pragma('vm:deeply-immutable')` — если нет, то выбор становится
"неизменяемость или кеш"», и тем же держался риск «не начинать волну 2, пока не
проверен `Expando` под `vm:deeply-immutable`».

**Совместим.** Проверено 2026-08-28 на AOT: чтение и запись работают, в том
числе на константах, канонизированных компилятором, — запись через одну
читается через равную ей другую. У разделённого объекта в другом изоляте
таблица своя, то есть кеш туда не переезжает, но и не ломается.

Цена чтения, отдельной пробой (AOT, 10 млн обращений, медиана пяти):

| Что | Время |
|:--|--:|
| поле объекта | 0.86 нс |
| `Expando` | 5.69 нс |
| построение самой короткой строки | 36.27 нс |

Против 1550 нс, которые стоит печать `ShortDecimal` в стенде, — шум. То есть
дилемма «прагма или кеш» ложная: кеш можно держать в `Expando`, ничего не
снимая.

**Не сделано.** Это правка на горячем пути, её нужно мерить стендом целиком и
решать отдельно; выигрыш придётся на `repeat-view` (сейчас `ShortDecimal` 1.550
против 0.028 у `Decimal`), а `raw-view` не сдвинется — там пул из 103 циклов, и
кеш по объекту в него не попадает.

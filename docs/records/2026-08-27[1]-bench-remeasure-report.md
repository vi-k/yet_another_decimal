# Перемер таблиц README

## Зачем

Таблицы в `README.md` были сняты до правок 2026-08-26/27. Часть тех правок
встала на измеряемый путь: проверка числа знаков в округлении, запасной точный
путь в делении. Каждая из них была проверена чередованием отдельно и разницы не
дала, но подтвердить это мог только полный прогон.

## Как снималось

```bash
dart compile exe example/bin/benchmark.dart -o /tmp/bench
cd example && /tmp/bench all --passes=2
```

Час пятнадцать, 35 тестов в двух проходах, код выхода 0. Во время прогона на
машине не запускалось ничего: посторонняя нагрузка может замер только
замедлить, а в ячейку идёт лучшая из двух медиан — то есть помеха, попавшая в
один проход, отсекается вторым.

Окружение прогона, из шапки стенда:

```
Dart:   3.13.0 (stable) on "macos_arm64"
OS:     Version 26.5.2 (Build 25F84)
CPUs:   14
Mode:   AOT (dart compile exe)
Runs:   5 (median of the series)
Passes: 2 (the best of them per cell)
Deps:   decimal 3.2.6, decimal_type 0.0.3, fixed 6.1.1, big_decimal 0.7.0,
        yet_another_decimal 1.2.0, big_double 1.0.2
```

Версии конкурентов берутся отсюда, а не из текста README: раньше в README
стояла `fixed 6.2.0`, тогда как `pubspec.lock` резолвил 6.1.1. В этот раз
сходится.

## Что куда пошло

Из вывода стенда берутся четыре набора данных.

1. **Полная таблица** (`README.md`, после блока окружения) — сводка стенда без
   колонки `big_double`. Метки `★`/`▼` переносятся как есть: `big_double` и
   `ShortDecimal` в зачёте стенда и так не участвуют, поэтому снятая колонка
   ничьей метки не меняет.
2. **Короткая таблица** (раздел «Performance») — колонки `decimal`, `Decimal`,
   `ShortDecimal`, только int-наборы. Метки считаются заново по этим трём
   колонкам: `★` — победитель и все, кто в пределах 10 %, `(▼Nx)` — во сколько
   раз медленнее победителя с округлением вниз, и при `N < 2` метка не ставится
   вовсе.
3. **Блок окружения** — из шапки прогона.
4. **Отдельные числа в прозе** — их три, и все три пришлось поправить, см.
   ниже.

Заодно снято примечание о том, что четыре строки `repeat-view` мерены отдельно:
после полного прогона оно неверно.

## Что изменилось

**Регрессии нет.** Против прошлого прогона всё стало быстрее — и у нас, и у
конкурентов, примерно на одну десятую по всей таблице разом. Это машина, а не
код: правки, которые стояли на измеряемом пути, разницы не дают, что и
проверялось чередованием заранее.

Числа в прозе, которые пришлось поправить:

| Где | Было | Стало |
|:--|:--|:--|
| `divide-dirty-big-int`, отставание `decimal` | 352 раза | 347 раз |
| `to-double-wide`, наше время | 2.5 µs | 2.3 µs |

Третье число — «`big_decimal` рвёт `unrepresentable-divide` примерно в 1.7
раза» — уцелело: 4.956 против 8.333, то есть те же 1.7.

## Единственное содержательное изменение таблицы

`Decimal` потерял `★` на четырёх строках умножения из шести:
`multiply-large-big-int`, `multiply-small-big-int`, `multiply-small-int`,
`multiply-dirty-int`.

Потерял на доли наносекунды. В `multiply-large-big-int` победитель —
`decimal_type` с 0.115 µs, порог десяти процентов равен 0.1265, у нас 0.127.
Разрыв — половина наносекунды. На остальных трёх строках то же самое: 0.103
против порога 0.1023, 0.040 против 0.0396.

Подгонять тут нечего. Метка считается по измеренному, правило порога описано в
README рядом с таблицей, и то, что на этих строках четыре пакета укладываются в
полпроцента друг от друга, — само по себе честный ответ: на умножении разницы
между пакетами нет.

## Проверка пункта про `fixed`

`compare` у `fixed` по-прежнему `ERROR` — «The results don't match». Его
`compareTo` сравнивает хранимые целые, не приведя масштабы, и ставит 0.5 ниже
0.49. Текст README рядом с таблицей остаётся верным.

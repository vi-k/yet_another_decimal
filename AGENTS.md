# AGENTS.md

Точка входа для ИИ-агентов, работающих над этим проектом (Claude Code, Codex
CLI и любых других). `CLAUDE.md` содержит только ссылку на этот файл.

Сессия может оборваться в любой момент. Этот документ описывает протокол,
который позволяет следующей сессии продолжить работу без расспросов владельца.

## Проект в двух словах

`denary` — Dart-пакет для десятичных чисел с фиксированной точкой
без потери точности. Два независимых типа: `Decimal` (на `BigInt`, без
ограничений по величине) и `ShortDecimal` (на `int`, быстрый, с риском
переполнения). Публикуется на [pub.dev](https://pub.dev/packages/denary).

Устройство — в `docs/architecture.md`. Текущее состояние — в `docs/handoff.md`.

## Протокол старта сессии

Выполнять **до** любого ответа владельцу и до любых правок:

1. Прочитать `docs/handoff.md` — что происходит прямо сейчас, на чём
   остановились, что не доделано.
2. Прочитать `docs/backlog.md` — пожелания владельца, ждущие своей очереди.
3. Прочитать `docs/conventions.md` — как здесь принято писать код и коммиты.
4. Прочитать `docs/architecture.md` — если работа касается устройства пакета.
   Если в `docs/handoff.md` названа запись из `docs/records/`, по которой идёт
   работа (спека, план), прочитать и её: там обоснование решений, которые
   нельзя пересматривать вслепую.
5. Проверить рабочее дерево: `git status`, `git log --oneline -5`.
   Незакоммиченные правки могут быть как оборванной работой предыдущей сессии
   (описана в `docs/handoff.md`), так и правками владельца — **это разные
   вещи, см. раздел «Границы коммита»**.
6. Если в бэклоге есть подходящая запись — предложить взять её в работу.
   Самому в бэклог не писать.

## Протокол во время работы

- `docs/handoff.md` держать актуальным непрерывно, а не в конце работы.
  Обновлять его сразу после каждого заметного шага: сменилась цель, появился
  промежуточный результат, обнаружено препятствие. Считать, что сессия
  оборвётся на следующей минуте.
- Перед сколько-нибудь объёмной работой класть план в `docs/records/` и
  ссылаться на него из `docs/handoff.md`.
- Проверять работу командами из раздела «Команды» до того, как назвать её
  сделанной.

## Протокол завершения эпизода

1. Прогнать `dart analyze`, `dart test`, `dart format`.
2. Написать отчёт в `docs/records/` (см. «Историю правок»).
3. Вычистить из `docs/backlog.md` пункты, которые закрыты этой работой.
4. Обновить `docs/handoff.md` — убрать из него завершённый эпизод, оставить
   только то, что актуально дальше.
5. Закоммитить и смержить в `main`.

### `docs/handoff.md`

Только текущее состояние проекта. Чего там быть не должно:

- пересказа истории коммитов — она есть в `git log`;
- разбора уже законченных эпизодов — это `docs/records/`;
- пожеланий владельца — это `docs/backlog.md`.

### `docs/backlog.md`

Список владельца. Агент его **читает** и предлагает взять пункт в работу.
Когда пункт сделан — **удаляет** его оттуда. Своих пунктов агент туда
**не добавляет**: всё, что придумал агент, живёт в `docs/handoff.md` или в
отчёте в `docs/records/`.

### `docs/architecture.md`

Устройство и принципы: типы, инварианты, ключевые решения и их причины.
Ничего быстроменяющегося — статус работ живёт в `docs/handoff.md`.

## История правок

Спеки, планы, отчёты и ревью — в `docs/records/`.

Имя файла: `YYYY-MM-DD[N]-name-kind.md`, где квадратные скобки — литералы,
`N` — порядковый номер записи за день:

```
docs/records/2026-08-25[1]-ai-onboarding-report.md
```

`kind` — жанр записи, одно слово:

| `kind` | Что это |
|:-------|:--------|
| `design` | Устройство и API |
| `plan` | План работ |
| `report` | Отчёт о сделанном: о волне правок, о разборе дефекта, о предмержевом ревью одной работы |
| `review` | Полное ревью проекта глазами ревьюера: `project-review`, `architecture-review`, `flutter-review`, `bug-hunter`, `performance-review` |

Нужного слова нет в списке — взять своё, но по тому же принципу: одно слово о
жанре записи, а не о её теме.

Каждый файл в `docs/records/` начинается с шапки текущего состояния:

```markdown
> **Состояние на YYYY-MM-DD:** что с этой работой сейчас — сделано и
> смержено (коммит), брошено, частично сделано, пересмотрено позже.
> **Что это:** одна фраза о содержимом.
> **Связанные записи:** имена других файлов в `docs/records/`.
```

Шапку поддерживать в актуальном состоянии: когда работа из старой записи
пересмотрена или отменена, править шапку той записи, а не только писать новую.

### Вердикты в ревью

При работе с ревью в конец каждой находки дописывается вердикт по этой находке.
Прозу самой находки при этом не трогать. Вердикт — отдельным абзацем. Вердиктов
не больше одного на находку.

## Язык

- По-русски: `AGENTS.md`, `docs/**`, `README.ru.md`, общение с владельцем.
- По-английски: `README.md`, `CHANGELOG.md`, dartdoc-комментарии в `lib/`,
  сообщения коммитов, тексты исключений и ошибок.

**`README.ru.md` — перевод `README.md`, и он обязан быть актуальным всегда.**
Правка `README.md` не считается законченной, пока то же самое не перенесено в
перевод: это одна работа и один коммит, а не два. Английский — исходник,
русский — перевод; расходиться они не должны ни на абзац. Таблицы замеров
переносятся один в один, без пересчёта. Подробности — в `docs/conventions.md`.
В пакет на pub.dev перевод не идёт: он в `.pubignore`.

## Git

- Мержить прямо в `main`, без PR.
- **Границы коммита:** не коммитить чужие правки вместе со своими. Если в
  рабочем дереве есть изменения, которых агент не делал, — они принадлежат
  владельцу. Коммитить только свои файлы поимённо (`git add <файл>`), никогда
  не `git add -A` и не `git commit -a` вслепую. Сомневаешься, чья правка, —
  спросить владельца.
- Сообщения коммитов — по-английски, повелительное наклонение, как в текущей
  истории: `Add ...`, `Fix ...`, `Update ...`, `Remove ...`.

```bash

cd example && dart bin/benchmark.dart all      # все бенчмарки, все пакеты

dart pub publish --dry-run                     # проверка перед публикацией
```

## Публикация на pub.dev

Публикация — это **вся связка целиком**: коммит `Release X.Y.Z`, тег `vX.Y.Z`,
push и `dart pub publish`, одним заходом и подряд. Ни одну часть по отдельности.

Подготовку к публикации (правка `CHANGELOG.md`, версии в `pubspec.yaml`,
`dart pub publish --dry-run`) делать свободно — это обычные правки в дереве, их
можно откатить.

Разрешение на публикацию — **только явное и только на эту связку**. Оно не
переносится на следующий релиз, не наследуется от прошлого раза и не выводится
из готовности релиза. «Всё готово к публикации» — не разрешение. Пройденный
чеклист — не разрешение.

Если в сообщении владельца есть хоть что-то ещё, кроме просьбы опубликовать, —
не запускать ничего из связки, даже если слово «публикуй» стоит в нём прямым
текстом. **Не спрашивать — отказать.** Не задавать вопроса «публиковать?», не
предлагать вариантов, не выносить решение на подтверждение. Сделать остальную
работу и отказать в публикации, назвав условие: разрешение должно прийти
отдельным запросом владельца, состоящим только из просьбы опубликовать.

Сомневаешься — не публикуй. Отказ стоит одного сообщения, ошибка стоит номера
версии.

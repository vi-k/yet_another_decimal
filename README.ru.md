## С чего начать

```bash
dart pub add yet_another_decimal
```

```dart
import 'package:yet_another_decimal/yet_another_decimal.dart';

final price = Decimal.parse('19.99');
final total = price * Decimal(3);

print(total); // 59.97
print(Decimal.parse('0.1') + Decimal.parse('0.2') == Decimal.parse('0.3')); // true

// Не у всякого деления есть десятичный ответ, поэтому пакет заставляет сказать,
// какой ответ вам нужен. Бросить может только последнее из этих.
print(total.divideOrNull(Decimal(7))); // null
print(total.divide(Decimal(7), scaleOnInfinitePrecision: 2)); // 8.57
print(total.divideWithRemainder(Decimal(2))); // 29 remainder 1.97
print(total / Decimal(3)); // 19.99
```

Числовых типов два, и сами по себе они не смешиваются:

- `Decimal` хранит значение в `BigInt`. Не переполняется никогда.
- `ShortDecimal` хранит его в `int`. В несколько раз быстрее и меньше, а за
  границей int64 молча заворачивается — ровно так же, как `int`.

Каждый импортируется без другого:

```dart
import 'package:yet_another_decimal/decimal.dart';       // семейство на BigInt
import 'package:yet_another_decimal/short_decimal.dart'; // семейство на int64
```

Какой брать и чего стоит второй — в разделе
[`Decimal` vs `ShortDecimal`](#decimal-vs-shortdecimal). Остальная часть этого
README — о том, зачем пакет существует и во что он обходится по замерам.

## Зачем?

На февраль 2025 года на [pub.dev](https://pub.dev) есть несколько пакетов,
работающих с десятичными числами.

### Какие пакеты уже есть?

#### [decimal](https://pub.dev/packages/decimal)

Прекрасный пакет, корректно работающий с десятичными числами. Существует
с 2014 года и постоянно обновляется. В одном из последних обновлений (3.2.0)
производительность заметно выросла. До этого скорость была слабым местом
пакета. Это и стало одной из причин, по которым появился
[yet_another_decimal](https://pub.dev/packages/yet_another_decimal): я начал
писать его до выхода 3.2.0. Впрочем, я написал бы его в любом случае. Об этом
ниже.

#### [fixed](https://pub.dev/packages/fixed)

У пакета сложности с делением. Нельзя просто взять и выполнить 1 / 8, получив
ожидаемые 0.125:

```dart
final a = Fixed.fromInt(1, decimalDigits: 0); // 1
final b = Fixed.fromInt(8, decimalDigits: 0); // 8
print('$a / $b = ${a / b}'); // 1 / 8 = 0

final c = Fixed.fromInt(10, decimalDigits: 1); // 1.0
final d = Fixed.fromInt(80, decimalDigits: 1); // 8.0
print('$c / $d = ${c / d}'); // 1.0 / 8.0 = 0.1

final e = Fixed.fromInt(100, decimalDigits: 2); // 1.00
final f = Fixed.fromInt(800, decimalDigits: 2); // 8.00
print('$e / $f = ${e / f}'); // 1.00 / 8.00 = 0.13
```

Результат зависит от масштаба делимого и делителя: деление берёт больший из
двух и округляет ответ до него. У одной восьмой есть точная десятичная запись —
и её всё равно округляют, не сказав ни слова. Масштаб ответа приходится знать
заранее и просить его:

```dart
final a = Fixed.fromInt(1, decimalDigits: 0).copyWith(decimalDigits: 3); // 1.000
final b = Fixed.fromInt(8, decimalDigits: 0); // 8
print('$a / $b = ${a / b}'); // 1.000 / 8 = 0.125
```

До переписывания этого README здесь говорилось ещё и о том, что деление идёт
через `double`, и показывалось, как `Fixed.parse('111111111111111111')`,
возведённое в квадрат и поделённое обратно, даёт `111111111111111120`. Это
больше не так, и утверждение убрано: сегодня `fixed` делит в `BigInt`, округляя
половины от нуля. Проверено на 6.1.1 и 6.2.0 — ответ возвращается точным:

```dart
final a = Fixed.parse('111111111111111111');
final b = a * a;
print(b); // 12345679012345678987654320987654321
print(b / a); // 111111111111111111
```

Остаётся первое, и оно же — причина существования этого пакета: деление
округляет до масштаба, которого никто не просил. Здесь `Decimal(1) / Decimal(8)`
равно `0.125` независимо от того, из чего собраны обе стороны, а деление, у
которого нет конечной десятичной записи, говорит об этом вместо тихого
округления.

#### [decimal_type](https://pub.dev/packages/decimal_type)

Этот пакет тоже делит через `double`, но, в отличие от
[fixed](https://pub.dev/packages/fixed), не знает об одном крайнем случае:

```dart
var a = Decimal(BigInt.parse('644385861467633436300000'), decimalPrecision: 0);
var b = Decimal.fromInt(123);
print('$a / $b = ${a / b}'); // FormatException: Could not parse BigInt 238909442826288e+21
```

Сначала результат деления считается как `double`, потом переводится в строку
через `double.toStringAsFixed`, а строка — в `BigInt`. Но
`double.toStringAsFixed` не всегда возвращает результат «asFixed». При
достижении предела погрешности метод переключается на
`double.toStringAsExponential`. Автор этой особенности не заметил. Зато мы
быстрее выяснили, что у пакета под капотом.

#### [big_decimal](https://pub.dev/packages/big_decimal)

Этот, похоже, портирован с Java:

> A bugless implementation of BigDecimal in Dart based on Java's BigDecimal.

Но 1 на 8 в нём просто так не поделить:

```dart
final a = BigDecimal.one;
final b = BigDecimal.parse('8');
print('$a / $b = ${a.divide(b)}'); //  Exception: Rounding necessary
```

Числа можно поделить, указав режим округления. Но мы хотели не этого.

```dart
final a = BigDecimal.one;
final b = BigDecimal.parse('8');
print('$a / $b = ${a.divide(b, roundingMode: RoundingMode.FLOOR)}'); // 1 / 8 = 0
```

Или изменив масштаб делимого:

```dart
final a = BigDecimal.parse('1.000');
final b = BigDecimal.parse('8');
print('$a / $b = ${a.divide(b)}'); // 1.000 / 8 = 0.125
```

Не угадали с масштабом — получили ошибку.

Вот так работает «a bugless implementation of BigDecimal».


### Каким он должен быть?

Три пакета из четырёх меня не устроили — из-за ошибок в вычислениях, неполной
функциональности (деление) или использования `double` под капотом.

У [decimal](https://pub.dev/packages/decimal) и
[yet_another_decimal](https://pub.dev/packages/yet_another_decimal)
описанных проблем с делением нет. Не нужно самому считать `scale`, и никакого
`double` под капотом.

Числа читаются из строк — включая экспоненциальную запись — и пишутся обратно,
ничего не теряя по дороге:

```dart
print(Decimal.parse('1.5e21')); // 1500000000000000000000
print(Decimal.parse('-0.000001')); // -0.000001
print(Decimal.parse('19.99').toStringAsFixed(4)); // 19.9900
```

[decimal](https://pub.dev/packages/decimal) возвращает результат как `Rational`
([rational](https://pub.dev/packages/rational)), поскольку не всякий результат
деления представим десятичным числом. Но его легко превратить в `Decimal`:

```dart
final a = Decimal.one;
final b = Decimal.fromInt(256);
print('$a / $b = ${a / b}'); // 1 / 256 = 1/256
print('$a / $b = ${(a / b).toDecimal()}'); // 1 / 256 = 0.00390625
```

Если результат десятичным числом не представим, то есть у числа бесконечное
количество знаков после точки (бесконечная точность), будет брошено исключение.
Но если передать в `toDecimal` параметр `scaleOnInfinitePrecision`, ограничив
точность, число будет переведено в десятичное с потерей точности и без
исключения.

```dart
final a = Decimal.one;
final b = Decimal.fromInt(3);
print('$a / $b = ${a / b}'); // 1 / 3 = 1/3
print('$a / $b = ${(a / b).toDecimal(scaleOnInfinitePrecision: 6)}'); // 1 / 3 = 0.333333
```

[yet_another_decimal](https://pub.dev/packages/yet_another_decimal) поступает
наоборот и возвращает результат сразу:

```dart
final a = Decimal.one;
final b = Decimal(256);
print('$a / $b = ${a / b}'); // 1 / 256 = 0.00390625
```

Мне хотелось, чтобы пакет, работающий с десятичными числами, по умолчанию
возвращал десятичное число. Но не у всякого деления есть десятичный ответ — у
одной трети его нет, — поэтому пакет заставляет сказать, какой ответ вам нужен.
Четыре способа, и упасть может только последний:

```dart
final a = Decimal.one;
final b = Decimal(3);

print(a.isDivisibleBy(b)); // false — спросить до деления
print(a.divideOrNull(b)); // null — поделить и получить ответ
print(a.divide(b, scaleOnInfinitePrecision: 6)); // 0.333333 — округлить сразу
print(a / b); // бросает DecimalDivideException
```

По умолчанию тянуться стоит к `divideOrNull`: он задаёт тот же вопрос, что и
ловля исключения, и делает это в несколько раз быстрее — примерно в пять раз
у `Decimal` и больше чем в сто у `ShortDecimal`, где само деление стоит
наносекунды, а бросок по-прежнему около микросекунды. `operator /` — быстрая
форма для случая, когда деление заведомо точное: значение, домноженное на
степень десятки, или делитель, являющийся множителем делимого. Деление денег на
части — не такой случай: у трети от 23.99 конечной десятичной записи нет, и
`Decimal.parse('23.99') / Decimal(3)` бросит. Деньги делят, сперва спустившись
до наименьшей единицы, — и тогда ничего не теряется:
`Decimal.parse('23.99') << 2` — это 2399 копеек, `~/ Decimal(3)` даёт по 799 на
часть, а `%` говорит, какие две остались.

А когда всё-таки бросает, исключение — не тупик: оно несёт в себе все остальные
ответы этого деления.

```dart
final a = Decimal.one;
final b = Decimal(3);
try {
  print('$a / $b = ${a / b}');
} on DecimalDivideException catch (e) {
  print('${e.dividend} / ${e.divisor} = ${e.fraction}'); // 1 / 3 = 1/3
  print('${e.dividend} / ${e.divisor} = ${e.quotientWithRemainder}'); // 1 / 3 = 0 remainder 1
  print('${e.dividend} / ${e.divisor} = ${e.round(6)}'); // 1 / 3 = 0.333333
}
```

Исключений можно избежать, воспользовавшись одним из методов:
`divideToDouble`, `divideToFraction`, `divideWithRemainder`.

Так я старался избежать разночтений. Нужен результат в `double` — скажите об
этом явно:

```dart
print('$a / $b = ${a.divideToDouble(b)}'); // 0.3333333333333333
print('$a / $b = ${a.divideToFraction(b)}'); // 1/3
print('$a / $b = ${a.divideWithRemainder(b)}'); // 0 remainder 1
```

Подход, реализованный в [decimal](https://pub.dev/packages/decimal), удобен
тем, что позволяет выполнить ряд действий, промежуточные результаты которых
десятичным числом не представимы, а конечный результат — всё-таки десятичный.
Например: 1 / 3 * 9:

```dart
final rational = Decimal.fromInt(1) / Decimal.fromInt(3) * Decimal.fromInt(9).toRational();
final decimal = rational.toDecimal(); // 3
```

Пакет, работающий только с десятичными числами, так изящно этот пример не
решит. Или придётся прибегнуть к округлению и потерять точность:

```
1 / 3 = 0.333
0.333 * 9 = 2.997
```

Но можно взять отдельные решения для работы с дробями — например,
[fraction](https://pub.dev/packages/fraction) или уже упомянутый
[rational](https://pub.dev/packages/rational).

У [yet_another_decimal](https://pub.dev/packages/yet_another_decimal) есть свой
класс `Fraction` с базовыми возможностями работы с дробями.

```dart
final a = Fraction(BigInt.from(1), BigInt.from(2));
final b = Fraction(BigInt.from(1), BigInt.from(3));
final f1 = a * b;
final f2 = a / b;
final f3 = a + b;
final f4 = a - b;
print('($a) * ($b) = $f1 -> ${f1.round(6)}'); // (1/2) * (1/3) = 1/6 -> 0.166667
print('($a) / ($b) = $f2 -> ${f2.toDecimal()}'); // (1/2) / (1/3) = 3/2 -> 1.5
print('($a) + ($b) = $f3 -> ${f3.round(6)}'); // (1/2) + (1/3) = 5/6 -> 0.833333
print('($a) - ($b) = $f4 -> ${f4.round(6)}'); // (1/2) - (1/3) = 1/6 -> 0.166667
```

### Производительность пакетов

Числа ниже сняты стендом из [`example/`](example), пересобранным под 1.2.0, —
что он делает и почему, написано в [`example/README.md`](example/README.md).
Коротко:

- каждый ответ проверяется до того, как его засекут, поэтому неверный ответ
  никогда не выдаётся за быстрый;
- каждый бенчмарк меряется пять раз, а весь набор прогоняется дважды
  (`--passes=2`); в таблицу идёт лучшая из двух медиан, потому что посторонняя
  нагрузка на машину может замер только замедлить;
- результат каждого измеряемого цикла уходит в сток, выбросить который
  оптимизатору не позволено;
- пакет, у которого такой операции нет, показывает `—`, а не ошибку.

Одна строка — один проход по списку значений, а число — во что этот проход
обошёлся в микросекундах. `★` отмечает победителя и всех, кто в пределах 10 %
от него, `▼Nx` говорит, во сколько раз медленнее победителя. `ShortDecimal`
в этом зачёте не участвует и носит собственную метку: `★★` там, где он быстрее
любого пакета из сравнения, — то есть строки, где этой метки нет, и есть строки,
на которых int64 не даёт ничего. Абсолютные значения сами по себе не значат
ничего: другая машина даст другие. Смысл — в соотношениях.

*Как запустить:*

```bash
dart compile exe example/bin/benchmark.dart
example/bin/benchmark.exe all --passes=2
```

неверным. [fixed](https://pub.dev/packages/fixed) и
[decimal_type](https://pub.dev/packages/decimal_type) возвращают 0 на
`1 / 256 / 256 / …` — вот что фиксированный масштаб делает с маленьким числом, —
а `fixed` ещё и ставит 0.5 ниже 0.49 в `compare`, потому что его `compareTo`
смотрит на хранимые целые, не приведя сперва масштабы.
[big_decimal](https://pub.dev/packages/big_decimal) в этой колонке честнее
всех: он отказывается с `Rounding necessary` вместо неверного ответа — но отказ
тоже не результат, и показывается он всё тем же `ERROR`.

`to-double-wide` — единственная строка, где `ERROR` показывает
[decimal](https://pub.dev/packages/decimal), и её стоит разобрать отдельно.
В её значениях больше значащих цифр, чем помещается в `double`, поэтому каждое
из них приходится округлять, и весь вопрос лишь в том, попадёт ли округление
в ближайший `double`. Набор сгенерирован вслепую — не подбором значений, на
которых кто-то ошибается, — а ожидаемые ответы посчитаны вне Dart точным
переводом. Из двадцати `decimal` промахивается мимо ближайшего `double` на
семи, и `big_decimal` тоже на семи; оба делят один `double` на другой, а это
округление дважды. На 100 000 случайных значений пакеты расходятся на 33 815 из
них, и на 300 выборочно проверенных точной арифметикой расхождений этот пакет
был прав каждый раз, а `decimal` — ни разу.

Эта же строка — та, где самые быстрые ответы оказываются неверными:
`big_decimal` проходит её за 0.8 µs, а `decimal` за 2.6 против наших 2.3.

Там, где деление точное, разрыв — не про `BigInt` против `int`, а про то, что
видит алгоритм. `divide-dirty` делит произведение обратно на его же множители —
каждый шаг точен, и заранее об этом ничто в числах не говорит, — и
[decimal](https://pub.dev/packages/decimal) тратит на это в 347 раз больше
времени, чем этот пакет.

Строка, которую этот пакет по-прежнему проигрывает, — `unrepresentable-divide`:
[big_decimal](https://pub.dev/packages/big_decimal) округляет непредставимое
частное примерно в 1.7 раза быстрее. То, что осталось от этого разрыва, — скорее
свойство, чем недосмотр. `divide` возвращает точный ответ всякий раз, когда у
деления есть конечная десятичная запись, сколько бы знаков она ни занимала, и
узнать об этом стоит одного `gcd` — который на этой строке тратится всегда и не
пригождается никогда, потому что треть не выходит ровной. `big_decimal.divide`
в любом случае округляет до выданного ему масштаба и такого вопроса не задаёт —
то есть отвечает на меньший.

#### Описание бенчмарков

##### add

Сложение чисел:

10000000000000000000 + 1000000000000000000 + 100000000000000000 + 10000000000000000 + 1000000000000000 + 100000000000000 + 10000000000000 + 1000000000000 + 100000000000 + 10000000000 + 1000000000 + 100000000 + 10000000 + 1000000 + 100000 + 10000 + 1000 + 100 + 10 + 1 + 0.1 + 0.01 + 0.001 + 0.0001 + 0.00001 + 0.000001 + 0.0000001 + 0.00000001 + 0.000000001 + 0.0000000001 + 0.00000000001 + 0.000000000001 + 0.0000000000001 + 0.00000000000001 + 0.000000000000001 + 0.0000000000000001 + 0.00000000000000001 + 0.000000000000000001 + 0.0000000000000000001 + 0.00000000000000000001 = 11111111111111111111.11111111111111111111

Очень простая операция. Но заметьте: в случае десятичных чисел она куда
сложнее умножения.

##### multiply-large

Умножение больших чисел:

123456789 * 123456789 * 123456789 * 123456789 * 123456789 * 123456789 * 123456789 * 123456789 * 123456789 * 123456789 = 822526259147102579504761143661535547764137892295514168093701699676416207799736601

Для десятичного числа операция простая. Ошибиться в ней невозможно. Проще
операции нет.

##### multiply-small

Умножение малых чисел:

0.0123456789 * 0.0123456789 * 0.0123456789 * 0.0123456789 * 0.0123456789 * 0.0123456789 * 0.0123456789 * 0.0123456789 * 0.0123456789 * 0.0123456789 = 0.0000000000000000000822526259147102579504761143661535547764137892295514168093701699676416207799736601

Операция простая, но не все пакеты готовы иметь дело с числами, у которых
больше 20 знаков после точки.

##### divide-large

Деление больших чисел:

822526259147102579504761143661535547764137892295514168093701699676416207799736601 / 123456789 / 123456789 / 123456789 / 123456789 / 123456789 / 123456789 / 123456789 / 123456789 / 123456789 / 123456789 = 1

Деление — не самая сильная сторона большинства пакетов. Даже целых чисел! Даже
таких, у которых и результат целый!

##### divide-small

Деление малых чисел:

1 / 256 / 256 / 256 / 256 / 256 / 256 / 256 / 256 / 256 = 0.000000000000000000000211758236813575084767080625169910490512847900390625

Задача трудная. Споткнуться легко. [decimal](https://pub.dev/packages/decimal)
её решает, но какой ценой! Некоторые пакеты идут на трюк с `double` и
спотыкаются об него. А некоторые и не пытаются.

##### divide-large-and-view и divide-small-and-view

Деление чисел и перевод результата в читаемый вид.

Пакеты могут пользоваться в работе промежуточными представлениями, которые
ускоряют операции, но не имеют понятной пользователю десятичной формы. (Именно
так делал [decimal](https://pub.dev/packages/decimal) до версии 3.2.0.) Поэтому
тесты divide-large и divide-small, где выполняется только деление, могут быть
далеки от реальной жизни. Эти тесты делают то же самое, что divide-large и
divide-small, но дополнительно переводят результат операции (именно операции,
а не каждого шага внутри неё) в читаемый вид. (И раньше на этих тестах
[decimal](https://pub.dev/packages/decimal) сильно терял в производительности.)

Признаюсь честно, решение, устроившее меня по производительности, я искал
долго.

Технически перевод таких чисел заметно отличается от перевода чисел без нулей

надо только вместе.

##### repeat-view

Перевод тех же самых чисел в читаемый вид во второй раз — и во все последующие.

Печатать одно и то же значение снова и снова — это то, чем занят экран, и пакет
вправе помнить, что он напечатал в прошлый раз. raw-view меряет первый перевод,
этот — все последующие, и смысл они имеют только вместе: пакет, который быстр
здесь и медленен там, имеет кеш, а не более быстрый алгоритм.

`Decimal` печатную форму хранит; `ShortDecimal` — нет: его конструкторы
`const`, и хранить её негде. [decimal_type](https://pub.dev/packages/decimal_type),
[fixed](https://pub.dev/packages/fixed) и [big_decimal](https://pub.dev/packages/big_decimal)
не хранят ничего.

До версии 1.2.0 этот тест назывался prepared-view и не мерил вообще ничего: он
печатал одно значение сто раз, и на девяносто девять из них отвечал кеш.

##### repeat-view-zeros

То же самое на числах с большим количеством ведущих или хвостовых нулей.

##### add-dirty, multiply-dirty, divide-dirty

Те же три операции на значениях, в которых нет ничего круглого: ни хвостовых
нулей, которые можно снять, ни общих множителей, которые можно сократить, ни
повторяющейся цифры. Все остальные наборы здесь собраны из степеней десятки или
из одного повторённого множителя, а это лучший случай и для снятия нулей, и для
`gcd`, и для быстрого пути деления. Деньги выглядят не так.

divide-dirty делит произведение обратно на его же множители. Каждое деление в
нём точное, но заранее об этом в числах ничто не говорит — увидеть это может
только `gcd`.

##### parse

Чтение двадцати денежных чисел из строк. Всем пакетам даются одни и те же
строки.

Строка не вполне сравнивает равное с равным, и разница здесь — осознанное
решение с нашей стороны: наш `parse` останавливается на цифрах и масштабе,
оставляя каноническую форму тому, кто её спросит, тогда как остальные пакеты
нормализуют значение на месте. Читать эту строку надо вместе с raw-view и
repeat-view — там работа, которую наш `parse` не сделал, возвращается.

##### compare

Сравнение соседних чисел одного порядка, но разного масштаба — так, чтобы
сравнение нельзя было решить по показателю и пришлось сперва привести оба числа
к общему масштабу.

[fixed](https://pub.dev/packages/fixed) 6.1.1 показывает здесь `ERROR`: его
`compareTo` сравнивает хранимые целые, не выравнивая масштабы, и потому ставит
0.5 ниже 0.49. Стенд проверяет каждый ответ до того, как его засечь, и неверный
ответ никогда не выдаётся за быстрый.

##### round

Округление до двух знаков, половины — от нуля.

##### to-double

Перевод в ближайший `double`.

##### to-double-wide

Тот же перевод на числах, в которых значащих цифр больше, чем помещается в
`double`, — а это единственный случай, когда округление к ближайшему `double`
вообще составляет вопрос. `to-double` выше работает на денежных значениях, где
все пакеты сходятся.

Двадцать значений сгенерированы с фиксированным зерном и без отбора, а их
ожидаемые ответы получены точным переводом из десятичного в двоичное вне Dart.
Порядки держатся между `1e-4` и `1e16`, где Dart печатает `double` так же, как
генератор, поэтому сравнение идёт побайтово.

##### to-string-as-fixed

Запись числа ровно с двумя знаками после точки — та самая операция, которая
форматирует деньги для экрана.

##### unrepresentable-divide

Деление на три: ни у одного из результатов нет конечной десятичной записи,
поэтому каждый приходится округлять до десяти знаков. Это цена тотальных форм
деления — `divide(other, scaleOnInfinitePrecision: 10)` здесь,
`toDecimal(scaleOnInfinitePrecision: 10)` в [decimal](https://pub.dev/packages/decimal),
`divide(..., scale: 10)` в [big_decimal](https://pub.dev/packages/big_decimal).
Пакеты, которые так не умеют вовсе, показывают `—`.

### [decimal](https://pub.dev/packages/decimal) vs [yet_another_decimal](https://pub.dev/packages/yet_another_decimal)

Меньше всего мне хочется соревноваться с автором
[decimal](https://pub.dev/packages/decimal), особенно когда я вижу, сколько лет
этому пакету и как хорошо он поддерживается. Не думаю, что мне есть что
предложить принципиально нового в привычном подходе к десятичным числам. Даже
при разных подходах под капотом итог будет снаружи, а не внутри. И это примерно
тот же набор возможностей с примерно той же производительностью.

Но на самом деле решение написать свой
[yet_another_decimal](https://pub.dev/packages/yet_another_decimal) было
вызвано не только слабой (на тот момент) производительностью
[decimal](https://pub.dev/packages/decimal). Была и другая причина. Для своей
задачи мне нужно было лёгкое десятичное число, которому под капотом для
хранения значений нужен обычный `int` вместо `BigInt`. Мои значения помещались
даже в int32. Это результаты тренировок: геопозиция, расстояние, набор высоты,
темп, пульс, каденс, мощность. Мне, программисту старого поколения, морально
тяжело разбрасываться ресурсами там, где без этого можно обойтись. Особенно
когда я жду большого объёма данных и вычислений над ними. И я с удивлением
обнаружил, что готового решения на [pub.dev](https://pub.dev) нет.

Так что `Decimal` изначально не был главной целью пакета. Главной целью был
`ShortDecimal`. `Decimal` стал естественным развитием пакета.

## `Decimal` vs `ShortDecimal`

Два семейства, три способа их импортировать:

```dart
// оба и мост между ними
import 'package:yet_another_decimal/yet_another_decimal.dart';

// только семейство на BigInt
import 'package:yet_another_decimal/decimal.dart';

// только семейство на int64
import 'package:yet_another_decimal/short_decimal.dart';
```

Берите `Decimal`, когда порядки величин заранее неизвестны: у него нет границы
и он не переполняется. Берите `ShortDecimal`, когда известно, что величины
малы, а важна скорость: он в несколько раз быстрее и меньше, а его переполнение
молчаливо. Мост между ними живёт только в общем импорте, потому что он —
единственное, чему нужны оба.

Оба семейства отзываются на одни и те же имена. Два из этих имён — операторы,
а операторы легко прочесть наоборот, поэтому у каждого есть словесная пара:

| Оператор | То же самое, словами |
|:--|:--|
| `value >> n` | `value.movePointLeft(n)` — делит на `10^n` |
| `value << n` | `value.movePointRight(n)` — умножает на `10^n` |

`>>` двигает точку **влево** — именно это и сбивает читателя с толку.

## Ограничения `ShortDecimal`

У `ShortDecimal` те же возможности, что у `Decimal`, но значения хранятся в
`int` со всеми вытекающими. С одной стороны, это высокая производительность,
с другой — возможность неконтролируемого переполнения значения, которого не
случится при использовании `BigInt`. Можно написать код, который будет
контролировать переполнение, но это сильно усложнит и замедлит алгоритмы.
Сложение слишком просто, чтобы обременять его дополнительными проверками.
Каждая такая проверка увеличит время выполнения операции в разы.

Поэтому пользоваться `ShortDecimal` следует, только держа в уме возможность
переполнения:

```dart
print(ShortDecimal(9223372036854775807) + ShortDecimal.one); // -9223372036854775808
```

Границы возможностей `ShortDecimal` — это границы `int`. На нативных
платформах и в wasm это int64, в среде js точность обещана только до int53.

Для int64 значащие цифры (в терминах пакета — база), то есть значение без
ведущих и хвостовых нулей, не должны выходить за пределы
[-9223372036854775808..9223372036854775807].

```dart
final a = ShortDecimal(9223372036854775807) >> 40; // ok
final b = ShortDecimal(9223372036854775807) << 23; // ok
print(a); // 0.0000000000000000000009223372036854775807
print(b); // 922337203685477580700000000000000000000000
```

Само число 922337203685477580700000000000000000000000 далеко выходит за
пределы `int`. Но его база (без хвостовых нулей) в int64 помещается.

Однако работать с этим числом придётся в том же масштабе:

```dart
//   922337203685477580700000000000000000000000
//                   - 100000000000000000000000
// = 922337203685477580600000000000000000000000
print(b - (ShortDecimal(1) << 23)); // 922337203685477580600000000000000000000000 <- ok

//   922337203685477580700000000000000000000000
//                                          - 1
// = 922337203685477580699999999999999999999999
print(b - ShortDecimal(1)); // -200376420520689665 <- переполнение
```

Такие ограничения накладывают на `ShortDecimal` необходимость постоянно
оптимизировать значение, получившееся в результате операций над ним, — чтобы
дольше сохранять возможность оставаться в границах `int`. `Decimal` в такой
оптимизации не нуждается.

Например, умножение двух чисел: 1.2 * 5. Под капотом всё хранится в целочисленной
переменной (`base`) и параметре, указывающем, где стоит десятичная точка
(обычно его называют `scale`). 1.2 будет храниться как (base: 12, scale: 1),
а 5 — как (base: 5, scale: 0).

```dart
final a = Decimal.parse('1.2'); // хранится как base 12, scale 1
final b = Decimal.parse('5'); // хранится как base 5, scale 0

final c = ShortDecimal.parse('1.2'); // хранится как base 12, scale 1
final d = ShortDecimal.parse('5'); // хранится как base 5, scale 0
```

Умножение таких чисел — операция довольно простая: базы перемножаются,
масштабы складываются. Результат получится: (base: 60, scale: 1). Это 6. И
`Decimal` не нужно приводить его к (base: 6, scale: 0). А вот для
`ShortDecimal` это жизненно важно.

```dart
final r1 = a * b;
print(r1); // 6, хранится как base 60, scale 1

final r2 = c * d;
print(r2); // 6, хранится как base 6, scale 0
```

`Decimal`, конечно, мог бы после каждой операции приводить значение к
нормальному виду, то есть к (base: 6, scale: 0), но это дополнительное время,
которое в большинстве случаев тратится впустую. А там, где используется
`BigInt`, практической нужды в этом и нет: между (base: 6, scale: 0) и
(base: 60000000000, scale: 10) не такая уж большая разница. Зато в случае `int`
переполнения можно достичь очень быстро. Например, достаточно умножить 1.0 на
1.0, то есть (base: 10, scale: 1) на (base: 10, scale: 1), всего 18 раз, чтобы
выйти за границу `int`. И это при том, что там всего лишь 1!

```dart
var a = Decimal.parse('1.0');
for (var i = 0; i < 18; i++) {
  a *= Decimal.parse('1.0');
}
print(a); // 1, хранится как base 10000000000000000000, scale 19

final i = 10000000000000000000; // The integer literal 10000000000000000000 can't be represented in 64 bits.
```

Вот почему значение стоит упаковывать после каждой операции — чтобы дольше
оставаться в границах `int`. Но о производительности беспокоиться не нужно:
в случае `int` это будет намного быстрее, чем `BigInt` без упаковки.

```dart
var a = ShortDecimal.parse('1.0');
for (var i = 0; i < 18; i++) {
  a *= ShortDecimal.parse('1.0');
}
print(a); // 1, хранится как base 1, scale 0
```

`Decimal` и `ShortDecimal` крутят одни и те же алгоритмы, поэтому расстояние
между этими двумя колонками — это расстояние между `BigInt` и `int`: два-три

Две строки — про другое. В `repeat-view` `Decimal` впереди в семьдесят раз,
потому что хранит строку, которую напечатал в прошлый раз, а `ShortDecimal`
хранить её негде — его конструкторы `const`. В `unrepresentable-divide` они
близки: строка меряет одно длинное деление, а на таких длинах `BigInt` не
намного хуже `int`.

неважно и подойдёт `Decimal` из любого пакета. Если же их очень много или если
память на счету, `ShortDecimal` в несколько раз дешевле — при условии, что вы
помните о его ограничениях.

### Оптимизация `Decimal`

На часть того, о чём можно спросить десятичное число, — сколько у него знаков
после точки, каково его значение без масштаба, равно ли оно другому
десятичному, — ответ есть только в канонической форме: база со снятыми
хвостовыми нулями и подогнанный под неё масштаб. `Decimal` хранит так не всякое
значение, потому что дорога туда стоит арифметики на `BigInt`, а большинство
значений об этом никогда не спрашивают. Он упаковывает значение в тот первый
раз, когда каноническая форма кому-то понадобилась, и держит результат под
рукой.

Должен быть и способ попросить её вручную — на случай, когда алгоритм сам этого
не делает, — и это `normalized()`:

```dart
final packed = value.normalized();
```

Он отвечает значением в канонической форме, и повторный вызов на результате не
стоит ничего: каноническая форма канонична сама себе.

До 1.2.0 то же самое делал `optimize()`, который ничего не возвращал, а вместо
этого менял получателя. Тот метод по-прежнему работает и объявлен устаревшим:
методу, меняющему то, на чём его вызвали, нечего делать в типе-значении.

Пользователю не нужно знать ни об упаковке и масштабировании, ни о `base` и
`scale`. Что пользователю законно может понадобиться — это число, разобранное
на части, и для этого есть `unscaledValue` и `exponent`: оба читают каноническую
форму, поэтому равные десятичные отвечают одинаково, из чего бы они ни
получились.

#### Что упаковка делает с печатью

Ничего, в большинстве случаев. Это исправление: прежние версии этого раздела
показывали, что упаковка ускоряет `toString` в пятьдесят раз, — и те числа были
сняты до того, как `toString` начал хранить напечатанную строку.

Печатать одно и то же значение снова и снова теперь бесплатно в любом случае:
первый вызов печатает, остальные читают сохранённую строку. Десять миллионов
вызовов `toString()` на одном числе, AOT, на той же машине, на которой мерены
таблицы выше, с результатом, уходящим в сток, который оптимизатору не позволено
выбросить:

| десять миллионов печатей одного значения | |
|:--|--:|
| как есть | 0.02 s |
| после `normalized()` | 0.02 s |

Разница видна на значениях, каждое из которых печатается по одному разу, — и
смотрит она в другую сторону:

```dart
var v = Decimal(1000000000000000000) >> 18; // = 1, и не в канонической форме

for (var i = 0; i < 10000000; i++) {
  final next = i.isEven ? -v : v; // каждый раз новое число
  sink += next.toString().length; // и 'normalized()' перед этим — во втором прогоне
}
```

| десять миллионов значений, каждое печатается один раз | |
|:--|--:|
| как есть | 1.36 s |
| `normalized()` перед каждой печатью | 5.38 s |

Упаковать число стоит в несколько раз дороже, чем напечатать его. `toString`
и так снимает хвостовые нули со строки, которую строит, а это дешевле, чем
снимать их с `BigInt` и выделять память под десятичное число, чтобы сложить
туда результат. Вот почему нормализация не встроена в `toString`: всякий, кто
печатает число один раз и забывает о нём, платил бы за каноническую форму,
которой не просил.

А там, где значение уже канонично, платить не за что и выигрывать нечего —
1.58 s против 1.61 s на тех же десяти миллионах.

Итого: `normalized()` — ради самой канонической формы: ради `unscaledValue`,
ради `exponent`, ради десятичного числа, которое будут много раз сравнивать или
использовать ключом в `Map`. Это не способ печатать быстрее; способ — та самая
сохранённая строка.

`ShortDecimal` ничего этого не нужно: он нормализует значение в каждой
операции, а его `normalized()` отвечает самим получателем.
